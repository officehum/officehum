Your three claims, checked

Checked against code on main, design docs, every worktree and the Linear project

Each claim was tested against what the repository actually does, what the accepted designs say, and what Linear plans. A claim can be true in the design and still unbuilt, so each verdict says which.

Confirmedbuilt and designed
Claim 1

Pi Durable is the underlying agent harness.

True in code and in every plan. The working Front Desk opens a Pi Durable Harness over JSONL storage (packages/office/src/solo.ts). Pi Durable 1.3.0 is pinned exactly and is a peer dependency of every role. The Paper design states it “remains the only agent harness and the authority for conversation state, task checkpoints, approvals, and recovery.” Linear plans one Pi Durable harness per office (RASF-3101, RASF-3104).

  • Pi Durable is marked experimental upstream, so every runtime call is meant to go through one adapter in @officehum/office. That adapter epic (RASF-3065) is still in progress; today only solo mode exists.
  • Office Hum adds what Pi Durable lacks: approval gates (built as Pi Durable hooks), and the planned workboard and relay. Pi Durable itself has no multi-agent board.
Partly trueneeds one correction
Claim 2

Office Hum is the collection of Pi Durable roles, built as operational roles for medium-sized companies.

The roles part is right. Every role is a portable Pi Durable agent: an MIT package that must pass its evals in a bare Pi Durable harness with no Office Hum code loaded. Third-party roles fit as long as they follow the same package contract.

The definition is too narrow. In the accepted design the roles are the free part. Office Hum is the layer on top that hosts, coordinates and configures them (workboard, relay, overlays, Studio, approvals, hosting). A role never depends on Office Hum.

  • Market wording disagreed. The README said “medium-sized businesses”, the Linear project “small businesses”, and RASF-3199 and RASF-3205 “mid-market”. Linear now says medium-sized companies everywhere (updated 15 Oct).
  • One role exists. Front Desk is built. Bookkeeper (called the reference role) and Office Manager are in the backlog. Sales was not planned; it is now an epic (RASF-3295) under a new catalog of free roles for every department (RASF-3293).
Splitone built, two not yet
Claim 3

Agents use Ultramarine 1, Office Hum offers a model marketplace, and the Paper Office libraries are implemented as agent tools.

Built

Ultramarine 1 Flash is the default. Merged in PR #14 (RASF-3282, Done). New Front Desk conversations start on paper/ultramarine-1-flash at maximum thinking. A saved conversation keeps its original model, and a Paper failure never silently falls back to another provider. The provider is registered by the CLI host, so a bare Pi Durable user gets the model choice from the manifest but must register the provider themselves until it moves into its own package (RASF-3297, M1).

Now planned

A model marketplace was not in the Office Hum plan when this was checked. It is now epic RASF-3296 (M4): a provider catalog with acceptance tests (RASF-3298) and a Studio marketplace screen (RASF-3299), building on bring-your-own-key (RASF-3175). Today the CLI still accepts only paper or openai, though pi-ai 1.0.2 already ships 44 provider adapters.

Not built

The Paper Office tools are designed, not implemented. The design is approved (14 Oct) and the versioned file store it depends on is merged (PRs #15, #16). The tool pack, the document service, the restricted Python worker and the Word, PowerPoint and Excel adapters do not exist yet. paper-docx, paper-pptx and paper-xlsx are not installed anywhere on this machine. Their tickets (RASF-3283 to 3286, plus the new Word and Excel adapters RASF-3300 and RASF-3301) are now in M3.

01

What Office Hum is

The product in one paragraph

Office Hum is an open-source multi-agent office. Each job in a department, such as the front desk, bookkeeping or office management, is its own AI agent with its own instructions, tools, skills, approval rules and test suite. Every agent runs on Pi Durable, which keeps a durable record of each conversation and tool call so work survives a crash. Office Hum hosts these agents, lets them hand work to one another through a shared workboard, asks people for approval before anything risky, and lets each business adjust the agents in plain language without editing their code. The hosted version at officehum.com runs one office per business on its own small server.

02

The stack and its boundaries

Who owns what, and what crosses each line

Four layers stack on top of one another, and Paper Instruments plugs in at two separate points: as a model provider under Pi Durable, and as document libraries inside a sandboxed worker. Paper never runs its own agent loop.

Who owns what

Host and product

Office Hum

  • Picks which roles run and injects their connectors (calendar, email, accounting)
  • Supplies the approver: who may say yes, and through which screen
  • Coordinates roles: workboard, relay, hand-offs by ticket type
  • Keeps each business's overlays and runs Studio and the configurator
  • Owns files: storage, leases, review and publication
Never edits a role package. Never runs its own agent loop.
Execution authority

Pi Durable

  • Runs the agent loop: model turn, tool calls, next turn
  • Commits every entry and tool result before showing it
  • Stores approval decisions and checkpoints in task memos
  • Resumes interrupted work without repeating finished steps
  • Holds each conversation's pinned model and tools
Knows nothing about tickets, roles, businesses or Office files.
Supplier

Paper Instruments

  • Ultramarine 1 Flash answers model requests through pi-ai
  • paper-docx, paper-pptx and paper-xlsx edit Office files inside the worker
  • Paper Rubric may add optional quality notes on documents
Never holds conversation state, credentials or approval power. Feather, Paper's own office agent, is a reference only, not a second harness.

What crosses each boundary

Each line in Figure 2.1 is a contract. Knowing what passes across it tells you where a bug or a policy belongs.

BoundaryWhat crosses itWhat never crosses it

Role → Pi DurableExtensions, tools with a declared replay class, prompt sections, the approval hook, agent settingsThe officehum.json manifest. Pi Durable ignores it; Office Hum reads it for routing, Studio and the Inbox.
Pi Durable → modelA ModelRef, the prompt and the tool schemas, through a pi-ai providerSilent fallback to another provider. A failed call is surfaced and the work stays resumable.

Document service → Paper workerRead-only leased versions, one writable staging folder, bounded CPU, memory and timeNetwork, home folder, host credentials, agent state
Role → roleTickets of a declared type, through the workboard and relayDirect calls to another role's tools
03

Pi Durable, the harness

The engine every agent runs on

Pi Durable (@earendil-works/pi-durable) is a durable agent harness from Earendil, built on the Pi model library pi-ai. Its one promise: nothing is shown before it is stored. Conversations, model turns, tool calls and custom state are written to storage in atomic commits. If the process dies mid-turn, reopening storage picks up the work where it stopped.

Pi Durable termMeaningHow Office Hum uses it
HarnessOne open store plus the machinery that runs agents on itSolo mode: one per state folder. Planned: one per office, hosting every role.
ConversationA transcript of immutable entries; can be forked or owned by a taskEach role session is a conversation. Inbound email gets its own.
AgentModel, thinking level, extensions, tools and instructions, stored per conversationA role's agent settings. The model is pinned when the conversation is created.
ExtensionA named bundle of tools, prompt sections, hooks and tasksdefineRole turns a role package into extensions.
TaskA durable state machine that checkpoints every stepEvery tool call is a task, so an approval decision survives a restart.
HookCode that runs before or after a tool, request or compactionThe approval gate is a beforeTool hook. Context and memory hooks are designed.
Submission + requestIdInput admitted durably, deduplicated by request IDThe CLI's --request-id; the planned relay uses the event ID.
Task-owned conversationA child conversation owned by a task: a subagentDesigned for narrow helper sub-agents inside one role (RASF-3235).
CautionPi Durable's API is experimental and can change between releases. Office Hum pins one exact version (1.3.0), lets Dependabot propose upgrades, and routes runtime calls through one adapter. The upgrade to 1.1.x is its own ticket (RASF-3237).
04

Roles

A role is a portable Pi Durable agent

A role is an npm package, free under the MIT license, that installs into any Pi Durable 1.3.x harness with or without Office Hum. Most of it is plain files that Pi users already know. Its code is a thin entry point that defines the tools and calls defineRole.

@officehum/bookkeeper/ package.json # Pi Durable and pi-ai as peer dependencies officehum.json # manifest: tools, approvals, accepts, connectors, default model AGENTS.md # who the role is and what it may not do (under 1,000 words) APPEND_SYSTEM.md # hard rules appended to the end of the prompt skills/collections/SKILL.md # loaded on demand with read_skill src/index.ts # tools, approval conditions, defineRole(...) evals/ # scenarios that must pass in a bare Pi Durable harness

Four layers keep a role honest

LayerLives inJob
ContextAGENTS.md, APPEND_SYSTEM.mdInforms. Who the role is. No amounts or thresholds.
KnowledgeSkills and their reference filesInforms. Loaded only when needed.
WisdomReplay class, approval rules, overlay limitsControls, in code. A prompt edit cannot switch it off.
Workflowaccepts with completion evidenceControls. A ticket is done only when its evidence checks out.

Overlays: one business's changes

An overlay is a folder with the same layout as the package. It adds to AGENTS.md, adds or edits skills, picks the model and switches skills and tools on or off. It can switch a tool off but never add one; new tools arrive only in a package release. Office Hum keeps one overlay per agent per business with version history, so upgrading a role never overwrites the business's settings.

The roster is meant to grow into a free catalog covering every department of a company (RASF-3293), with the owner choosing departments, roles and order in RASF-3294. Most roles are meant to come from the Role Factory (RASF-3096): an interview produces a ROLE_SPEC.md, which a generator turns into a role package of exactly this shape. Every catalog role passes the same SDK checks and its evals in a bare Pi Durable harness.

05

Models

Ultramarine by default, other providers by choice

Office Hum registers Paper's Ultramarine 1 Flash as a custom pi-ai provider named paper. It talks to Paper's OpenAI-compatible endpoint, maps thinking levels to Paper's low, high and max, and sends system messages instead of developer messages, which Paper rejects. A guard turns a stream that ends without its closing marker into an error, so a cut-off answer is never taken as complete.

How a conversation gets its model

  1. Role defaultThe manifest's defaultModel. Front Desk: paper / ultramarine-1-flash / max.
  2. Business overlaysettings.json can set defaultProvider, defaultModel and defaultThinkingLevel. Studio's model picker will edit this (planned).
  3. Operator overrideToday the CLI's --provider paper|openai and --model.
  4. Pinned at creationThe choice is stored in the conversation. Resuming later always uses the same provider and model, even if the default has changed.

One decision stays open: bundled usage versus bring-your-own-key billing (RASF-3184). Since pi-ai already supports 44 providers, most of the work is the catalog, testing and billing rather than new adapters.
06

Paper Office documents

Approved design · file store built · tools not built

The design gives every role two ways to work on Word, PowerPoint and Excel files: small typed tools (inspect_document, read_document, edit_document, create_document, preview_document, compare_document, publish_document) and, when a task grants it, run_document_python, a sandboxed Python workspace with the three pinned Paper libraries. Both ship as a portable tool pack. Office Hum supplies the document service behind it; a bare Pi Durable user can supply their own.

Not yet availableNone of the tools below exist on main. What exists is the versioned file store they will write to: immutable versions, operation receipts and replay, stale-edit conflicts, and a publish pointer that only moves if nobody changed the file first.

The life of a document edit

  1. LeaseThe host admits the task, pins every input file to an exact version and hash, and grants a lease: which files, which formats, how long, how much compute. Prompt text, skills and document contents cannot widen it.
  2. Operation IDEach edit gets a stable ID derived from the Pi Durable task and tool call. Reusing it with different intent fails.
  3. Ledger checkIf that operation already committed, the same receipt is returned. No edit runs twice after a crash.
  4. Worker runs in stagingThe Python worker opens only leased versions and writes only to staging. No network, credentials or home folder.
  5. ValidateThe output is reopened with the pinned library and checked: Word structure and redlines, PowerPoint slide renders, Excel formulas and changed cells. Macros, external links and zip bombs are rejected.
  6. CommitAn immutable version and its receipt are stored, then reported back to Pi Durable.
    New fileSaved as a draft automatically.
    Existing business fileBecomes a proposal. A person reviews the exact source, proposal, diff and preview.
  7. PublishOn approval, the published pointer moves only if the source is still current. If someone changed the file meanwhile, it conflicts and needs a fresh review.

Numbers in a document or deck must trace back to spreadsheet or engine results, never to model arithmetic. Paper Rubric may score layout and clarity, but it cannot approve publication.

Delivery order: provider (done), file foundation (SDK done; office store and worker not started), the three format adapters, then review and publish. Each format has its own adapter ticket in M3: Word (RASF-3300), PowerPoint (RASF-3284) and Excel (RASF-3301).

07

Running a team of agents

Front Desk, Sales, Bookkeeper and Office Manager in one office · designed for M2, not built

In a running office, one runtime process hosts one Pi Durable harness and every role in it, all in one SQLite file. Roles never call each other. They post tickets of a declared type to a shared workboard, and a relay delivers each ticket exactly once to the role whose manifest accepts that type. Work nobody accepts goes to the Office Manager's triage, then to a person.

The rules that make it safe

RuleWhy it mattersTicket
Dispatch by type, never by nameYou can replace or add a role without rewiring the othersRASF-3109
Exactly-once deliveryThe relay uses the event ID as the Pi Durable request ID, so a crash cannot deliver a ticket twiceRASF-3067
Provenance and budget are inheritedA child ticket carries where the work came from (customer email is external) and what budget remainsRASF-3066, 3142
Hop limitAfter four hand-offs a ticket goes to a person, so agents cannot loopRASF-3066
Evidence to closeA ticket is done only when its declared evidence checks out, such as an invoice ID in QuickBooksRASF-3230
Install-time checkThe office warns when a role hands off a ticket type nobody acceptsRASF-3236
Shared memory and filesFacts are shared office-wide; a file one agent makes is handed to another by IDRASF-3222, 3193
Askers' permissionsAn agent answering a staff member acts with that person's approval limits, not its ownRASF-3089

Worked example: a prospect becomes an invoice

A prospect emails asking for a meeting on Tuesday and for onboarding pricing. Four agents and the owner handle it. Steps 5 to 12 depend on M2 and on roles that are not built yet; the Sales ticket types come from its draft brief (RASF-3295).

  1. Email arrives at Front DeskA signed Resend webhook creates an inbound receipt and a conversation. In that conversation the Front Desk may only check the schedule and reply. The email text is outside content: it can never grant an approval.
  2. Owner approves the booking and the exact replyBoth are gated. Without an answer nothing is written or sent.
  3. Front Desk hands the sales question offIt does not answer pricing itself. It dispatches a ticket of type lead.qualify, tagged with external provenance, to the board.
  4. Relay delivers it to Sales onceSales accepts the type. If no role accepted it, the Office Manager would triage it.
  5. Sales drafts a proposal deckIts task gets a file lease. The new deck is stored as a draft. Before it reaches the customer, a person reviews it, and the first message to a new address needs approval.
  6. Sales hands off the deposit invoiceinvoice.create goes to the Bookkeeper. It carries the original provenance and the remaining budget.
  7. Bookkeeper asks for approval$6,000 exceeds the large_invoice limit, so the owner decides in the Inbox. QuickBooks totals the invoice; the agent does no arithmetic.
  8. Ticket closes on evidenceThe board closes the ticket only when the invoice ID checks out, then Sales gets the reply.

If the process crashes anywhere in this chain, Pi Durable resumes each conversation from its last commit, the relay does not redeliver tickets already delivered, and the approval decisions already made stay made. The M2 exit test is exactly this: a Front Desk to Bookkeeper invoice.create hand-off that survives a crash with nothing lost or duplicated.

Operating it today

The Front Desk, solo, on your machine

The credential-free demo runs a synthetic model and leaves a resumable state folder. Requires Node 22.19 or later.

npm install
npm run build
node packages/cli/dist/index.js demo --state .officehum/frontdesk-demo --approval allow
node packages/cli/dist/index.js bookings --state .officehum/frontdesk-demo
node packages/cli/dist/index.js resume --state .officehum/frontdesk-demo

Live mode uses Ultramarine by default. Put PAPERINSTRUMENTS_API_KEY in the process environment from your secret store, then run start with a message and a request ID. Add --provider openai to use OpenAI instead.

node packages/cli/dist/index.js start \
  --state .officehum/frontdesk-live \
  --message "Book Demo Guest on 2030-01-15" \
  --request-id booking-1

Commands

CommandWhat it does
demoRuns the synthetic booking with no keys
startSubmits a durable request; asks for allow or deny on gated actions
resumeContinues interrupted work from storage
bookings, contactsRead-only lists; no model is loaded

What is in a state folder

.officehum/frontdesk/ harness/ # Pi Durable JSONL: conversations, tasks, approvals calendar.sqlite # bookings, approvals, operation journal messages.sqlite # console outbox (never contacts a customer) email.sqlite # Resend operations and accepted receipts inbound.sqlite # signed inbound receipts and reply approvals messenger.json # the transport this folder is bound to, forever ownership.sqlite # one live process at a time
CautionBack up the whole folder together. Keep email.sqlite, messenger.json, inbound.sqlite and harness/ side by side; recovery depends on all of them.

Glossary and sources

Terms as this manual uses them
Role
One job (Front Desk, Bookkeeper) packaged as a portable Pi Durable agent.
Overlay
A business's folder of changes layered on a role without editing it.
Manifest
officehum.json: a role's tools, approvals, accepted ticket types and default model.
Ticket type
A named kind of work, such as invoice.create, used to route hand-offs.
Workboard
The shared table of tickets and their append-only events.
Relay
The service that delivers each ticket event to the accepting role exactly once.
Approver
The host-supplied function that asks a person to allow or deny a gated action.
Harness
Pi Durable's runtime over one storage: conversations, tasks and recovery.
Provider
A pi-ai adapter for one model vendor, such as paper or openai.
FileRef
An immutable reference to one exact file version and its hash.
Lease
A task-scoped grant of which files a document operation may read and write.
Receipt
The stored proof that an operation ran, with its inputs, outputs and hashes.
