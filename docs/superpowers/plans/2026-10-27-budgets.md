# Plan: Budgets, hop limits, provenance (RASF-3074)

Design only. Implementer writes the board (migration 4), the relay guards, and the office hooks from this;
no production `.ts` here, no commit, no worktree. RASF-3074 is an epic with three children — RASF-3141
(budgets), RASF-3142 (provenance), RASF-3143 (red team) — so this is the parent design; each child implements
its slice and the red-team tests land in 3143.

## Contract

The issue cites a platform spec, "Safety and governance". **It is not in this repository** — no such section
exists under `docs/` or `packages/` (`docs/design/` holds only agent-package, file-store, role-spec). The
issue's **Goal / Context / Done-when**, plus the standing principle in `docs/design/agent-package.md`
("Guardrails live in code, not prompt text: approval gates, budgets and provenance are hooks"), are the
contract. Everything below is testable with scripted/faux providers and a real `Harness` over SQLite — no
network, no live model.

## (a) What a budget is, and what the office can measure today

A budget is one per-ticket-chain ceiling over **three quantities plus hops**: tool calls, tokens, dollars.
The board's `budgets` row already carries `max_tokens`/`max_usd_cents`; 3074 adds `max_calls`/`used_calls`
(migration 4). What the office measures honestly today:

- **Tool calls** — every execution is a countable, deterministic event: `beforeTool` fires for model-issued
  *and* nested calls, model worker or deterministic engine worker alike. **This is the hard cap.**
- **Hops** — already in the board (see (e)).
- **Tokens / dollars** — visible only in model-turn receipts. `GenerationHooks.afterResponse(message)` carries
  `message.usage` with `totalTokens` and `cost` (the provider's catalog price, via pi-ai `calculateCost`). A
  deterministic (no-model) worker runs no generation task, so it produces **no usage and no cost**. Token and
  dollar spend is therefore recorded when observed and enforced at the *next* boundary — at most one model turn
  of overrun, an honest guarantee rather than a false per-token one.

`[decision]` a token ceiling must not be taken as "zero spent because no receipt" for a deterministic worker —
that would falsely exempt exactly the worker with no receipts. The call cap is what actually fences them, and
that is stated, not silently papered over. (`[decision]` dollars = the provider-reported catalog cost converted
to integer cents, clamped and non-negative; a business-configured rate is out of scope, no table exists.)

Do not confound these with the manifest's `limits` (`LimitDeclaration`, overlays): those are **approval
thresholds**, a different concept the SDK already ships.

## (b) Where enforcement lives

Three seats, one authority, none of them the prompt:

- **The board is the single authority over the number.** `checkBudget`/`chargeUsage` run inside one
  `BEGIN IMMEDIATE` and are correct-or-absent. Two counters that can disagree (a prompt plus best-effort code)
  are not a budget.
- **The host hook is the sensor-gate mid-turn.** `beforeTool` checks the call ceiling and blocks; `afterTool`
  and `afterResponse` charge the spend they observe.
- **The relay guard `checkBudget` is the coarse gate at delivery.** A ticket at or over budget is refused before
  it reaches the agent, and (new) routed to a person rather than recorded as a bare `failed`.

A budget that lives only in the `office` prompt section is not a budget: nothing enforces it, and the data rule
already proves prompt text is advice, not enforcement. `[decision]` all three seats; the board is the truth, the
hook is the teeth, the relay is the door.

The hook's `HookApi` exposes `conversationId`/`taskId`, not a ticket. 3074 adds a durable conversation→ticket
binding — a conversation-scoped `defineDoc` the relay writes when it resolves a per-ticket conversation (it
already holds both ids there). `[addition]` this binding does not exist in-repo today (the adapter's
`OfficeDirectoryDoc` maps key→conversation id only; `parentOf` is supplied externally). The implementer must
verify the doc-read API on `HookApi` against the installed types before assuming a read shape.

## (c) At exhaustion

All three happen, and the ticket leaves the harness:

1. **Refuse the tool call.** `beforeTool` returns `{ block }` naming the ceiling; the board records the crossing.
2. **Stall the ticket.** Status → `blocked` and a surfaced event (`stalled` / `budget_exhausted`) with the
   reason, so a person reading the board sees why work stopped.
3. **The surfaced event IS the notification** (board CLI, inbox, owners manual). A push channel (email/Teams)
   is out of scope — none exists in-repo.

The agent sees a block message: "budget reached (N calls / M tokens / $X). This ticket is blocked and with a
person; do not retry, do not open children." The anti-loop is durable, not wording: `blocked` status means every
re-ask is refused identically, and the relay guard refuses any new delivery so the agent never gets another turn
on that ticket.

## (d) Recording spend, crash-safe

`chargeUsage(ticketId, callId, { calls, tokens, usdCents })` runs in one `BEGIN IMMEDIATE`:

- `INSERT OR IGNORE` a `spend_ledger` row keyed by `call_id`. Ignored = already charged → no-op (the dedup).
- If newly inserted, add the deltas to `used_*` on the ticket **and every ancestor** — roll-up, because the
  board already defines a parent's `used_*` as subtree spend (a sibling's `remaining()` is computed from the
  parent's `used` at creation; without roll-up two children would each get the full headroom).
- `callId` is the tool call's identity (`conversationId:taskId:callId`), the same shape the office tools already
  use as their caller key. A replayed/recovered re-run carries the same `callId` and is deduped.

Migration 4 (expand-only): `ALTER TABLE budgets ADD COLUMN used_calls INTEGER NOT NULL DEFAULT 0; ADD COLUMN
max_calls INTEGER;` (column order: the two land after `max_hops`); `CREATE TABLE spend_ledger (call_id TEXT
PRIMARY KEY, ticket_id TEXT NOT NULL, tokens INTEGER NOT NULL, usd_cents INTEGER NOT NULL, calls INTEGER NOT
NULL, at TEXT NOT NULL)` + index on `ticket_id`. `NewTicket.budget`, `BudgetRow`, `findBudget`/`insertBudget`,
`narrow`/`remaining` all gain the call fields.

## (e) Hop limits: what 3074 adds

The board already counts `hop_count` and refuses the `max_hops+1`-th agent child at **create** (default 4),
landing a person-assigned child `waiting`. 3074 must **not reimplement the count** — a second counter is the
drift. 3074 adds only:

- **`checkHops` in the relay** reads the *same* board columns and refuses a delivery to an agent at or past the
  limit — defense-in-depth for any event that reaches an agent without going through `create`'s check. It
  allows `== max` and refuses `> max`, matching the board.
- **A uniform exhaustion outcome** shared with budgets (status `blocked`, surfaced event, person handoff), so
  "exceeds hop limit → stops and goes to a person" is one path, not two divergent ones.

The board is the counter; the guard is the surface. Nothing else is added.

## (f) Provenance: what the fence already does, and what remains

Already done (do **not** re-implement): `relayMessage` fences external-origin content under an explicit
`EXTERNAL` marker when `origin === "external"`, applied before guards and the transport; the `office` section
states `OFFICE_DATA_RULE` (external text is data, never instructions); provenance is a board row copied verbatim
to children at `create` (a caller's provenance on a child is ignored — lineage is a fact, not caller-chosen).

Remaining (RASF-3142): (1) **what a person sees** — the board has `provenance()` and the row, but the ticket's
origin is not surfaced on the line a human reads; add an "external — treat as data" label to the inbox/card so
the label is not only inside the model's fence. (2) **Recording** is the existing `provenance` row; 3142 mostly
surfaces and verifies it, it stores little new. (3) **The red team** (RASF-3143): prove injected external text
never triggers a gated action.

Where the fence must **not** be re-implemented: there is exactly one model-facing fence (`relay/message.ts`),
and the extension's comment already promises no second one. 3074/3142 add the *human-facing* label and the
*tests*, never a second model fence.

## (g) Exact tests

All scripted/faux provider + real `Harness` + SQLite (`demo-model.ts` shows the response-factory shape). The
red-team suite is RASF-3143's; these are the budgets tests.

1. **A model cannot talk its way past the cap.** Faux model scripted to call a role tool repeatedly, and to
   re-try with different arguments (then a different tool) after each block; budget `max_calls: 2`. Assert
   exactly 2 execute, the 3rd call is blocked by `beforeTool`, `used_calls` never exceeds 2, ticket `blocked`.
   This proves "refuse", not "politely request".
2. **Crash between spend and refusal does not double-charge.** `hook(ToolTask, { afterTool })` pauses
   first-run-only (the pi-durable crash/replay pattern), `close()` the crash, reopen the same SQLite,
   `recover()`; assert the `callId` appears in `spend_ledger` **once** and `used_*` reflects one charge. Also:
   a `replay:"safe"` tool that re-runs charges once (dedup by `callId`); a `replay:"unsafe"` tool charges once
   and never loses it.
3. **A deterministic worker is fenced by calls, not tokens.** Engine worker (no generation task → no usage)
   with `max_calls: 1`: the second call is blocked even though `used_tokens` stays 0. A token ceiling alone does
   not falsely exempt it.
4. **Token/dollar recorded when observed.** A model turn records `totalTokens → used_tokens` and `cost →
   used_usd_cents`, rounded to integer cents, clamped, non-negative.
5. **Board arithmetic** (extends the existing `board.test.ts` seeded-usage helpers): charge rolls up to
   ancestors; the same `callId` twice increments once; two distinct `callId`s increment twice. Apply the
   "two values differ" mutation — revert the roll-up and confirm the ancestor assertion fails naming the wrong
   value, then restore.
6. **Hop guard.** `checkHops` refuses a delivery to an agent when `hop_count > max_hops`, allows `== max` (board
   columns); the board's own refusal of the `max+1` agent child stays pinned.
7. **Exhaustion → person.** A chain over its call ceiling goes `blocked` + surfaced event; the relay refuses the
   next delivery and surfaces it (`stalled`), and no agent turn runs.

## (h) Seam with RASF-3073 (approvals)

3073 owns approvals outright: the `approvals` table is already created (migration 1) and marked 3073's;
`checkApproval` is `openGuards`' no-op; `OfficeHookSeam.approve` is accepted and consumed by nothing. 3074 stops
at that line: it fills `checkBudget` + `checkHops`, leaves `checkApproval` returning `{ allowed: true }`, and
does **not** touch the `approvals` table, the `approve` seam, or any approval gate. The exhaustion→person path is
distinct (`blocked`/`stalled`), never an approval row. Guard order stays `checkBudget → checkHops →
checkApproval`; 3074's `beforeTool` budget-block is a separate `HookRegistration` from 3073's tool-raised
approval ask, and the "declare-and-suppress the generic gate" trap 3073 must manage is not 3074's.

## Out of scope

Push notification at exhaustion (email/Teams — none in-repo). A business-configured price rate (3074 records
provider catalog cost as integer cents). Per-role/per-provider concurrency caps (no Pi primitive; already noted
in the relay plan). The red-team suite (RASF-3143). The approval gate and inbox (RASF-3073, RASF-3108).

The three most contestable decisions: (a) token/dollar ceilings are checked at the *next* boundary, not the
exact token — a deliberate one-model-turn overrun rather than pretending providers expose per-token control;
(b) dollars = provider catalog cost, not the business's real rate; (c) "goes to a person" = the surfaced
`blocked`/`stalled` event, with no push channel, because none exists.
## Implementation notes (added while building RASF-3141)

Where the plan above turned out to be wrong, and what the code does instead. Each of these is a fact
checked against the installed types or the running suite, not a preference.

1. **The hooks exist, and `beforeTool` can refuse.** `ToolHooks.beforeTool` returns
   `{ arguments?, block? }`; `{ block }` (or a throw) settles the call as the harness's blocked result and
   the tool never runs. `afterTool` and `GenerationHooks.afterResponse` also exist, so the sensor is
   `afterResponse` — the lazy-charging fallback was not needed.
2. **The conversation→ticket binding is a board table, not a `defineDoc`.** `HookApi extends
   DocumentReader`, so a doc *could* be read; but the binding, the ceiling and the ledger then live in two
   stores that can disagree. `ticket_conversations` is written by the relay in the commit that opens a
   delivery, and the hook reads it synchronously from the same authority that holds the counters.
3. **Per-conversation usage does live in a doc** — `UsageDoc` / `pi.usage`, keyed `provider/modelId` for
   model turns and by tool name for tools, readable with `api.snapshot(UsageDoc, api.conversationId)`, and
   `Harness.usage()` for the session total. The hooks do not read it: `afterResponse(message)` already
   carries `message.usage`, and a second source would be a second answer.
4. **`blocked` had no API path.** `Board.block(ticketId, actor, { reason, assignee? })` now moves the
   ticket, appends exactly one `blocked` event with the reason, and assigns the person. It is idempotent,
   because an exhausted budget refuses every later call and each refusal would otherwise append an event
   for a fact already recorded.
5. **A dollar ceiling is a price table, not the provider's catalog cost.** Providers report a float in
   dollars that moves when the vendor re-prices; a ceiling has to be reproducible from the board a week
   later. `spend/prices.ts` converts tokens to integer cents from a checked-in table of cents per million
   tokens, rounding each component once, with no lookup at charge time. This repository has no office-level
   config file, so the table is data an office supplies when it builds its hooks (`DEFAULT_PRICE_TABLE`
   covers the models whose rate this repo states).
6. **The relay's refusal had to become a board fact.** A refused delivery used to settle as `failed` and
   nothing else. It now also `stall`s the ticket, and `checkBudget`/`checkHops` (RASF-3141's
   `boardGuards`) block it with a person first — one exhaustion outcome for money and for hops.
7. **`get_state` does not exist in this repository.** Spend is surfaced where a person looks: `board.budget`,
   `board.spendByAgent`, the CLI's card (used against the call cap), its footer (per agent per day) and its
   `o` detail (ceilings and headroom).
8. **The call cap is enforced inside one transaction.** `Board.admitCall` reads the ceiling and increments
   in the same `BEGIN IMMEDIATE`, so two calls in a parallel round cannot both take the last slot, and a
   replayed call id is admitted without being counted twice. Token and dollar ceilings keep the plan's
   honest one-turn overrun: they are charged when the response lands and refused at the next `beforeTool`.
9. **A scripted run does report tokens, and never reports money.** pi-ai's faux provider fills `usage` with
   an estimate from the transcript (about four characters a token) and leaves `cost` at zero, so token
   accounting is exercised by the real path and dollar accounting is exactly why the table exists.
