# Front Desk contact management design

Date: 2026-10-13. Architectural slice; autonomous execution authorized. GPT-6.1 Sol designs/reviews; GPT-5.6 Sol implements. Scoped Linear child RASF-3255 belongs to RASF-3130; the broader parent stays open.

## Intent and boundaries

Operators can discover contacts, approve creation/correction, and explicitly associate an approved appointment with one contact. Contact data survives interruption and is available to future first-contact logic. Preserve existing free-text booking calls, both calendar backends, UTC scheduling policy, model/conversation identity, and portable role packaging. No implicit message parsing, name-based identity inference, contact deletion/archiving, arbitrary notes, outreach, first-contact messaging conditions, Google Contacts/OAuth, dependencies, live customer/API writes, or deployment.

Use a role-owned session-scoped Pi Durable document. A host SQLite contacts table would duplicate storage and break bare-Harness portability; a provider contacts integration adds auth and synchronization unrelated to this slice. Session scope shares one identity across conversations/forks in the same Harness; separate state directories remain separate address books. The document is created lazily on the first successful write; empty reads create nothing. Existing SQLite schema/journal/provider request shapes stay intact.

## Public contract and identity

Export `Contact = {id:string; name:string; email:string|null; phone:string|null; revision:number; bookingIds:string[]}` and `ContactsDoc` from the Front Desk package. Define `ContactsDoc` with kind `frontdesk.contacts`, version 1, scope `session`, and initial `{nextId:1, contacts:[], operations:[], bookingLinks:[]}`. IDs are `contact-<nextId>` allocated/incremented inside the same commit that creates the record. Profile revision starts at 1; profile updates increment it, booking observations do not. `bookingIds` is read-only to tools, unique, and sorted. Persist JSON-safe arrays/plain values only; no prototype-keyed map from user input.

Add replay-safe tools:
- `list_contacts({query?:string})`: return `{contacts:Contact[]}` sorted by name then ID; optional case-insensitive substring search on name/email/phone or exact ID. Empty query means all; bounded query at 254 characters. Always show exact IDs/revisions, including multiple equal-name matches.
- `create_contact({name:string,email?:string,phone?:string})`: unconditional `confirm_contact_creation` approval; return `{contact:Contact,replayed:boolean}`.
- `update_contact({id:string,expectedRevision:number,name?:string,email?:string|null,phone?:string|null})`: unconditional `confirm_contact_update` approval; require at least one supplied profile field, known ID and positive integral revision. Omitted fields remain; null clears email/phone; name cannot clear. Stale revisions reject without mutation. Return the same receipt shape.

Trim names (1–200 characters), IDs and channels; reject control characters in profile fields. Email: 1–254 characters, lowercase, basic `^[^\s@]+@[^\s@]+\.[^\s@]+$` validation. Phone: canonical international `^\+[1-9][0-9]{6,14}$`; do not guess country codes or strip punctuation. Blank channels reject rather than clear. Non-null normalized email/phone must each be unique across contacts; a duplicate create/update rejects with the conflicting ID and no automatic merge. Equal names are allowed. Schemas reject undeclared properties. No arbitrary data fields or authority/trust claims.

## Atomic contact writes and replay

All writes derive the key only from `${api.conversationId}:${api.taskId}:${api.callId}`. Contact operations store `{key,kind:'create'|'update',argsJson,contact}` with canonical normalized arguments and a detached successful profile/booking snapshot. `api.commit(async tx => tx.doc(ContactsDoc), context)` performs receipt lookup, cross-kind/argument binding, duplicate/revision checks, record mutation and receipt insertion atomically. Never retain a mutable document draft outside its callback. Use the invocation cancellation context, not a background context.

Matching receipts return the original snapshot with `replayed:true`, without mutating or revalidating current revision/channels; changed kind/arguments under the same key reject. New failures make no profile/receipt changes. Later corrections cannot be undone by an old retry. Tool text explicitly calls a replay a historical receipt at its saved revision; `list_contacts` supplies current state. Retain receipts without eviction in this initial small address book. SDK durable approval memos continue to govern these tools; denied/missing approvers change nothing.

## Explicit booking association

Retain required `book_appointment({start,customer})`; add optional `contactId`. No contact ID means existing behavior and no implicit contact creation. For a supplied ID, require an existing exact ID and trimmed `customer` equal to the contact's current name before the first calendar effect. Store a first-writer-wins `api.memo('frontdesk.booking-contact', {argsJson,contactId,revision,name}, context)` containing canonical booking arguments and the selected snapshot; validate a prior memo against those arguments. On retries use that pinned name/identity even if the profile changed. No new FrontDeskOptions dependency or Calendar method is needed.

After `calendar.book(start,pinnedName,key)` returns its successful receipt, commit its returned booking ID into the pinned contact's `bookingIds` exactly once. The same commit records `{key,argsJson,contactId,bookingId}` in `bookingLinks`; conflicting replay linkage rejects. A failed/denied booking never creates an observation. No provider contact metadata or changes to `Booking` are required. Renames/channel changes do not rewrite past appointments. Cancellations retain the historical association. Linking is a second durable commit after the calendar effect: interrupted recovery reruns the existing idempotent calendar call then completes the link; do not claim the whole operation succeeded if the link commit fails. Existing superseded/canceled-calendar replay rejection remains authoritative.

## Host compatibility and acceptance

Existing role declaration/overlays expose the new tools with mandatory gates. Extend `openSolo`'s one-time Front Desk tool-selection migration to add contact tools to old explicit selections containing the known five pre-contact tools, while preserving current overlay removals and stored removal masks. Handle original two-tool roots after their existing lifecycle migration. Never reset root/model, pending work, unrelated explicit tool selections, or previously intentional removals. New/default selections follow registry declarations. No new bare-Harness initialization hook is required: session document APIs work directly from role tools.

Add read-only `officehum contacts [--state DIR]`: acquire existing solo ownership, snapshot ContactsDoc and print current IDs/revisions/name/channels (empty address book is successful). Export generic Office helper `readSoloDocument<T extends JsonObject>(directory:string,token:SessionDocToken<T>):Promise<Readonly<T>|undefined>`: under the existing owner guard, open only an existing `<directory>/harness` JSONL store, use public `createSession(storage)` and `session.snapshot(token,context)`, then close/release in finally. Missing harness returns undefined without creating a Harness/root/document. Normal owner-guard files are allowed; no contact/calendar/identity/task/model state is written. No registry, role, Calendar, connector selection, credentials, inference, scheduler, submit/resume or provider/network request is needed; pending submissions remain untouched. This helper retains host ownership without importing Front Desk.

Through actual Harness tools interrupt create/update after document commit before tool settlement, close/reopen/resume original submission, and assert one decision/effect. Exercise contact-linked booking on local and fake Google hosts with interruption between calendar and link commits, one booking/association/approval, pinned profile after rename, and failure/denial without links. Session sharing/fork behavior and old-root/overlay migration need explicit tests. CLI inspection tests pin empty/populated output, active-owner refusal, no pending-work resumption, and Google-bound/no-credentials/no-provider behavior. README examples use ordinary `start --message` plus approval for mutations. Run all repository checks; use only temporary/synthetic state.
