# Front Desk reschedule and cancellation design

Date: 2026-10-13. Architectural slice; autonomous design/implementation is authorized. GPT-6.1 Sol designs/reviews; GPT-5.6 Sol implements. The controller owns commits and scoped Linear issue RASF-3253 under RASF-3130; broader issues stay open.

## Intent and boundaries

An operator can discover actual managed bookings, approve a move or cancellation, and recover interrupted work without duplicate effects or false confirmations. Add the complete workflow to both local and Google hosts. Keep the credential-free booking demo/defaults, portable role boundary, persisted connector identity, and UTC 09:00–12:00 hourly policy. No contacts, outreach, customer sends, auth flows, payment features, live Google acceptance writes, or deployment.

## Portable role contract

Keep `Booking = {readonly id:string; readonly start:string; readonly customer:string}`. Add `Cancellation = {readonly id:string; readonly status:"canceled"; readonly alreadyCanceled:boolean}`. Extend `Calendar` with `listBookings():Promise<Booking[]>`, `reschedule(id:string,start:string,key:string):Promise<Booking>`, and `cancel(id:string,key:string):Promise<Cancellation>`; retain `freeSlots` and `book`. Hosts may retain their existing `bookings()` compatibility alias. Role code must never import Office or provider packages.

Add `list_bookings({})`, `reschedule_appointment({id,start})`, and `cancel_appointment({id})`. Listing returns only active managed appointments sorted by start/id, with structured `{bookings}` and readable IDs/times/customers. Do not guess a booking ID from a name; ask to disambiguate multiple matches. Check availability before suggesting moves; the connector authoritatively checks the target, excluding the booking itself. A same-slot move is permitted.

All tools declare `replay:"safe"`. All three writes require unconditional manifest approval (`confirm_booking`, `confirm_reschedule`, `confirm_cancellation`) through the existing SDK gate; absent/denied approvers produce zero mutations. Each write derives its key exclusively from `${api.conversationId}:${api.taskId}:${api.callId}`. Existing persisted roots must gain the newly registered role tools without replacing their conversation/model or pending calls. Update both role context files: confirmation follows a successful tool receipt only; denied, failed, unknown, canceled, or superseded moves must not be described as completed.

Normalize nonempty bounded IDs/keys and trimmed customers; appointment starts accept the existing exact UTC hourly spelling or its equivalent `.000Z` spelling, canonicalized consistently. Reject other offsets, invalid dates, and out-of-policy slots before effects. Successful move results use the actual returned booking; cancellation reports `Canceled <id>` or `Already canceled <id>` from the persisted receipt. `alreadyCanceled` distinguishes a new no-op on a known cancellation, not a replay of the original successful call.

## Durable operation journal and alternatives

Extend `calendar.sqlite` with `calendar_operations`: globally unique key, operation kind (`book|reschedule|cancel`), canonical argument JSON, optional booking ID, optional pre-effect booking snapshot, and optional successful result JSON. The store exposes `operation(key)`, first-write-wins `bindOperation(key,kind,argsJson)`, `captureBooking(key,booking)`, `completeOperation(key,result)`, and `canceledBooking(id)`; mismatched operation/arguments always reject. Capture/completion persist atomically and cannot overwrite earlier evidence. No credentials enter this journal.

This small host journal is necessary: the Google client has move receipts per event but cancellation accepts unknown 404/410 and does not bind a key across different event IDs or operation kinds. Provider receipts alone cannot enforce the role contract; a new independent Google journal/API would duplicate existing recovery logic. Reuse the same SQLite approval store and add only host-level intent/result evidence.

Failed operations retain their bound arguments but no successful result; an exact retry may proceed. An uncertain provider failure retains pending intent/pre-effect evidence. Do not hold a SQLite transaction over network calls. Google host writes use one rejection-safe promise queue encompassing journal reads, preflight, provider mutation, and result persistence; the provider's existing queue remains in place. Local writes use synchronous `BEGIN IMMEDIATE` transactions. Parallel tool calls cannot bypass intent binding or cancel preflight.

Completed book/move retries verify an active current booking still matches the successful result before returning it, without writing again; missing/canceled or changed targets reject as canceled/superseded. A completed cancel retry returns its original cancellation receipt without another DELETE. Never allow a completed booking key to recreate an event after its provider tombstone disappears. Pending book/move recovery still uses deterministic provider IDs and existing move receipts; a provider deletion purged before any host success receipt remains an external-history limitation.

## Local persistence and migration

Replace the inline `start UNIQUE` constraint with a partial unique index on `start WHERE status='active'`. Keep booking ID, original start/customer/book key, mutable current start, and `status='active'|'canceled'`; retain every canceled row and operation receipt. Cancellation frees the slot; rescheduling preserves ID/customer, frees the old slot, and refuses occupied targets. Unknown IDs reject; known canceled IDs cannot move, and a newly approved cancellation returns `alreadyCanceled:true`. Book/move key replays cannot resurrect or undo a later move. Active listing/freeSlots exclude tombstones.

Detect the legacy schema explicitly. Before rewriting it, make a consistent SQLite snapshot with `VACUUM INTO` at a fresh adjacent backup path (includes WAL contents), copy that snapshot to a disposable fixture, dry-run the identical transactional migration there, and verify integrity plus booking/approval row counts and exact record values. Then `BEGIN IMMEDIATE` on the source, compare its schema and deterministic booking/approval records against the snapshot, and migrate only if unchanged; otherwise roll back and retry snapshot preparation. Refuse malformed/unrecognized schemas. Never overwrite an existing backup.

The actual migration creates the replacement table, copies every booking as active with its original arguments, replaces the old table, installs the partial index/journal, checks counts and record equivalence, and sets schema version in one transaction. Approval rows/request JSON remain byte-for-byte intact. Rollback leaves the old schema/data readable; keep the verified backup and document restore with all owners stopped. Current-schema opens are idempotent. Tests migrate temporary old-schema databases only; do not open real operator state. Extend the host durable-state predicate to count operation rows too, including pending intent, so identity-free journal state cannot bind Google as fresh.

## Google host mapping and truthful cancellation

Use `CalendarClient.listBookings/reschedule/cancel` and derive end from the configured 60-minute duration. For a new cancellation, require a current active managed booking from provider listing, or a durable completed host cancellation for that ID. Unknown/foreign/missing first-time IDs reject with no DELETE and no cancellation receipt. Persist the active booking snapshot under that exact key before DELETE. On exact pending retry, that snapshot authorizes calling the existing idempotent provider cancellation even if GET now returns 404/410; persist success afterward. Completed host cancellations supply the known already-canceled outcome for new keys.

Retain provider ownership, attendee, ETag, conflict, pagination, receipt-cap, and no-send checks. A canceled tombstone with stripped metadata must recover safely: the provider may accept a canceled GET before ownership parsing because no DELETE occurs; a found active foreign event must still reject. Treat any provider/network/malformed result failure as failure, not success. No broad retry loops, key eviction, global provider guarantees, or new REST features are required. External concurrent Google writers remain outside the in-process slot guarantee.

## Acceptance

Pin role approvals/results and backend lifecycle parity; unknown/canceled/conflicting/self-target behavior; cross-operation/cross-booking/changed-argument key reuse; successful and pending replay; old book/move after later move/cancel; tombstone slot reuse; migration preservation/rollback/backup and WAL rows. Use actual durable Harness recovery for move and cancel on both backends, including lost PATCH/DELETE responses and interruption after effect before settlement, with one operator decision per tool call. Exercise competing parallel moves and move/cancel calls through the actual Harness. README examples use ordinary `start` messages plus approval; no mutation CLI bypass. Scripted faux-model tests make the full workflow reviewable, so a new demo mode is unnecessary.
