# Front Desk inbound Resend email and threaded replies

Date: 2026-10-14. Architectural slice, autonomous design/implementation authorized. GPT-6.1 Sol plans/reviews; GPT-5.6 Sol writes product/test code. Scoped issue RASF-3264 belongs to M1 under RASF-3161 and relates to RASF-3160/3261/3257/3130. RASF-3160/3161 remain open until their broader acceptance, including human-verified live send/receive, is completed.

## Intent and selected approach

Run a real local webhook listener through the existing CLI. A signed Resend receiving event becomes a durable inbox receipt, its content is fetched from Resend, and a customer message reaches a stable customer conversation in the existing fsynced Harness session. The customer can obtain availability and receive an operator-enabled threaded reply. First-time customers do not need a pre-existing contact. Contacts/calendar state stays shared with the existing operator root, while customer conversations cannot inspect other customers or perform contact, generic outbound, or appointment mutations.

Three approaches were considered:

1. **Native HTTP + SQLite inbox + existing Harness (selected).** Fits the current local product, needs no hosted deployment, preserves current ownership/recovery, and provides a runnable receive-to-reply entrypoint. A local public HTTPS forwarding arrangement is an operator deployment concern, documented but not provisioned here.
2. **Hosted receiving gateway forwarding to the local office.** Better availability but requires new deployment, remote authorization and queue synchronization. It is an additional product subsystem and is deferred.
3. **Polling Resend's receiving list or vendor beta Inbox/Threads APIs.** Polling avoids a listener but does not fulfill webhook acceptance; vendor-managed threads couple role state/recovery to a new API. Neither is needed for this slice.

Use native `node:http`, crypto, fetch and SQLite. Add one bounded HTML-to-text parser dependency in Office because regex tag removal does not safely decode or suppress HTML content. The role remains provider independent. Do not add an HTTP framework, MIME downloads, hosted gateway, Studio, SMS, webchat, automatic contact creation, customer appointment mutations, DNS/webhook provisioning, credential changes, deployment or live/customer sends during development.

## Provider facts and trust boundaries

Resend's [content documentation](https://resend.com/docs/dashboard/receiving/get-email-content) says `email.received` carries metadata; bodies and headers require the receiving GET. Use `GET https://api.resend.com/emails/receiving/{encoded UUID}?html_format=cid`, not webhook body fields, raw-download URLs or attachment URLs. The [receiving API](https://resend.com/docs/api-reference/emails/retrieve-received-email) supplies `message_id`, `reply_to`, `headers` and server-computed `authentication`. A signed provider event authenticates Resend's delivery, not the email's sender.

Only provider-computed `authentication.dmarc === 'pass'` earns customer submission/reply authority. `null`, `gray`, `unknown`, `processing_failed` and `fail` are retained as blocked receipts. Do not infer authentication from attacker-supplied `Authentication-Results`, SPF/DKIM headers, display names or body claims. DMARC authenticates the sending domain's alignment; it is not an identity check for a person or authorization to change appointments. No security-sensitive customer writes are exposed.

Take the canonical sender mailbox from the fetched provider `from`; accept either a bare ASCII mailbox or one bounded display-name `<mailbox>` form. Canonicalize only the mailbox to lowercase using the strict mailbox grammar already used by the Resend sender adapter. Reject multiple addresses, groups, comments, quoted local parts, CR/LF/C0/C1 controls, malformed angle forms, non-ASCII mailboxes and ambiguous parse results. Display names never become contact names. Preserve case-sensitive Message-ID text, and never use it to route a conversation.

Honor actual reply semantics: absent/empty Reply-To means From; one canonical Reply-To identical to From is eligible. A different or multiple Reply-To, or disagreement between fetched `reply_to` and the case-insensitive Reply-To header, is `reply_to_mismatch` and blocks submission/reply. Do not quietly reply to From when the author specified a different Reply-To. The operator may handle that case through a separately approved generic message; this feature supplies no rebinding command. [RFC 5322](https://www.rfc-editor.org/rfc/rfc5322.html) defines Reply-To and threading behavior.

The bound inbound address must appear in the verified event's `to` and fetched `to`, with exact canonical mailbox equality after safe mailbox parsing. Require matching email UUID, sender, recipient arrays, subject, Message-ID and attachment metadata between event and fetched content. Ignore `received_for` as routing authority because it describes forwarding. CC/BCC may be retained as metadata; neither creates recipients, conversation routing, nor reply-all. Event IDs and provider email IDs are separately deduplicated with full payload binding.

## Explicit configuration and lifecycle

Add `officehum listen --state DIR [--model ID] [--calendar local|google] [--messenger resend] [--port PORT] [--approval allow|deny]` and `officehum inbox --state DIR`. `listen` requires a Resend Messenger binding, existing or fresh. It uses the existing `RESEND_ACCOUNT_ID`, `RESEND_FROM_EMAIL`, `RESEND_SUBJECT`, `RESEND_API_KEY` and explicit `RESEND_INBOUND_EMAIL`. No env presence enables a listener or live transport implicitly. Port defaults to 8787, accepts only integers 1–65535, and binds `127.0.0.1`; the fixed route is `POST /webhooks/resend`. No configurable HTTP/provider origin, arbitrary path, TLS provisioning or shell tunnel execution is added.

Signing keys come from `RESEND_WEBHOOK_SECRET` and optional `RESEND_WEBHOOK_SECRET_PREVIOUS`, read through a callback, never persisted or logged. Accept current/previous keys during rotation without changing the bound nonsecret authority. Require a current valid `whsec_` key before listening. Existing credentials remain environment callbacks. Missing credentials never downgrade transport or verification.

New `inbound.sqlite` metadata binds `{version:1, messengerId, accountId, fromEmail, inboundEmail}` and a random UUID ledger namespace, with exact schema/key/type checks. The fixed subject remains part of the existing Messenger identity but reply subjects are pinned from the inbound receipt. Changing any nonsecret inbound authority rejects; key rotation is allowed within the same declared provider account. Console/legacy console cannot acquire inbound authority. Adding a new inbox to an existing correctly bound Resend state is additive and supported. Existing `messenger.json`, `email.sqlite`, outbound keys/receipts/payloads and legacy Harness records are never rewritten or retargeted. Generic `send_message` retains its original fixed subject and original lack of `reply_to`. Its replies can reach this listener only if its already configured From is the inbound mailbox; do not change old approved operations to make that happen.

The existing `openSolo` ownership guard is acquired before the hosted factory opens any inbox/transport/listener. Bind and revalidate inbox authority under that guard. `contacts`/`bookings` stay unchanged and require no email key. `inbox` is read-only, acquires the same directory ownership, reads an existing inbox without creating one or selecting live models, and prints only email/event IDs, state, reason code, conversation/submission IDs and counts. It prints no raw From, subject, body, headers, attachment filenames or credentials.

Keep ownership until HTTP intake is closed, active HTTP readers and provider fetches are aborted/drained, inbox workers are joined, hosted resources and Harness are closed, and all SQLite connections are closed. SIGINT/EOF preserves admitted receipts, pending tools/approvals and existing decisions. Do not wait for every submission to settle before acknowledging a webhook or stopping. Extend the CLI's active cleanup abstraction to include the listener without bypassing the existing shutdown guarantee. Port-bind/factory/model/config failures close everything already opened and release the guard.

`resume` with an existing inbox opens its trusted reply transport and ingress worker under the same guard, reconciles pending inbox receipts, and resumes all admitted Harness submissions. It does not open a listener. Normal outbound-only states and existing static `openSolo({role})` callers keep their behavior. Neither resume nor listen broadens existing conversation tool selections. An existing inbound conversation's removal masks/declines stay removed/declined.

## Webhook authentication and durable acknowledgement

The listener accepts only the fixed POST endpoint and JSON content type; use static 404/405/415 errors for other paths/methods/types. Bound raw request bytes to 256 KiB and read time to 10 seconds. Limit headers to Node's bounded defaults and require exactly one each of `svix-id`, `svix-timestamp`, `svix-signature` from raw headers, rejecting duplicates. Bound ID to 200 control-free characters, timestamp to safe nonnegative integer seconds and signatures to 4096 characters/at most 16 candidates. No unbounded Buffer collection or response text logging.

Before JSON parsing, writes, provider GET, model work or acknowledgement, verify [Svix's raw-body construction](https://docs.svix.com/receiving/verifying-payloads/how-manual): HMAC-SHA256 over `id + '.' + timestamp + '.' + exact raw bytes`, with strict base64-decoded `whsec_` key bytes. Accept any valid `v1` signature from bounded space-separated candidates using `timingSafeEqual` on exactly 32-byte decoded signatures; test multiple signatures and previous-key rotation. Require timestamp within ±300 seconds of the trusted injected/current clock; neither duplicate events nor saved receipts bypass this freshness check on network intake. Strict base64 round-trip checks prevent permissive Buffer decoding from accepting malformed keys/signatures. Failure returns a static 400/401 and performs zero durable effects/network/model calls.

After verification, decode UTF-8 strictly, parse a bounded JSON object and validate the receiving shape. Require `email.received`, valid timestamps, UUID email ID, safely parsed mailbox fields, bounded subject, Message-ID and at most 50 attachment metadata entries. Unsupported signed event types get 204 and no receiving work. Malformed signed receiving events get 400. Route mismatches are retained blocked, without a provider GET. Valid new intake is committed in SQLite WAL, `synchronous=FULL`, bound parameters and short transactions before responding 202 with a static body. Duplicate identical committed intake returns 200. Persistence failure returns 503 so Resend retries. Intake uses a short synchronous transaction independent of the worker tick and reply-send queues; it cannot wait behind GET, model, approval or POST work. Worker fetch/model/approval latency does not hold the HTTP response open.

`events(event_id UNIQUE, raw_payload BLOB, raw_sha256, canonical_event_json, email_id, verified_at)` binds the event ID to exact verified bytes, not just a hash. Receipts use this explicit storage shape (SQL names are snake_case):

```ts
type InboundReceiptRow = {
  email_id:string; canonical_event_json:string;
  state:'received'|'prepared'|'admitted'|'settled'|'blocked'; reason:string|null;
  fetched_json:string|null; normalized_json:string|null;
  route_snapshot_json:string|null; // authority, canonical sender, optional exact contact ID/revision
  conversation_id:number|null; request_id:string|null; envelope:string|null;
  submission_id:number|null; settlement_json:string|null;
  reply_request_id:string|null; // unique reservation for this receipt; never cleared after uncertainty
};
```

`receipts.email_id` is unique and binds the provider ID to the complete canonical event. Fetch/normalized snapshots and admission envelope have separate immutable columns; route/admission/reservation updates cannot overwrite them. A same ID/different payload rejects 409 before any GET/admission; a new event ID/same email ID/exact canonical event records the additional event but never duplicates customer work. Canonicalization recursively sorts object keys and preserves arrays/values/unknown JSON fields. Do not compare only sender/subject hashes. Local replay of already verified durable rows needs no old signature revalidation; it does not accept new network input.

Schema validation detects malformed metadata, broken state combinations, corrupt JSON, conflicting duplicate identities and impossible receipt/operation fields before work starts. Validate persisted data before model/send effects. On ingest corruption or full-disk errors, fail closed with safe reason text; retain every historical event/operation. This is a new database with no destructive migration. Any future state migration requires a backup/dry run/count verification and is outside this implementation.

## Fetching, normalizing and loop suppression

Use native fetch with a 30-second deadline covering headers plus streamed bounded body, `redirect:'error'`, bearer callback and the fixed encoded UUID GET endpoint with `html_format=cid`. Limit response to 1 MiB, headers total to 64 KiB/200 entries, each header value to 8192 characters, and each text/HTML input to 256 KiB. Validate UUID and metadata cross-binding. Store the first successfully fetched canonical content payload (all body/metadata/header/authentication fields) and normalized message durably before admission; omit `raw` and any expiring download URLs entirely and never dereference them. Subsequent admission/reply recovery uses that immutable snapshot, never refreshed mutable provider fields. Safe errors use status/reason codes only, not provider raw bodies, fetch causes, credentials or email text. Transient GET failures retain `received` with `fetch_failed`; listener retry ticks every 5 seconds, one attempt per receipt per tick, and startup/resume performs one immediate pass. Do not spin or retry indefinitely inside a single processing call.

Use nonblank plain text when present; otherwise parse bounded HTML with `html-to-text` 10.0.1 (Office-only dependency, registry-confirmed, pinned lockfile). Add a compatible published `@types/html-to-text` dev dependency, also pinned, rather than exposing untyped converter calls. Disable word wrapping/href output and skip script, style, iframe, object, embed, form, img, head, blockquote and common Gmail/Yahoo quote containers; cap conversion depth to 40 and children per node to 1000. Reject text/HTML inputs above 256 KiB before conversion, and set converter maxInputLength at least that bound so its input-limit stderr path never occurs. Documented DOM depth/child limits may omit deep/excess output; configure a fixed omission marker and set `truncated:true` when that marker is present (a conservative false positive is acceptable). Do not write a regex HTML structure/depth pre-parser. No script execution, DOM browser, remote assets or attachment download. Preserve original fetched content locally for recovery; model text is at most 16,000 characters with explicit `truncated` metadata. Strip C0/C1 controls except tab/newline, normalize CRLF to LF, and conservatively remove quote lines (`>`), suffix after an exact `-----Original Message-----` line, and suffix after an `On ... wrote:` line only when followed by a quote block. Trim is a convenience, not a security boundary; do not remove arbitrary instructions by regex. If the remaining body is empty, block `empty_body` rather than inventing content. Attachments are inert bounded `{id,filename,contentType,size}` metadata, never read or summarized as their contents.

Require a strict single RFC-style `<local@domain>` Message-ID of at most 998 characters, no whitespace/controls. Parse References into at most 50 such tokens/8192 total characters; reject invalid/interleaved text. A missing/invalid parent Message-ID or invalid thread headers blocks `invalid_thread_headers`. Provider top-level Message-ID and an included header must agree. Unfold only legal CRLF+space/tab in References/header values where relevant; bare CR/LF and other controls are malformed. Never copy arbitrary inbound headers to outbound requests.

Suppress model submission and reply for Auto-Submitted other than absent/`no` (case-insensitive keyword before optional parameters), bulk/list/junk Precedence, List-Id, list-unsubscribe, multipart/report/Delivery-Status notifications, null Return-Path, sender equal to bound From/inbound mailbox, or common no-reply/noreply/mailer-daemon/postmaster local parts. Mark `auto_message`, retaining a receipt but no reply authority. These conservative checks prevent common loops; they do not claim perfect spam or bounce detection. Replies include server-owned `Auto-Submitted: auto-replied` and `X-Auto-Response-Suppress: All`, consistent with [RFC 3834](https://www.rfc-editor.org/rfc/rfc3834.html).

## Stable conversations and the admission crash gap

Keep one Harness/session/calendars/ContactsDoc, not one state directory or Harness per customer. Add Office-owned session `InboundRoutesDoc` and conversation `InboundConversationDoc`, both v1. Routes bind authority + canonical sender to a conversation, optionally an exact existing contact ID/revision. Unrecognized authenticated senders create a route/conversation without creating/updating any Contact record. Reading `tx.doc(ContactsDoc)` may initialize the framework's empty document when absent; that empty document is permitted and is not customer-driven contact creation. Existing exact contact email matches can link metadata. Sender address is the stable fallback identity; names, subject, References and body claims never select a route.

For an existing contact, reuse its already linked route's conversation when a later authenticated current canonical contact email arrives; append that sender alias rather than move old receipts. If an existing sender route is linked to another contact, or resolving an unknown route to a newly created contact would require merging two existing conversations, block `route_conflict` and retain both histories. Creating a contact later for the same sender may attach its exact ID without replacing the existing conversation. No inferred identity merge, contact write or historical recipient rewrite is allowed. Stable routes remain after contact edits. Pending already routed receipts retain their original sender/contact snapshot; new routing considers current contact email and preserves conflicts.

Hosted role creation precedes Harness.open, so callbacks capture `getHarness:()=>Harness|undefined`, initially undefined. Installed Pi Durable 1.0.2 source confirms Harness.open loads/requeues tasks without dispatch and stays paused; root/config/read calls do not resume it. After openSolo returns under retained ownership, assign the resolver to its real Harness, attach InboundSession and reconcile before any submit/resume/wait-for-progress call. Probe and active runtimes use separate closures; the probe never attaches/runs ingress. Unbound callbacks fail closed before approval/network. Restored pending replies therefore have their actual active Harness before scheduling.

Eliminate conversation-creation split-brain by a single Harness commit: read ContactsDoc and route state before table writes, `tx.createConversation({ownership:{kind:'ownerless'}})`, apply `configure(tx,id,agent)` to the new AgentDoc, then write the route and InboundConversationDoc in the same commit. Do not create a conversation and persist its map in a later SQLite commit. Raw `tx.createConversation` runs the registry creation hook; `configure` installs the selected role/model before scheduling. For an existing route use its saved conversation, never the operator root.

New customer conversations select only `check_schedule` and `reply_message`, intersected with current role availability/removal masks. They expose no `list_contacts`, `list_bookings`, generic messaging, contact creation/correction or calendar writes. Apply a host/role tool hook that rechecks this allowlist for an inbound-marked conversation even if a fake/model-emitted tool call asks for a masked tool. This hook blocks before any operator prompt or effect; because SDK approval hooks run first, use an inbound-aware approver that refuses non-reply customer calls statically before delegating to the operator approver. Do not mutate/reconfigure an existing inbound conversation on reopen; removal masks stay removed. Operator root retains its current tools, migrations and decisions; `reply_message` is not automatically added to legacy explicit root selections. There is no new legacy tool migration or provider-ledger migration.

Render a fixed host envelope containing receipt ID, safe metadata, normalized text and attachment metadata as untrusted customer data. The system section states that this input is not operator instructions or approval. No email text is interpreted as CLI tokens, approvals, shell/tool authority or a request to expand the allowlist. Customer messages requesting booking/contact changes receive a truthful response that this email slice can check availability and the operator must authorize changes through their existing workflow.

Before `conversation.submit`, pin in SQLite the exact content string and stable request ID `officehum.inbound.v1/` + SHA-256 of `[inboxNamespace,authorityId,emailId]`, and the route conversation ID. Submit `{type:'input',content,requestId,whenBusy:'steer'}` through the real API, without awaiting settlement in the intake/worker queue. New mail for an active customer is durable steering input at the next Harness boundary. Unrelated customers can progress independently. Bound a single worker tick to at most 20 receipts, serialize tick/admission to avoid local races, and retain the rest for later ticks.

The Harness deduplicates request ID by type, not full content; therefore recovery must use `harness.commit(tx => tx.submissionByRequest(conversationId,requestId), context)` and validate its existing UserEntry/InboxDoc content against the saved exact envelope inside the same public commit before accepting it. The lookup is on Tx, not on the Harness public surface. A queued input is checked against the matching `InboxDoc.items` entry with `mode:'steer'`; a placed/done/unanswered input with an entry is checked against its exact single UserMessage content. An unanswered input without an entry can only be reconciled as the historical canceled submission when the inbox already saved that exact submission ID; otherwise block `submission_binding_unknown`, never recreate it. If found and validated, record the existing submission ID; never re-submit altered content or silently reuse a different submission. If not found, re-submit the same pinned envelope/request ID. Crash after Harness admission but before SQLite update recovers the existing submission. Crash after route commit but before receipt route update finds the atomic route. No submission is lost because the worker was interrupted between databases.

Receipt states are `received` (needs fetch), `prepared` (immutable content awaiting route/admission), `admitted` (submission ID known), `settled` (saved Harness settlement), or `blocked` (static reason). Failed fetch/admission retain the appropriate prior state and safe retry reason. Auth/thread/loop/mismatch blocks are terminal in this slice; no automatic unblocking or rebinding. A watcher may persist settlement after admission without serializing other messages. On restart reconcile admitted/unfinished submissions, then call Harness resume; settled receipts never create another submission.

## Narrow portable reply tool and approvals

Add `reply_message({receiptId:string,text:string})`, with additionalProperties false. The model does not choose contact, recipient, sender, subject, Reply-To, References, transport, provider key or conversation. A portable `ReplyMessenger` structurally defines:

```ts
type ReplyTarget = {
  receiptId:string; conversationId:string; messengerId:string;
  from:string; to:string; replyTo:string; subject:string;
  inReplyTo:string; references:string[];
};
interface ReplyMessenger {
  readonly identity:string;
  prepare(receiptId:string, conversationId:string):Promise<ReplyTarget>;
  send(intent:{target:ReplyTarget;text:string}, options:{requestId:string}):Promise<DeliveryReceipt>;
}
```

Office owns the Resend implementation and immutable receipt lookup. `prepare` requires an eligible immutable receipt, matching current conversation, bound authority and exact canonical sender, with actual Harness admission proof. Normally the inbox has admitted/settled state and saved submission ID. A fast model may call reply_message after Harness admission but before the worker saves that ID; for a prepared receipt with a pinned conversation/request/envelope, `prepare` performs the same public Harness commit using `tx.submissionByRequest` plus exact UserEntry/InboxDoc validation described above and persists the admission ID before permitting a reply. A merely prepared receipt with no valid Harness submission never earns authority. The receipt ID cannot select another customer's conversation even when guessed. Reply target uses saved From recipient (eligible Reply-To equals From), configured sender, configured inbound Reply-To, `Re: ` plus incoming subject unless already prefixed case-insensitive `Re:`, and incoming thread snapshot. Bound subjects to 200 characters including prefix; longer inbound subjects are blocked rather than truncated into a different thread. References follow the parent's References plus parent Message-ID; if absent use single parent In-Reply-To plus parent Message-ID, per RFC 5322. Deduplicate preserving order and reject overflow; do not copy all historical IDs from unrelated topics sharing a customer conversation.

For durable per-call recovery, pin `{key,argsJson,target,text}` in `api.memo('frontdesk.reply-intent',...)`; key is existing `conversationId:taskId:callId`. Full model args and full target are compared on every replay. Text follows the existing exact nonblank 1–4000-character message bound, permitting only tab/CR/LF controls. Maintain separate session `RepliesDoc` successful history, not MessagesDoc: inbound success never grants generic send_message first-contact permission. Historical accepted reply returns its original target/text/receipt forever, even after contact edit, later mail or expiration.

Every reply performs explicit operator approval inside the tool *after* trusted preparation/pinning and *before* send; it is not a generic manifest gate over model-supplied routing. Use the existing `Approver` signature and a fixed `confirm_inbound_reply` approval ID, with request arguments built from pinned server-owned `{receiptId,from,to,replyTo,subject,inReplyTo,references,text,messengerId}`. Persist the decision in `api.memo('frontdesk.reply-approval', {argsJson,approved,by,note})` and compare full intent on replay. No callback means blocked. Malformed callback decisions fail closed; false is durably declined and cannot be replaced by `--approval allow` on resume. The existing calendar DecisionStore only looks up by key and ignores stored request_json, so it cannot provide the required bound reply recovery unchanged. Add a new `reply_approvals` table in inbound.sqlite with unique key, canonical full request_json and approved/by/note fields. Its read and first-write-wins record methods compare the complete canonical trusted request before returning any decision; a same-key changed request fails closed, and an existing false decision cannot be overwritten. This bridges the human-decision-before-tool-memo gap without changing legacy root approval rows/schema/behavior. Share one CLI prompt queue between the root cliApprover and inbound reply approver; serialize every interactive prompt on that shared terminal, not just customer replies, so one answer cannot approve another call. The inbound-aware wrapper still refuses non-reply customer gates before delegating because SDK approvalGate precedes custom safety hooks.

The operator sees bounded safely escaped exact generated reply text, trusted recipient/sender/subject/Reply-To and all thread headers before deciding. Render JSON-string escaped text/metadata or an equivalent terminal-safe display; never display raw terminal controls or email body as instructions. Only the terminal's exact `allow`/`deny`, or the operator's explicit `--approval allow|deny`, supplies a decision. Email words never supply that token. `--approval allow` explicitly authorizes this selected runtime's scoped replies; default interactive review is conservative under the owner's customer-send policy. No customer send happens during implementation/tests. Existing operator-root gates/first-contact behavior stay intact.

## Reply provider ledger and threading recovery

Store reply operations in new `inbound.sqlite`, separate from the schema-strict existing `email.sqlite`, sharing the inbox's persisted random namespace. Preserve the old ledger and global idempotency separation: reply provider key is `officehum.email.reply.v1/` + SHA-256 of `[replyMessengerIdentity,inboxNamespace,requestId]`; old outbound `officehum.email.v1/` keys/namespaces remain unchanged. Fresh inboxes differ; reopen/copied state preserves the namespace. Identity is `officehum.resend.reply.v1:` plus SHA-256 of canonical inbound authority; credential/signing secrets are excluded.

Each reply operation binds request ID, full pinned ReplyTarget/text intent, exact payload, key, firstAttemptAt, lastObservedAt, pending/accepted receipt. Payload is `{from,to:[to],reply_to:inboundEmail,subject,text,headers:{'In-Reply-To':parent,'References':joined,'Auto-Submitted':'auto-replied','X-Auto-Response-Suppress':'All'}}`. Server re-derives and compares full target with its receipt before first attempt; old pending/accepted operations replay their exact saved target regardless of later contact/current mail. A reused request ID with any changed body, subject, destination, headers or identity rejects before credential/network access. A receipt permits at most one distinct reply operation; persist the reservation atomically before any attempt, allowing only the same call/request ID to retry. This limits agent repeated-tool loops and prevents a new call from bypassing an uncertain expired operation.

Use the existing outbound adapter's proven semantics: serialized queue, short SQLite commits outside awaits, native fixed POST `/emails`, 30-second full-response deadline, 64 KiB streamed response limit, static safe errors, credential callback on every actual attempt, redirects rejected and abort/drain on close. Persist the pending row immediately before first POST. Retain its key/payload forever; do not delete failures or reset clocks. Pending attempts require safe finite time, no regression below lastObservedAt and `now < firstAttemptAt + 23 hours`, rechecked after credential waits immediately before dispatch. Accepted local rows replay forever without credentials/POST; uncertain expired rows make zero POSTs and tell the operator to inspect the provider. Resend's [24-hour idempotency retention](https://resend.com/docs/dashboard/emails/idempotency-keys) is not an indefinite retry guarantee. Conflict/HTTP/network/timeout/lost response/commit errors retain pending rows and never establish role success history. No internal new-key retry.

POST's `id` is a Resend email UUID, not the RFC Message-ID. The [sent-email API](https://resend.com/docs/api-reference/emails/retrieve-email) documents a real `message_id`, but fetching/enriching it is explicitly deferred in this slice: no sent-email GET, extra enrichment column or new network/recovery path. Inbound replies already supply their own parent Message-ID/References. Never invent a Message-ID from provider UUID, and never use missing sent-ID enrichment as justification to resend. Parent References supplied by the next inbound mail are the next reply's thread chain.

Crash after provider acceptance before local receipt repeats the same provider key within 23 hours. Crash after adapter acceptance before RepliesDoc commit returns accepted locally and writes role history once. Crash after history before tool settlement returns historical role receipt. In every case exact approval, destination and thread payload remain pinned. A successful Harness text answer is not automatically sent; only successful reply_message acceptance is a send receipt.
