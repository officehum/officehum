# Agent packages: portable Pi Durable roles

Status: accepted (2026-10-07) · Applies to every package under `agents/`

## Decision

Every Office Hum role (Front Desk, Bookkeeper, Office Manager, and every department role after them)
is a **portable Pi Durable agent**: a free, MIT-licensed package, on npm and GitHub, that anyone can
install into **any** Pi Durable 1.6.x harness, with or without Office Hum. Roles are part of Office
Hum's free offering.

A role is mostly **files Pi users already know**: `AGENTS.md`, `APPEND_SYSTEM.md` and `skills/`, plus
an `officehum.json` manifest and a thin Pi Durable entry point for its tools. Roles generated from an
interview and the department roles Office Hum supplies have exactly this shape.

A **host** runs a role: `officehum run` for one role in a terminal, your own Pi Durable harness, or a
platform such as Office Hum's office, which runs several roles together and lets each business
configure them in plain language. A host installs, composes and configures roles; it never modifies a
role package, and a role never depends on it.

```
Hosts: officehum run · your own Pi Durable harness · Office Hum's office
  hand a role its approver, verified sender, clock, app clients and tool packs; apply overlays
        │ installs, composes and configures; never modifies
        ▼
Role packages — portable Pi Durable agents (MIT, on npm and GitHub)
  AGENTS.md · APPEND_SYSTEM.md · skills/ · officehum.json · tools · approval gate · evals
        │ run on
        ▼
Pi Durable 1.6.x — any install
```

## The portability boundary

Enforced by `validatePackage()` and `checkAgent()` in `@officehum/sdk`, and by each role's CI:

1. **Built on Pi Durable.** Tools, hooks and tasks use `defineTool`, `hook` and Pi Durable tasks
   directly. `defineRole` returns plain Pi Durable extensions and agent settings.
2. **Pi Durable, pi-ai and pi-schema are peer dependencies** (range `1.6.x`), never `dependencies`, so a role
   uses the host's single copy.
3. **No platform dependencies.** A role may not depend on `@officehum/cli`, on a host's own packages
   or on anything else that needs the Office. It may depend on `@officehum/sdk` (which depends only on
   Pi Durable, pi-ai, `typebox`, `semver` and `yaml`, with `@earendil-works/pi-mcp` as an optional
   peer that only roles with MCP tools load) and on portable app clients such as
   `@officehum/quickbooks`.
   The SDK's own fixtures in `packages/sdk/fixtures/` are the deliberate exception: they import the
   SDK's **source** by relative path, so the SDK's tests cover source rather than a build. That is
   also why a built CLI cannot load them — see `packages/sdk/fixtures/README.md`, and import the
   package specifier in a role you intend to run.
4. **Safe without Office Hum.** Gated actions are blocked unless the host supplies an approver.
5. **Guardrails live in code, not prompt text.** Approval gates, budgets and provenance are hooks.
   No edit to `AGENTS.md`, `APPEND_SYSTEM.md` or a skill can switch them off.
6. **Proven by a portability test.** A role's evals pass in a bare Pi Durable harness, and again with
   the office extension layered on.

Only *running* agents goes through the harness adapter in `@officehum/runner` (harness, storage,
`submit` with `requestId`, resume). *Building* them does not.

## Four layers

**Context and knowledge inform the agent; wisdom and workflow control it.** Every role, hand-written
or generated by the Role Factory, keeps these four apart:

| Layer | Lives in | Seen | Rule |
| --- | --- | --- | --- |
| Context | `AGENTS.md`, `APPEND_SYSTEM.md` | every turn | Short (under 1,000 words) and structural: who the role is, who it reports to, what it may and may not do. No amounts, percentages or thresholds. |
| Knowledge | `skills/*/SKILL.md`, `skills/*/references/*`, read-only tools | on demand | Descriptions are listed up front; instructions and references load only when read. Facts and tables live in references and the engine's data, not in prose. |
| Wisdom | `replay`, `approvals` with `when`, `noApproval`, overlay limits | enforced by code | Judgment is data and code, never a request in a prompt. Every tool that writes states its approval decision. With no approver, gated actions are refused. |
| Workflow | `accepts` with `done` evidence, operator `commands`, the board | derived from records | Nobody talks a status into existence: a ticket is done only when its declared evidence checks out (an engine check, a record, a file, or a person). |

A `when` condition on an **optional** argument needs `present`: a comparison on a missing argument
fails safe (it holds), so `{ "arg": "discountPercent", "op": "gt", "value": { "limit": "x" } }` alone
gates every call, including the ones that carry no discount. Write the pair instead —

```json
"when": [
  { "arg": "discountPercent", "op": "present" },
  { "arg": "discountPercent", "op": "gt", "value": { "limit": "booking_discount_percent" } }
]
```

— because `when` is a conjunction: absent makes `present` false, so nothing waits. `absent` is the
mirror. Neither takes a value. Absence with no presence operator still holds, so a malformed call
cannot skip a gate by leaving a field out.

A condition can also total an argument instead of comparing it. `field` names a numeric field of each
element of an array argument, and `times` an optional second field to multiply it by:

```json
"when": [
  { "arg": "lines", "op": "gt", "field": "unitPriceCents", "times": "quantity",
    "value": { "limit": "large_invoice" } }
]
```

That is "the lines come to more than the business's limit" with no invoice knowledge in the SDK or in
the office. `op` stays the comparison, so `gt` means the same thing on a total as on one number. The
sum fails safe on every element: a missing, non-numeric or negative field, or a `times` that is not a
positive number, refuses the whole total rather than skipping that element — a skipped element reports
a smaller total than the call's own numbers, which is the one direction that slips a call past a
limit. An empty array is not a total of zero; there is nothing to compare.

An approval can declare its **amount**, the money a call is about, which a remote approver's limit is
checked against. It names an argument, or a field totalled over one, the same way, and is
in cents:

```json
"amount": { "arg": "lines", "field": "unitPriceCents", "times": "quantity" }
```

An approval with a facts reader (below) names a top-level fact instead, so the limit is compared with
the figure the role's own records hold and the person is shown, never a number the model wrote:

```json
"amount": { "fact": "totalCents" }
```

The amount is never taken from `when`, whose numbers can be percentages or counts. An approval with
no amount can be approved only by someone with no approval limit. An approval that moves or commits
money declares its amount: `checkAgent` reports an approval on an unsafe tool whose facts reader states
a `…Cents` field (`declaredFacts(fields, reader)`) and that declares none, and an amount fact its reader
does not state. In the catalog: the Bookkeeper's `any_payment` (`totalCents`), Purchasing's
`po_over_limit` (`totalCents`), Sales' `quote_approval` (`totalCents`), Support's `any_credit`
(`proposedCents`, the desk's proposal; the approver enters `creditCents`), Payroll's `any_pay_run` (`grossCents`), and Inventory's `write_off` (`valueCents`) and
`stock_adjustment` (`varianceCents`). Finance Analysis' `budget_revision` and Payroll's
`pay_adjustment` carry no amount on purpose: the person deciding sets the figure. Both ask for it as
a value (`revisedCents` and `adjustmentCents`, below), so the approver's limit is compared with what
they enter.

An approval can also ask the person approving for a **value**, a figure only a person may set, such as
a credit to give or a budget line's revised amount ([approver-values.md](approver-values.md)). One
kind only: money in whole cents.

```json
"value": { "name": "creditCents", "label": "Credit to give", "min": 1, "maxFact": "lineCents" }
```

`name` is the tool's name for it, a camelCase identifier ending in `Cents`; `label` (at most 80
characters) is what the person is asked for. The bounds are whole cents, fixed (`min`, default 0, and
`max`, optional) or read from a fact of the approval's facts reader (`minFact`, `maxFact`) when the
person is asked; a negative `min` allows a downward correction. `validateManifest` reports a bad
`name`, `min` above `max`, a side bounded both ways, a value on an approval whose tool is
`replay: "safe"`, and two approvals on one tool that both ask for a value (one reserved argument
carries one value). `checkAgent` reports a fact bound the reader does not declare, and a tool whose
parameters lack `officehumApprovedValue`. An approval that asks for a value needs no `amount`; where it
declares one, the amount is the proposal the person sees first. The approver's limit is compared with
the value entered, by its absolute size, so a person with a 500 limit can enter neither 900 nor -900.
How the gate checks the value and hands it to the tool is under the entry point, below.


It guards against three habits:
- pasting policy manuals into `AGENTS.md`
- asking the model in a prompt to "be careful" instead of gating the action
- letting the model declare work finished

Each layer is files or manifest data, never generated code: `@officehum/sdk` enforces wisdom, and
Office Hum enforces workflow: hand-offs are host tools, and a ticket is done only when the office
has run the `done` evidence its type declares (see "Completion evidence" below). The SDK validates
that the evidence is declared, that a tool it names changes nothing, and that it passes only
arguments the tool takes.

`checkFourLayers()` checks a package, and `validatePackage()` runs it:
- **Context:** the word budget, no amounts, percentages or thresholds in context files, and a "You may not" section
- **Knowledge:** references only inside `skills/<id>/references/`, and no `data/`, `work/` or `deliverables/` folder
- **Wisdom:** no generic shell or file tool in the role's list (every writing tool's missing approval decision is a manifest error, from `validateManifest`, so it holds for every role)
- **Workflow:** `done` completion evidence for every accepted ticket type

It is strict (every issue an error) for the free department roles and for Role Factory output.
Elsewhere it gives warnings, except wisdom issues, which are always errors.

Learned memory (below) only ever adds to context and knowledge, through an approval; nothing an
agent learns can change the wisdom layer.

## Package layout

```
@officehum/bookkeeper/
  package.json          peerDependencies: Pi Durable, pi-ai, pi-schema 1.6.x
  officehum.json        Office Hum metadata: tools, approvals, accepts, connectors, skills, evals
  AGENTS.md             the role: who it is, what it does, how it works, house style
  APPEND_SYSTEM.md      rules appended to the end of the system prompt (boundaries)
  role.md               optional: the researched description of the job, every claim cited
  role.sources.json     the sources and the supporting passages behind role.md's claims
  skills/
    collections/
      SKILL.md          Agent Skills format: name, description, instructions
      references/       optional files the skill points to
  src/index.ts          the entry point: tools, approval conditions, defineRole
  evals/                scenarios with expected outcomes
```

The files follow Pi's conventions: `AGENTS.md` and `APPEND_SYSTEM.md` as in Pi's agent directory,
and skills in the [Agent Skills format](https://agentskills.io/specification). Pi Durable itself does
not load these files (Pi's coding agent does), so `defineRole` brings them to Pi Durable:

| File | How the agent sees it |
| --- | --- |
| `AGENTS.md` | The `agents_md` prompt section |
| `skills/*/SKILL.md` | The `skills` section lists each enabled skill's name and description; the agent loads the instructions (and reference files) on demand with the safe `read_skill` tool, as Pi does |
| `APPEND_SYSTEM.md` | The `append_system` section, last of the role's sections |
| Tools | `defineTool` with `replay` written out; a skill's tools live in a `<role>.<skill>` extension selected only while the skill is on |
| Approvals | `approvalGate()` in the role extension; applicability, facts, value bounds, decisions (with any value entered) and declined-handler outcomes kept in separate tool-task memos |

A role gets no shell or file-editing tools. Pi Durable's own `instructions` stay free for the host's
per-conversation notes.

### `role.md` and `role.sources.json`

A departmental role may ship `role.md`: its function, responsibilities and actions, terminology,
workflows, principles, systems, decisions that go to a manager, measures and sources, as `##`
sections in that order. `role.sources.json` holds `sources` (`S1`, `S2`, … with `url`, `title`,
`kind` and `fetchedOn`) and `claims` (`C1`, `C2`, … each with one or more `{ source, passage }`).
`validatePackage` runs `checkRoleMd` when `role.md` exists, offline, and enforces six rules:

1. Every required section is present, in order.
2. Every list item in the eight content sections ends with claim markers such as `[C12]` or `[C3, C4]`.
3. Every marker names a claim in `role.sources.json`.
4. Every claim has at least one source, each source id exists, and each passage is 1 to 400 characters.
5. `Sources` lists exactly the sources in `role.sources.json`, as `- [S1] Title — URL`. Besides those entries it
   may hold only one closing paragraph that starts `Source licences.`; any other line is reported.
6. Every source is cited by at least one claim.

`officehum verify-role ROLE_DIR [--online]` prints the same issues and exits 1 on any error.
`ROLE_DIR` may be a role package or a folder holding only `role.md` and `role.sources.json`, so a
role can be researched before its package exists; `npm run sync-company` skips such a folder until it
has an `officehum.json`.
`--online` also fetches each source and reports every claim whose passage is not in the page text,
ignoring whitespace and case. That check needs the network, so CI does not run it.

## The entry point

```ts
import { fileURLToPath } from "node:url";
import { defineRole, type Approver } from "@officehum/sdk";
import manifest from "../officehum.json" with { type: "json" };

export default function bookkeeper(options: {
  quickbooks: QuickBooks;
  overlays?: string[];
  approve?: Approver;
}) {
  return defineRole({
    packageDir: fileURLToPath(new URL("..", import.meta.url)),
    manifest,
    overlays: options.overlays,
    approve: options.approve,
    tools: [readInvoices(options.quickbooks), createInvoice(options.quickbooks)],
    skillTools: { collections: [sendReminder(options.quickbooks)] },
    when: { large_invoice: (args) => invoiceTotal(args) > 5000 },
  });
}
```

Code conditions may be synchronous one-argument predicates or async predicates that read committed
durable documents through a read-only environment, and may read the role's limits through it too:

```ts
const firstContact: ApprovalCondition = async (args, { read, limits }, context) => {
  const history = await read.snapshot(MessagesDoc, context);
  if (history?.messages.some((message) => sameTarget(message, args))) return false;
  return invoiceTotal(args) > (limits.large_invoice ?? 0);
};
```

The environment exposes only bound `snapshot` and `snapshotAsOf` methods, plus the resolved
`limits`. A role can also read them directly, through `role.current().limits`, when it writes a
condition that needs the business's values. Before approving or bypassing, the gate stores a
canonical tool/arguments applicability memo with the computed boolean. That value is immutable for
the call across recovery, including `false`; existing legacy decision memos remain authoritative.
Predicate errors, rejected promises, and nonboolean results require approval, while active
cancellation propagates. This keeps a previously declined call declined even when another call later
changes the durable history that the predicate reads, and a condition that names a limit it cannot
resolve waits for a person, like any other error.

An approval can also have a **facts reader** (`approvalFacts` in `defineRole`, keyed by approval
id), so the person approves what the role's records hold rather than what the model typed. After
applicability, and only when an approver is configured, the gate calls the reader with the call's
arguments, the hook context, and the call's identity `{ conversationId, taskId }`
(`ApprovalCallIdentity`). The ids come from the Pi Durable hook API, never from tool arguments, so a
reader can scope what it reads to the call's verified sender by handing them to the role's
`SenderResolver`; the gate passes them. It memoises the
result under `officehum.approval-facts.<callId>.<approvalId>` (first write
wins) and asks with it as `ApprovalRequest.facts` (`{ summary, facts }`). A reader that throws blocks
the call with its message and asks nobody. On a yes the gate returns the arguments with
`officehumApprovedFacts` (`APPROVED_FACTS_ARG`) set to the memoised facts; it overwrites that key
whatever the model sent, and strips it from any call it does not grant. The tool reads it with
`approvedFacts(args)`, refuses without it, and its desk refuses when the record no longer equals it
(`sameFacts`). Pi Durable 1.3 validates the arguments a `beforeTool` hook returns against the tool's
parameters again, so a tool whose parameters refuse additional properties declares the key with
`approvedFactsParameter()`. Accounting's `pay_vendor_bill` is the reference: it takes only `{ billId }`.
Purchasing's `request_po_approval` (`{ draftId }`) and `request_new_supplier` (`{ supplierId, reason }`,
the reason being the requester's words, not a desk fact) and Marketing's `request_claim_approval` and
`publish` (`{ draftId }`) follow it. A record the gate reads must exist on the desk, so an eval scenario
whose stubbed write "creates" the record the next gated call names relies on the demonstration desk
holding it: Purchasing's draft PO-1004 and Marketing's held drafts D-104 and D-105 are seeded for
that reason.

For an approval that asks for a **value**, the gate pins the request's bounds after the facts are read:
the fixed bounds and the facts the bounds name, memoised under
`officehum.approval-value.<callId>.<approvalId>` (first write wins), so a record that changes after the
ask does not move them. Bounds it cannot resolve (a fact that is missing or not whole cents, or `min`
above `max`) block the call and ask nobody, as a reader's refusal does. It asks with
`ApprovalRequest.valueRequest` (`{ name, label, min, max? }`) and `amount`, the proposal, where the
approval declares one. `ApprovalDecision.value` carries the cents on a yes. One rule,
`approvalValueProblem(valueRequest, decision)`, says whether an answer is a decision: a yes to an
approval that asks for no value carries none; a yes to one that asks carries a whole number of cents
inside the pinned bounds; a no never carries one. The gate applies it to every answer and the runtime
applies it before it records one. An answer that breaks it is no decision: the gate memoises nothing,
the tool does not run, and the person can be asked again. The rule returns a structured problem: the
approver is told it with the bounds (`valueProblemForApprover`), and the model only that the approval
was not completed (`valueProblemForModel`), never a bound or the entered value. A valid yes is memoised with its value in
the decision memo (first write wins), and the gate returns the arguments with `officehumApprovedValue`
(`APPROVED_VALUE_ARG`) set to `{ name, cents, by }`. As with the facts, the gate strips that key from
the model's arguments before anything reads them, so neither the facts reader, the approver nor the
tool ever sees a model-supplied value. The tool declares the key with `approvedValueParameter()` and
reads it with `approvedValue(args, name)`, which throws when the call carries none or carries another
name; it writes with that value, records `by` beside it, and never falls back to a figure in its other
arguments. A replay or a restart reads the memo and hands the tool the same value, without asking
again.

A call the approval does not apply to (its `when` holds false) gets no facts, so a tool that requires
them refuses every call the condition exempts. Give a facts reader only to an approval that applies to
every call of its tool, or let the tool proceed without facts when no approval applied. `defineRole`
also exposes the readers as `DefinedRole.approvalFacts` (always set, `{}` when the role has none), so a
host's own gate can read the same facts.

An approval can also have a **declined handler** (`approvalDeclined` in `defineRole`, `declined` in
`approvalGate`, keyed by approval id; `ApprovalDeclinedHandler`), for a role whose gated call follows
a write that a no leaves behind. The gate calls it when a person declines a call it asked about, or when
the request expires (the runtime's approver reports an expiry, and a run stopped while it waited, as a
decline). It never runs for a call refused because no approver is configured, a call whose facts
reader refused, or an answer still pending: in those cases nobody was asked, so nothing was put to
anyone and there is nothing to undo. It receives the call's arguments (without `APPROVED_FACTS_ARG`)
and `DeclinedApproval`: the call's `conversationId`, `taskId` and `callId`, the facts the person was
shown, and the decision's note. It never receives model text. It returns a sentence the gate adds to
the decline block (the block's own wording does not change). It runs once per call: its outcome is
memoised under `officehum.approval-declined.<callId>.<approvalId>`, beside the decision. A replay or a
restart repeats that outcome without running the handler again. A crash after the handler's write and
before the memo lands runs it again with the same `callId`, so a handler that writes derives its
request id from the `callId` (`requestId(kind, declined)`) and the desk returns the first write. A
handler that throws leaves the call blocked. The gate memoises the failure as the outcome, and the
block tells the model that recording what follows the decline failed and that the action was still
not done. An abort is rethrown and memoises nothing. Support is the reference: its `any_credit`
handler withdraws the proposal the person saw (reason `declined`), so a declined credit never stays
pending because the model forgot to record it.

**One approval path**. The role's own gate is the only gate: the host hands the role its
approver through `loadRole`, and evals hand it a scripted one. An approval covers one tool call with
exactly the arguments the approver was shown; it cannot be reused, by the same call with other
arguments or by a later call with the same ones. The approver is shown the facts as the summary and
the call's canonical arguments beside them. A host installs no gate of its own.

Installing it on any Pi Durable harness:

```ts
const role = bookkeeper({ quickbooks, overlays: ["./my-bookkeeper"] });
for (const extension of role.extensions) registry.install(extension);
const harness = await Harness.open(storage, { models, registry }, context);
const root = await harness.root(context, { agent: role.agent });
```

**Today comes from the host's clock.** `defineRole({ now })` adds a `today` prompt section, rendered
from that clock at every request: today's date and weekday, the next 14 dates with their weekdays,
and the rule that every date the role states or records comes from that section or a tool result.
The day is the one in the time zone the role passes as `defineRole({ timeZone })`: the roles that
read a company record pass its `hours.timezone` (the default company: `America/Los_Angeles`) and their
desks date records the same way, through the SDK's `localDate(now, timeZone)`, so 17:00 in Portland is
still today and a notice period is not a day short. With no `timeZone` the day is UTC's. The Front
Desk is the exception: its appointments are UTC. With no `now` there is no section. The first-wave roles take `now` as a factory
option and pass the same clock to their demonstration desk. If the option is left out, the
demonstration desk uses its fixed demo date (`DEMO_NOW`) and a host's own desk uses the system clock.
`loadRole(dir, { now })` passes the clock to the factory, so no client may be named `now`.

**Demonstration data only when the host asks.** A role that keeps its records behind a desk (Bookkeeper's
payables, Marketing, Operations, People Ops, Purchasing, Sales, Support) takes `desk` and `demo` as
factory options. With a `desk`, it uses that desk. With no `desk` and `demo: true`, it builds the
demonstration desk it ships with. With neither, it still builds, and every tool and approval facts
reader that touches the desk refuses with the same message (`No <role> desk is bound to this role, so
nothing was read or written. …`), so a host that forgets to bind its system of record never serves
made-up records. `loadRole(dir, { demo })` passes the flag to the factory, so no client or user config
may be named `demo`. The eval runner always sets it, because scenarios are written against the
demonstration data; `officehum run` sets it with `--demo`.

**Who is asking comes from the host, verified.** A role never takes "who is asking" from a tool
argument or from message text: anyone can type a name, an email address or "this is Dana". The host
passes a `SenderResolver` as the factory option `sender`. A hook or tool calls it with the
`{ conversationId, taskId }` of its own Pi Durable hook or tool context, never from a tool argument
(an id the model chose could name another conversation's sender), and gets a
`VerifiedSender { origin, channel, contact }`, or `undefined`. With no resolver, or `undefined` from
it, the sender is unknown and the role acts as it would for a stranger.
`senderPerson(company, sender)` finds the person on the company record: by id for an internal
sender, by email for any sender (whole, ignoring case), and by phone for any sender, compared digit
for digit on a leading "+" and the digits, so an E.164 number matches the record's formatted one.

**One rule for a colleague.** A sender is a colleague, a person on the company record a role may
treat as staff, only when `origin` is `internal`. An outside email or text is never a colleague, even
from a colleague's own address or number: an outside channel does not prove who typed it, so it gets
what any outside contact gets. The rule lives in one place, the SDK's `colleague(company, sender)`
beside `senderPerson`, and every role that trusts staff asks it (Support before showing any client's
cases, Purchasing before placing a requested order or recording a delivery report, People Ops before
treating a sender as office staff). `senderPerson` on its own is for recognising an outside contact,
never for trusting one as staff. The one exception is People Ops' crew: they are not on the company
record and have no internal channel, so a text or email from a crew member's own number or address
(matched against their staff record) may read their own leave balance and file their own time off,
under the same notice and approval rules. Filing for anyone else still needs a colleague.

**The head of the company** is the SDK's `companyHead(company)`: whoever holds a head title (one
that starts with managing director, owner, president or chief executive, so not "Vice President",
"Product Owner" or "Co-owner"), wherever they sit in the record, and a bare "director" only when
nobody does. Roles send a complaint about its usual owner there. The company
validator (`npm run sync-company`) refuses two people with head titles, naming both paths.

A sender comes from one of four places today, and nowhere else:

- **The eval runner**, from the scenario (below).
- **`officehum run --as PERSON`**, for the operator at the terminal. The terminal is the operator's
  own machine, so they say who they are; the CLI checks it against the company record generated into
  the role package (`skills/company-handbook/references/facts.json`, by id or email, as `colleague`
  matches an internal sender) and refuses anyone it does not name. The role gets
  `{ origin: "internal", channel: "terminal", contact: <person id> }` for every call. With no `--as`
  the CLI passes no resolver and the sender is unknown.
- **A host with a board**, which passes `boardSenderResolver(board)`: it reads the provenance row of
  the ticket the conversation is bound to. A child ticket, `agent_dispatch` children included, copies
  its root's row, so delegated work keeps the original asker.
- **A host with signed-in people**, which maps the person it signed in to the company record (by id,
  or email ignoring case) and hands the role `{ origin: "internal", channel: <its channel>, contact:
  <person id> }`; anyone else is unknown.

`loadRole(dir, { sender })` passes the resolver to the factory, so no client or user config may be
named `sender`. The eval runner hands a role the scenario's `from` with its `origin` (external when the
scenario gives none), or unknown when the scenario names nobody. A scenario whose sender is staff says
`"origin": "internal"`.

## Overlays: configuring a role without changing it

An overlay is a directory with the package's layout. Overlays sit on the package the way Pi's project
`.pi/` sits on its agent directory, lowest first:

| File | In the package | In an overlay | When both exist |
| --- | --- | --- | --- |
| `AGENTS.md` | Required: the role | The business's additions | Combined, package first |
| `AGENTS.override.md` | Not allowed | Optional | Replaces every `AGENTS.md` below it |
| `APPEND_SYSTEM.md` | Optional | Optional | The top-most one wins (Pi's rule) |
| `skills/<name>/` | Bundled skills | New or edited skills | Merged by name; the higher layer wins |
| `settings.json` | Not allowed (defaults are in `officehum.json`) | Model; skills, tools and approvals on or off; named limits | Applied in order; later overlays win |
| `templates/<name>.typ` + `templates/<name>.schema.json` | Not read | The business's document templates (Typst source and the JSON Schema of its data) | Merged by name; the higher layer wins |

An overlay's `settings.json` uses Pi's setting names and its `+name` / `-name` edit lists:

```json
{
  "defaultProvider": "paper",
  "defaultModel": "ultramarine-1-flash",
  "defaultThinkingLevel": "high",
  "skills": ["+vip-customers", "-collections"],
  "tools": ["-send_reminder"],
  "approvals": ["-any_payment"],
  "limits": { "large_invoice": 2500 }
}
```

Rules:

- **Defaults, not a floor.** A role's approvals, limits and tools are strong defaults: an overlay may
  lower any of them, including switching an approval off. What counts as lowering a safeguard is
  computed, not judged (`guardChanges` and `loweredGuards`), and inside an office a lowering is
  applied only with the owner's acknowledgement and recorded. See
  [overlay-rules.md](overlay-rules.md).
- Overlays switch declared tools **on or off**, never add one. New tools arrive only in a role or
  tool pack release. Switching on a writing tool the role ships off (through a skill that starts
  off) lowers a safeguard.
- Overlays switch declared approvals **off or back on** (`"-id"`, `"+id"`), never add one or edit its
  conditions. A threshold changes only through a named limit. **An approval on a tool declared
  `outside` (it sends or publishes to people outside the business) stays on**, as does one on the
  channel's send tools (`send_message`, `reply_message`), and a limit such an approval compares with
  may be tightened but not loosened past its default: sending to customers without a person reading
  it first is not available yet. That floor is the controller's default, waiting on the owner's
  decision.
- **A limit lives in one place.** Every amount a business sets is a named limit in a role's
  `officehum.json`, changed here. The company record holds none, and its handbook names a limit
  without a figure (the company check refuses an amount it does not record), so what a role says
  and what it enforces are one number.
- **Limits change; they are never removed.** An overlay sets a value for a limit the package declares.
  It cannot add a limit or remove one: a `null` value is refused, because an approval comparing with
  a missing limit asks every time. To stop asking, switch the approval off, which names what is
  lowered. Raising a ceiling (or lowering a floor) past its default lowers a safeguard; the overlay
  still loads, and an office asks for the owner's acknowledgement before applying it.
- Overlay skills hold **instructions and reference files only** (`.md`, `.txt`, `.csv`, `.json`), never
  scripts. Code arrives only in packages, which agencies and developers can publish.
- A replaced skill keeps its on/off state; a new skill starts on.
- **Templates** are for the document generation pack (`@officehum/tools-docgen`): a business adds a
  template, or replaces a built-in one (`letter`, `memo`, `report`, `quote`, `customer-statement`,
  `meeting-notes`) by using its name. `templates/` holds only `<name>.typ` and `<name>.schema.json`
  pairs, names in kebab-case. `resolveRoleFiles` checks that shape and returns the templates; an
  office also compiles each one with sample data from its schema before accepting the overlay (see
  "Overlays in an office"). A template reads its data with `json("data.json")` and never reaches
  outside its own directory or the network. An overlay template renders PDF only.
- Roles default to Paper's Ultramarine 1 Flash. An overlay can choose another provider's model the
  same way; Office Hum surfaces offer the models in its tested catalog. A model change
  applies to new conversations; a saved conversation keeps the model it started with. The Paper
  provider itself ships as the portable `@officehum/provider-paper` package, so a role's
  default model resolves in a bare Pi Durable install.
- Prompt text and skills update **live**: `role.reload()` re-reads the files and the agent sees the
  change on its next request. A changed model, or skills and tools switched on or off, apply when the
  host next configures the conversation with `role.agent`. A broken edit is reported and the last
  good files stay in use.

Anyone can use overlays: a Pi Durable user writes the files by hand and passes the directory.

## What a host adds

A host may keep one overlay per agent per business with version history, so upgrading a role replaces
only the package and a business's configuration is never overwritten. It may add company context
(house rules every agent reads after its role's own instructions, and department documents as a skill
its agents read on demand), hand-offs between roles, budgets and provenance. None of these is a guard:
they never approve anything, change a limit or add a tool, and a change that lowers a safeguard is
applied only as an explicit, recorded choice ([overlay-rules.md](overlay-rules.md)).

## Engines: a role's deterministic core

Many roles must never produce a number themselves: every figure comes from code. A role does this
with an **engine**, a command-line program (Python, for example) that the role's tools call. The
engine is passed into the role like any app client: the real program in production, `stubEngine` in
tests and evals.

```json
{
  "runtimes": [{ "name": "python3", "version": ">=3.10" }],
  "engine": { "command": ["python3", "engine/engine.py"] },
  "tools": [
    {
      "name": "stock_adjust",
      "replay": "unsafe",
      "description": "Record a stock adjustment.",
      "engine": ["adjust"],
      "parameters": {
        "sku": { "type": "string", "description": "The SKU", "required": true },
        "quantity": { "type": "integer", "description": "Units added or removed", "required": true }
      },
      "guidelines": ["Cite the finding id for every quantity you state."]
    }
  ],
  "approvals": [
    {
      "id": "large_decrease",
      "tool": "stock_adjust",
      "description": "Removing more than 10 units",
      "when": [{ "arg": "quantity", "op": "lt", "value": -10 }]
    }
  ],
  "commands": [{ "name": "stock-board", "description": "Stock on hand", "engine": ["levels"] }]
}
```

- **Runtimes.** The engine's program must be declared in `runtimes`, so every host knows to provide it.
  `checkRuntimes(manifest)` runs each program's `--version` and checks the range before a host loads
  the role.
- **Engine tools are data.** A tool with `engine` has no code: `defineRole({ engine })` builds it from
  its description, guidelines and parameters, with the declared `replay`. A call becomes
  `<command> <subcommand…> --name value…` (underscores become hyphens; a boolean is a bare flag).
- **The contract.** The engine prints one JSON object: `{ "ok": true, "data": …, "findings": [{ "id": … }],
  "caveats": [] }` or `{ "ok": false, "error": "…" }`. Findings carry the ids the role cites. Results
  over 9,000 characters are cut down to their findings.
- **No mutable files in the package.** The engine reads input from `OFFICEHUM_DATA_DIR` and keeps its
  records in `OFFICEHUM_WORK_DIR`, both the host's. Each call carries `OFFICEHUM_IDEMPOTENCY_KEY` (stable
  per tool call), so a repeated write is applied once. `officehum run --data DIR --work DIR` passes
  them for one role; another host passes its own, and the work directory may not be or hold
  the data directory.
- **No secrets.** The engine sees only `PATH`, `HOME`, `LANG` and what the host passes explicitly; model
  keys and connector tokens never reach it.
- **Guardrails from data.** An approval's `when` conditions (`gt`, `gte`, `lt`, `lte`, `eq`, `ne`, `in`
  over the call's arguments) decide which calls wait for a person. A threshold may be a named limit,
  `{ "limit": "large_invoice" }`, that the business sets in its overlay. `field` (with optional
  `times`) compares against the sum of a field across an array argument instead of one argument, so
  "the lines come to more than the limit" is data rather than code. They fail safe: a condition on
  a missing or unreadable argument, on an element the sum cannot read, or on a limit that does not
  resolve, counts as met. A condition written in code takes precedence — and note that a host gate
  that reads the manifest only, never the role's code, treats an approval written as code as
  unconditional.
- **Operator commands** are engine views with no model involved: `runOperatorCommand(manifest, engine,
  name)`. Each host shows them its own way; `officehum run` runs one as `/NAME`.

A role's generator (the Role Factory) writes these fields from the interview, so generated
roles carry almost no code.

### MCP tools

A tool can also come from an MCP server. The manifest declares the server under `mcpServers` (a
`stdio` `command` as an argv array with `env` variable **names**, or an `http` `url` with
`auth.connector`) and the tool with `mcp: { server, tool, idempotencyArg? }`. As for an engine tool,
the manifest states the tool's `description`, `parameters` and `replay`; nothing the server says
about itself reaches the model, and a server tool the manifest does not list is never shown.
`defineRole({ mcp: { tickets: client } })` builds the tools from clients the caller connected — a
role never starts a server — and with no client each call answers "not connected". The server's
output reaches the model inside a fixed frame that marks it as an outside program's data.
`checkMcpDrift` compares a server's `tools/list` with the manifest, and `stubMcp` gives tests and
evals a real pi-mcp client over an in-memory server. `@earendil-works/pi-mcp` is an optional peer
of the SDK, loaded only when an MCP tool is called. The full design, including pinning, drift and
what is not yet contained, is [tool-sources.md](tool-sources.md).

### CLI tools

A tool can also run a service's command-line program, such as `gh`. The manifest declares the
program under `clis` (`command` as an argv array, `env` as variable **names**, and the program in
`runtimes`) and the tool with `cli: { use, args, output: "json" | "text", timeoutSeconds? }`, with
its `description`, `parameters` and `replay` stated as for an engine tool. `{name}` in `args` is a
whole argument that becomes one declared parameter's value, and `{callId}` the call's idempotency
key; `"--repo={repo}"` is refused. `defineRole` builds the tools itself: each call starts the program
once, without a shell, with no standard input, in an empty temporary directory, and with only `PATH`
and the named variables from the host's environment. A string value that starts with `-` is refused,
a non-zero exit is an error result with the exit code and stderr, and the output reaches the model in
the same outside-output frame as an MCP server's. Evals stub a CLI tool by name like any other tool.
See [tool-sources.md](tool-sources.md), section 3.

### Pack tools

Some tools are too heavy for a role package to carry. The data pack (`@officehum/tools-data`:
`data_inspect`, `data_query`, `data_export`, `chart_render`) runs DuckDB, 65 to 100 MB of native
code, and a role must stay light and portable. So a role **declares** such a tool and its office
**supplies** it:

```json
{ "name": "data_query", "replay": "safe", "pack": "data", "writes": true,
  "description": "Answers a question over a spreadsheet with one SQL query; every figure comes from the query.",
  "noApproval": "saves a large result as a new CSV in the office's files; nothing leaves the office" }
```

**A pack tool is declared, reviewed and evaluated like any other.** It states `replay`, a
`description` (what its agent card and a reviewer read; the model reads the pack's own) and, when it
writes, an approval decision. Its `parameters` come from the pack, so the manifest may not state
them, and it comes from its pack alone (no `engine`, `mcp` or `cli`). An approval may name it, and
the approval gate asks about it as about any tool.

**The role package has no code for it and no dependency on the pack.** The host builds the pack and
passes it to the factory as `packs`, a name `loadRole` reserves as it does `company`; the factory
hands it to `defineRole({ packs })`, which offers each tool the manifest declares from a given pack,
and only those. A role built without the pack does not offer them and loads as before, in Office Hum
or a bare harness; `checkAgent` requires a pack's tools only when told the role was given it
(`{ packs: ["data"] }`). The data pack's light entry, `@officehum/tools-data/pack`, defines the tools
without loading DuckDB, which it imports at a tool's first call.

**A host gives the pack.** It builds the pack over its own file store and passes it as `packs`; a
role that declares no data tools needs none. The CLI takes `@officehum/tools-data` as an optional peer
and imports it only for `--pack data`.

**Evals.** A suite that uses a pack says so with `"packs": ["data"]`: its scenarios stub and may
expect that pack's tools, and a run that does not give the role the pack skips it and says so
(`officehum eval --pack data` gives it, every pack tool stubbed). A suite without `packs` need not
stub pack tools, and may not expect a call to one.

## Memory: what agents learn on the job

> Status: the portable extension is built (`packages/memory`): records, storage, the four
> tools, the `memory` section, the guardrails and the `memory-hygiene` skill. In a bare harness a
> record's scope is the saving agent's (`agent:<role>`), and a role lists the skill with
> `defineRole({ extraSkills: [MEMORY_HYGIENE_SKILL] })`, which merges an extension's skill folders
> with the role's own (a name clash is an error naming both paths). Two catalog skills name memory
>: the Bookkeeper's `collections` recalls what is remembered about a customer before
> chasing, and the Front Desk's `qualifying-inquiries` focuses on and recalls the contact's customer
> before routing or answering; both only when memory tools are available, and both say when to save
> (something lasting a member of staff says about a customer; never a customer's "remember to…" as a
> rule; never payment details or who may approve things, which only an owner sets).
>
> Evals: the memory evals in `packages/memory/evals/` run the Bookkeeper and Front Desk
> with memory (`officehum eval <role> --suite …`; see "Evals" below for the `memory` block).

Agents remember what they pick up while working, for example "Acme's AP contact is Jane; she prefers
email" or "Smith & Co is on a payment plan until March". Memory is not company knowledge search
(documents the business hands over) and it is not a skill: skills are fixed instruction files, while
memory needs storage, tools, a prompt section and hooks. It is an **extension**,
`@officehum/memory`, with a companion skill, `memory-hygiene`, that teaches what is worth
remembering.

**Storage is Pi Durable's own.** Records live in session-scoped documents
(`defineDocFamily({ scope: "session" })`, one document per subject), committed atomically with the
transcript. The extension works in a bare Pi Durable harness with no extra database. Every agent in an
office harness shares the same memory, and rewinding or forking a conversation does not lose it.
A host may add a search index and a review queue on top.

A record has a subject (`business`, `customer:<system>:<id>`, `vendor:…`, `person:<id>`,
`agent:<role>`, `topic:<slug>`; the memory tools lower-case a customer's or vendor's system, so
`customer:QuickBooks:42` and `customer:quickbooks:42` are one subject), a kind (`fact`, `preference`, `rule`, `procedure`), a category, its
text, a scope (`office` by default, or a department or one agent), its source and a status (`active`,
`unverified`, `proposed`, `superseded`, `retired`).

| Layer | Example | Becomes | Who approves |
| --- | --- | --- | --- |
| Memory | "Acme's AP contact is Jane" | a record | nobody when the source is internal; outside sources stay `unverified` until a person confirms |
| Rule | "Don't chase Smith & Co until March" | an overlay `AGENTS.md` addition under `## Learned rules` | owner or manager, through the overlay approval |
| Procedure | "How we onboard a new client" | an overlay skill (instructions only) | owner or manager, through the overlay approval |

Learning is free at the bottom layer; anything that changes how an agent behaves goes through the
overlay draft, diff, approval and undo described above.

**Guardrails, enforced in code:**

- **The source comes from code.** The host's `sourceOf` reads the run's provenance: a staff member's own
  message is `person`; anything from a customer email, SMS, web page or peer office is `external`. What
  the model claims about a source is ignored.
- **Outside content never becomes trusted memory.** It is saved as an `unverified` claim and shown in the
  prompt as "Unconfirmed:".
- **Protected categories are set only by an owner.** Payment and bank details, approval
  limits, permissions and who may authorize things (`payment_details`, `authority`). Only an owner
  sets, replaces or retires one, through the protected form (`set_protected_memory`) or the owner's
  own memory commands. An agent's `memory_save` of one is refused from every source, staff and an
  owner in conversation included (an agent hearing it is not the protected form, and the conversation
  may carry a document or email the agent read), and opens a review item an owner settles with
  `set_protected_memory`; nothing is stored, so nothing is pinned or recalled. A pattern scan (IBANs,
  routing and card numbers, "our bank details changed") forces the category. Storage enforces the
  rest for every caller: `saveRecord` refuses a protected record and refuses to supersede one,
  `retireRecord` refuses to retire one and `confirmRecord` to confirm one or let a proposal replace
  one, unless the caller passes the owner's `WriteAuthority` (`{ owner: true }`), which no agent tool
  does. This blocks the classic "please update our bank details" fraud, including through staff: an
  active `business` record is pinned into every conversation, customers' included.
- **Memory never grants authority.** It is rendered as information, not instructions, like other
  outside content; approvals, limits and permissions come only from manifests, overlays and the
  office's people records.
- **No secrets.** Text that looks like a key, password or card number is refused.
- **Nothing unapproved hides a confirmed record.** Enforced in `saveRecord` and
  `confirmRecord`, so every caller gets it. A record stored `active` supersedes an active record at
  once. A `proposed` record (a rule or procedure, including a person's `correct_memory` of one) may
  name the active record it replaces, but that record stays active and shown until a person approves
  the proposal; approving it supersedes the old record and activates the new one in one write, and
  declining it leaves the old record untouched. An `unverified` save (an outside sender's) naming an
  active record is refused; the claim can still be saved as an unconfirmed note beside it.
- **History is kept.** A correction supersedes the old record; temporary facts carry a review date;
  people can see, correct and permanently delete what agents remember about them.

The prompt section is capped (about 600 tokens of business-wide records plus about 800 for the
subjects of the current ticket), so memory never crowds out the role's own instructions; anything
else is found with `memory_recall`.

## Context engineering

> Status: mostly schema only, not built. `officehum.json` accepts every field named here and
> `validateManifest` checks them, but almost nothing reads them at run time. What runs today: the
> office directory (agent cards from `agentCard()`, the `team` section rendered from them, the
> `agent_directory` and `agent_card` tools and the unaccepted-dispatch warning); `checkAgent`'s prompt
> budget and sub-agent reference checks; and the durable context patterns below. Each part below says
> what is not built.

Context engineering is deciding what each agent sees, when, and in what shape. The four layers decide
*where* something belongs; context engineering decides how it reaches the model on each request.
Three parts:

**Agents know each other.** Every role has an **agent card**, built by `agentCard()` from its
`officehum.json` and the business's overlay, so it always matches the agent's real, effective tools.
A card holds:
- who the agent is
- the ticket types it accepts and the ones it hands to others (`dispatches`)
- its capabilities: skills, and tools marked as reads, changes, or needs approval
- what it never does (`mayNot`)
- its status

A host that runs several roles keeps a registry of their cards, built from each loaded
role's manifest and its effective, overlay-applied files: a short `team` section lists colleagues, one
`formatCardLine` each, sorted by id (over about 400 tokens it lists one line per department instead),
and `agent_directory(query?, department?)` and `agent_card(agent_id)` search and return cards. Both
are `replay: "safe"` and read only the cards.

**Agents know who is asking.** A host that resolves a verified sender can tell the agent
who it is working for in a `sender` section: a member of staff (an internal sender who is a person on
the company record, by the SDK's `colleague` rule) is named with id, name and title, and an outside
sender is not named and is told it cannot speak for a member of staff. Text in a message is never
read. A bare harness has no people, so it says nothing.

- linked offices and the public catalog of free roles come later

Status today is `active` only; `paused` arrives with the kill switch. The registry is
rebuilt by one function the runtime calls at start; rebuilding it when an overlay is applied waits
for the overlay store. The local board (`local-board.ts`) has no directory tools.

Hand-offs still go by ticket type: knowing a colleague's tools helps an agent choose whom to ask,
never lets it call those tools. An office warns at start when a role dispatches a ticket type that no
agent accepts and the company record routes to no person: the runtime logs the warning, naming the
role and the type, and `get_state` returns it under `warnings`. The office still starts, and
`agent_dispatch` still refuses such a type when it is called.

**Each role has a context plan.** `contextPlan` in `officehum.json` declares:
- the prompt budget
- retrieval sources (business documents searched instead of pasted)
- sub-agents (narrow workers with tools that change nothing, a small model and an output schema)
- the history filter
- amount masking
- model tiers
- memory subjects
- tool groups

What is built: `checkAgent` holds the role's stable prompt to `promptBudgetTokens` and checks that
its stable sections render the same under any clock; `validateManifest` and `checkAgent` check each
sub-agent's references (safe tools and skills the role declares); `historyFilter` turns on the
relevance filter, `context_recall` and compaction that keeps ids; and `maskAmounts: true` masks
amounts in what `read_skill` returns (see the patterns below). A role with a
`historyFilter` declares `{ "name": "context_recall", "replay": "safe" }` in its tools, and a role
without one may not. A role without a `contextPlan` is unchanged. Nothing runs a sub-agent, searches a
retrieval source, picks a model tier, stores memory or narrows tools by ticket type: `retrieval`,
`subagents`, `modelTiers`, `memorySubjects` and `toolGroups` are validated and then unused.

The Role Factory writes the plan ([role-spec.md](role-spec.md), "The context plan"). The
interview gathers a short context profile; a rule table recommends each technique with a reason that
quotes the profile; a person accepts or declines each one in `ROLE_SPEC.md`; and the accepted ones
become `contextPlan`, with the `context_recall` declaration when the filter is accepted. Only the built
fields can be accepted — `promptBudgetTokens`, `historyFilter` and `maskAmounts` — and the advisor
shows the others with their reason and that they are not available yet. Not built yet: generated
context evals in the package (`evals/context.json`) and a README section listing the plan; today the
Role Factory's own tests run the context eval on a generated package (a long session within its
budget).

**Durable context patterns** (`packages/sdk/src/context/`, on Pi Durable 1.3.0's own hooks, wired by
`defineRole` through `withContextPatterns`). The last column says what exists in the code today:

| Pattern | How | Today |
| --- | --- | --- |
| Storage is not context | The transcript stays complete in storage; each request gets a projection of it | Built: the filter changes one request's messages and never the transcript |
| Stable sections | No timestamps, counters or random values in the role's sections, and `today` after them, so the provider's prompt cache holds. Host sections that change per ticket (memory, focus) belong to the host's extension, selected after the role's | Built: `checkAgent` renders each of the role extension's sections synchronously under two fake clocks and random seeds (the globals are swapped only for that synchronous call, so nothing else in the process sees them) and reports any that differ, or any that renders asynchronously and so cannot be checked ("section `skills` is not stable: it includes the time"), and any stable section placed after `today` |
| Relevance filter | A `beforeRequest` hook. The last `keepRecentRounds` tool rounds stay whole. An older result over `maxToolResultTokens` becomes `[context: <tool> result from <time> omitted (ids: …). Call context_recall("<call id>") to see it again.]`, unless one of its ids is cited by a later user or assistant message or the latest user message (with `keepCitedIds`). Ids are engine finding ids and JSON fields named `id` or ending in `Id`/`_id`; a stub lists five. `context_recall` (replay safe, reads only) returns the result from the transcript | Built. The hook sees model messages, not entries, so a result is named by its tool call id |
| Compaction that keeps ids | A `beforeCompact` hook asks the conversation's model (then the role's default model) for a summary that keeps ids and figures, checks it in code, and appends every id of the range it dropped under "Ids and figures kept", with the figures recorded beside it. An earlier kept list carries into the next compaction. A range with no ids is left to Pi Durable's own summary | Built, on with `historyFilter`. It does not decline compaction: the hook sees only the range, not the whole request; Pi Durable's threshold already measures the filtered request through the provider's usage. The summary's model call is not recorded in `pi.usage` |
| Decisions in memos | Filter decisions, compaction summaries and approval decisions live in task memos, so a restart reuses them | Built. A filter memo lasts one request and its recovery: Pi Durable hands each tool round to a new generation task |
| Amount masking | `read_skill` replaces currency amounts and numbers next to currency words with `[amount: take it from an engine finding]`, so the model takes figures from the engine. Fenced blocks marked `no-mask` stay as written; the skills index is never masked | Built when `maskAmounts` is `true`; not applied by default |
| Sub-agents | Task-owned child conversations with only tools that change nothing, a small model and an output schema; fan-out survives restarts | Not built: declarations are validated, nothing runs them |

### The published schema

`@officehum/sdk` publishes `schema/officehum.schema.json`: an editor-facing JSON Schema (draft
2020-12) generated from the SDK's own `ManifestSchema` when the package builds, so it is the manifest
the code validates, not a second description of it. Point a manifest at it with `$schema`, relative to
the manifest:

- a role package under `agents/`: `"$schema": "../../packages/sdk/schema/officehum.schema.json"`
- an SDK fixture under `packages/sdk/fixtures/<name>/`: `"$schema": "../../schema/officehum.schema.json"`

Every manifest this repository ships declares one, and `packages/sdk/src/schema.test.ts` resolves each
declared path against the file it names — a path that does not work fails the build rather than quietly
giving an editor no completion. The document's `$id` is `urn:officehum:schema:officehum.json:v1`, its
`$schema` is `https://json-schema.org/draft/2020-12/schema`, and it claims `additionalProperties:
false`, so an unknown field is flagged as it is typed.

The schema carries every field in the table above, including these three:

- `limits`: a map of snake_case names to `{ "description", "default" }` — the description up to 300
  characters, the default a number.
- `tools[].noApproval`: optional text up to 300 characters, saying why a writing tool needs none.
- `tools[].writes`: optional boolean; `true` for a tool that changes something yet is safe to re-run.
- `tools[].verifies`: optional `{ "subject": "customer" | "vendor", "system", "field" }`,
  the connected system's id a successful result carries, read from its `details` at `field`
  (dot-separated names, each optionally ending in `[]` for every element of an array, e.g.
  `customers[].id`). A dispatch from the same conversation may name `<subject>:<system>:<id>` in
  `agent_dispatch`'s `about`; see "Memory" above.
- `accepts[].done`: a list of completion evidence, each entry one of the four shapes — `engine`,
  `tool` with `expect: "found"`, `file`, or `person: true`.

It is structural, and only structural. The rules that span fields — unique names, reserved tool names,
the single approval decision every writing tool states, limits and tools that a condition or a `done`
entry refers to — cannot be written in JSON Schema, and stay in `validateManifest`, which reports them
with a path and a plain message. Role packages the Role Factory generates declare no `$schema`: they are
written to whatever directory the generator is given, so no relative path is right for them.


## Completion evidence

Nobody talks a status into existence. When an agent calls `agent_reply` in a host with a board, the
host looks up the `done` entries its manifest declares for the ticket's type and runs every one of them
itself. The model does not run the checks and has no way round them: `agent_reply` is the only tool
that finishes a ticket.

| Entry | How the host checks it | Passes when |
| --- | --- | --- |
| `engine` | Runs the role's engine with the entry's subcommand and arguments | The engine answers `ok` with at least one finding; the finding ids are kept |
| `tool` | Runs the role's tool as a nested call of `agent_reply`, through the role's extension and its hooks | The result's `details.found` is `true`; the details are kept |
| `file` | Looks up the file id the reply attached under that name | The host's file store holds it |
| `person` | Moves the ticket to `awaiting_confirmation` and asks a person | That person confirms it |

Arguments are filled from the ticket: `{ticket.id}`, and `{ticket.data.<path>}` from the data the
ticket was opened with (`agent_dispatch`'s `payload`). A placeholder the ticket cannot fill fails
the check; the host never runs a check half-addressed. A check the host has no means to run
(no engine, no file store) fails too. It is never skipped.

What happens next:

- **Every check passes, no person asked:** the ticket is `done`, and the `completed` event carries
  the evidence.
- **Every check passes, a person is asked:** the ticket waits until the person answers through the
  host. A yes completes the ticket, with their confirmation beside the other evidence.
  A no returns it to the agent with their reason, and counts as a failed attempt.
- **A check fails:** the reply is a tool error naming each failed check and what it found, an
  `evidence_failed` event is recorded, and the ticket stays with the agent.
- **Three failed attempts:** the ticket is `blocked` and assigned to a person. The
  block reason lists the failed checks, what each found, and the role that owned the work.
- **The type declares no `done`:** the ticket completes as before, and the `completed` event carries
  a warning. This keeps a role written before evidence existed working; a catalog role cannot be in
  this state, because the four-layer check requires `done` on every accepted type.

A ticket an agent dispatched with `wait: true` returns to it only once the ticket is `done`, so the
asker waits for the person too.

A host with a board proves this for each type a role accepts with `done` evidence, with a
completion-evidence suite written from the manifest: the model claims the ticket is done before the
work, and the board must refuse it (or hold it for a person) until the evidence exists.

## Validation

Every validator reports all problems at once, each with a path and a plain message:

```
officehum.json › tools[1].replay: must be one of "safe", "unsafe" (got "maybe")
skills/collections/SKILL.md › name: must match its folder name "collections" (got "Collections")
overlay acme/settings.json › tools[0]: "issue_refund" is not a tool of this role; an overlay switches a role's tools on or off, and new tools arrive in a role or tool pack release
overlay acme/settings.json › limits.vat_rate: "vat_rate" is not a limit of this role; a limit is declared in officehum.json
package.json › dependencies.@officehum/cli: is not allowed; a role must run on any Pi Durable install without Office Hum
role › bookkeeper › create_invoice: replay is "safe" in code but "unsafe" in officehum.json
AGENTS.md: warning: is 1200 words; keep AGENTS.md under 1000 words and move the detail into a skill or one of its reference files
```

Each issue carries a **severity**: `error` unless it says `warning:`, and a warning leaves the package valid — it is what the four-layer check reports on a role Office Hum does not own.

- `validateManifest(json)`: the schema plus cross-field rules (duplicates, reserved names, references, the approval decision every writing tool states, and completion evidence).
- `resolveRoleFiles({ packageDir, manifest, overlays })`: the role's files and every overlay. Office
  Hum validates a draft overlay with it before applying an edit.
- `checkFourLayers(packageDir, manifest, { strict })`: the four layers, every issue tagged with its
  layer. Context: the word budget, no numbers in `AGENTS.md` or `APPEND_SYSTEM.md`, a "You may not"
  section. Knowledge: references only inside `skills/<id>/references/`, no host folders. Wisdom: no
  generic shell or file-writing tool in the role's list. Workflow: `done` evidence on every accepted
  ticket type. `strict` makes every issue an error; otherwise context, knowledge and workflow issues
  are warnings and wisdom issues stay errors.
- `validatePackage(dir)`: `package.json` against the portability boundary, `officehum.json`, the
  role's files, `role.md` against `role.sources.json` when present, the four layers (strict for a package under `agents/` or one its `package.json`
  marks `"officehum": { "generated": true }`), and every eval file.
- `checkAgent(bundle, manifest, { strict })`: the entry point's output, with no overlays, against the
  manifest, including that each `done` tool entry passes only arguments its tool takes. It also
  renders the role's stable prompt — its own sections, without any host extension's
  — and estimates its size as characters ÷ 4; over `contextPlan.promptBudgetTokens` (default 4,000) is
  a warning, or an error under `strict` (the `checkFourLayers` rule). A declared sub-agent's `tools`
  must be the role's declared tools that are safe to re-run and do not write, and its `skills` must be declared skills.
- `agentCard(manifest, resolvedRole, { status })`: the role's agent card, for other agents and hosts.
  `formatCardLine(card)` gives a team line of at most 160 characters; `formatCard(card)` gives compact
  Markdown for an `agent_card` tool. A card carries no secrets, overlay settings values, limit amounts
  or the role's prompt text, and a tool an overlay switched off is absent.
- `defineRole` validates the manifest and files itself and throws `RoleFilesError` on problems.

## Evals

Evals check the role's judgment: given a situation, it takes the right actions, avoids the wrong
ones, and asks a person where it must. They run before every role release, on every Pi Durable
upgrade, and as a smoke test after each customer upgrade.

`officehum eval ROLE_DIR --overlay DIR` (repeatable, lowest first) runs the same suites
under a business's overlay directories, as a host loads them: a
house rule as an overlay `AGENTS.md`, a tool switched off, a limit set. The run's first lines say it
is a result under overlays, not on the role's defaults, and name every safeguard the overlays lower
(`loweredGuards`); an overlay that does not load is refused before any trial runs. Without the flag
nothing changes. The "offered" bar is measured on the defaults.

Each file in the `evals` directory holds scenarios:

```json
{
  "scenarios": [
    {
      "id": "invoices-completed-job",
      "description": "A completed job arrives; the bookkeeper creates one invoice",
      "severity": "normal",
      "tags": ["smoke"],
      "input": { "kind": "message", "text": "Job J-12 for Acme is done: 3 hours at $120." },
      "stubs": {
        "read_invoices": { "text": "No open invoices for Acme" },
        "create_invoice": { "text": "Created invoice 1042 for $360" },
        "send_reminder": { "text": "Sent" }
      },
      "approvals": {},
      "expect": {
        "calls": [{ "tool": "create_invoice", "args": { "jobId": "J-12" } }],
        "notCalled": ["send_reminder"],
        "approvalsRequested": [],
        "reply": { "contains": ["1042"] }
      },
      "trials": 3,
      "limits": { "maxTurns": 8 }
    }
  ]
}
```

- `input` is a `message` (text, optional `channel`, `from` and `origin`) or a `ticket` (`type` from
  `accepts`, `payload`, optional `provenance: "external"`). A ticket input needs a host with a board
  to deliver it (office mode), where `agent_reply` and the type's completion evidence apply; the bare
  harness reports it unrun.
  `origin` is `"internal"` or `"external"`: where `from` wrote from. Bare mode defaults it to
  external; a host with a board makes it the ticket's provenance origin. It needs a `from`.
- Every declared tool is stubbed for every scenario (by the scenario or by the file's top-level
  `stubs`, below), so evals never touch a real system. Stubs keep the
  tool's real name, description and parameters, using `wrapTool`. `read_skill` runs for real: it only
  reads the role's own files. A stub is `{ "text", "isError"? }`, or `{ "byArgs": [{ "args", "text",
  "isError"? }], "otherwise"? }`, which answers by the call's arguments: the first entry whose `args`
  match answers, else `otherwise`, else the trial stops. In `byArgs` and in `expect.calls[].args`, an
  argument given as `{ "includes": "…" }` matches a string argument that contains that text. An
  argument given as `{ "some": { … } }` matches an array argument when at least one element has
  those fields, matched the same way (only the fields listed, matchers allowed inside), e.g. a quote
  line `{ "lines": { "some": { "priceBookItemId": "clean-office-visit", "visitsPerWeek": 5 } } }`. So a
  parameter cannot be matched against the literal object `{ "includes": … }`: that object is always
  the matcher. A matcher goes on an argument's value only: `validateSuite` refuses `includes` directly
  under `args`, with its path.
- A file may also declare `stubs` once at the top level, in the same shape. Every scenario gets them
  for each tool it does not stub itself, so read data shared by many scenarios is written once; a
  scenario's stub for a tool replaces the file's stub for that tool whole (the two are never merged
  inside one tool's stub). A scenario then needs no `stubs` of its own. Each declared tool must still
  be stubbed by the scenario or the file, and the file's stubs are checked like a scenario's.
  `validateSuite` folds them in, so every runner sees complete per-scenario stubs:

  ```json
  {
    "stubs": {
      "read_invoices": { "text": "No open invoices for Acme" },
      "create_invoice": { "text": "Created invoice 1042 for $360" },
      "send_reminder": { "text": "Sent" }
    },
    "scenarios": [
      { "id": "invoices-completed-job", "...": "no stubs: all three come from the file" },
      {
        "id": "invoice-refused",
        "...": "only create_invoice differs",
        "stubs": { "create_invoice": { "text": "Refused: job J-12 is not complete", "isError": true } }
      }
    ]
  }
  ```
- `approvals` scripts the person's decision for each approval id: `approve`, `decline` or `pending`.
  `pending` means the request reaches a person who has not answered by the end of the trial: the
  call is blocked as waiting and the run goes on, so a scenario can grade what the role says while
  it waits. An approver gives the same answer as `{ approved: false, pending: true }`; the gate
  records no decision for it, so the same call is asked again later and runs on a yes.
  A scripted `decline` carries no note in either mode, so the model reads only the gate's decline
  block, which says it does not name who declined and why: the person asked may not be the one who
  answered, since another approver can decide and an unanswered request closes as declined.
  An approval that asks the person for a value ([approver-values.md](approver-values.md)) is
  answered yes with the value they enter: `{ "decision": "approve", "valueCents": 2500 }`. Both
  modes hand it to the gate as a person's decision would (`ApprovalDecision.value`; in office mode
  through the store's `decide`), so the gate's own check applies: a value out of the pinned bounds,
  or a plain `"approve"` that carries none, is refused, the tool does not run and the trial fails
  with the refusal's words. `validateSuite` reports, each with its path, a value on a decline, a
  value that is not whole cents, a value for an approval that asks for none, and a plain
  `"approve"` for one that asks for one. Bounds are left to the gate, so a scenario can script a
  value out of them and see it refused.
- `expect.calls` must appear in that order, with other calls allowed in between; `args` matches only
  the fields listed. `args` is what the model emitted, so it never sees the value a person
  approved: the gate adds `officehumApprovedValue` after the model. `approvedValue: { "name":
  "creditCents", "cents": 2500 }` on an expected call matches the value the call ran with instead,
  from the executed ledger (`executedCalls[].approvedValue`); a call that did not run never matches,
  and `validateSuite` checks the name is a value an approval of that tool asks for. A stub can also
  answer by it, `{ "byArgs": [{ "args": { "officehumApprovedValue": { "cents": 2500 } }, … }] }`,
  because a stub runs with the arguments the gate handed the tool. `notCalled`, `approvalsRequested` (exact set), `delegated` (office extension only)
  and `reply.contains` / `reply.containsAny` / `reply.notContains` / `reply.judged` complete the checks. Reply matching
  is case-insensitive, reads typographic quotes and Unicode hyphens and dashes (U+2010 to U+2015, and
  the minus sign U+2212) as their ASCII forms in both the reply and the phrase, so "Q‑3047" with a
  non-breaking hyphen satisfies `Q-3047`, and compares clock readings without a `:00` seconds suffix,
  so `10:00` satisfies an expectation of `10:00:00`. `containsAny` holds groups of alternatives and needs one phrase from
  each group, so a scenario names the fact it requires instead of one sentence that carries it; a
  prohibition is a wrong action in `notCalled`, never a banned word in `notContains`.
- **Reply assertions test behaviour, not vocabulary.** A substring check fails a correct reply that
  words the fact differently, or that contains a forbidden fragment inside a negation ("I have not
  marked it complete"), a condition ("if the exception is approved"), a plan ("once his account is
  disabled") or a quotation of someone else's claim. So:
  - A fact that is an action is asserted on the action: `calls`, `notCalled`, `approvalsRequested`.
  - A fact that must be in the reply is best asserted with the tool receipt's own identifying token
    (an id, an amount, a date as the receipt prints it), which a reply relaying that receipt carries
    whatever its wording. Where a phrasing list must stay in `containsAny`, it is written from what a
    correct reply plainly says ("no free slots", "nothing free", "fully booked", "the diary is
    full"), not from one preferred sentence. `validateSuite` cannot judge a list's width; review does.
  - `validateSuite` refuses a bare `notContains` phrase unless it has a shape an honest reply cannot
    contain: a **first-person claim** (it starts with "I" or "we" as a word: "i've filed the report",
    "i'll ask again"); a **presentation** of content ("here is …", "here are …", "please find
    attached", "your … is/are/has been"); a **decider**, a one- or two-word subject and a decision
    verb ending the phrase ("dana declined", " he said no"), which exists to catch naming who
    decided; or a **receipt token**, text that only the stub of a tool the scenario forbids carries
    (listed in `notCalled`, or gated by an approval it declines or leaves pending) and the input does
    not. Each refused phrase is reported with its path and the advice to prove the behaviour with a
    call-level expectation or rewrite it as a first-person claim.
  - The rare phrase that fits no shape and that no call can prove, such as a name the reply must not
    disclose, is written `{ "phrase": "grace", "reason": "…" }`. The reason is required (at least 20
    characters) so the exception is stated where a reviewer sees it.
  - **What the reply claims or promises** is a judged assertion, because no substring
    can tell "Eileen will be in touch" from "I cannot say she will be in touch":
    `"judged": [{ "claim": "The reply promises or states, even on a condition, that someone at the
    company … will contact … the sender.", "verdict": "absent" }]`. A judge model is asked one
    closed question, with the claim and the reply delimited and the reply marked as untrusted text
    to assess, and must answer `PRESENT` or `ABSENT` (any case, at most a closing full stop). The
    prompt is defined once, in the SDK (`judgePrompt`, versioned by `JUDGE_PROMPT_VERSION`), and
    carries nothing of the scenario but the claim, so the judge never sees what calls it expects.
    The SDK makes no model call: the runner supplies a `ReplyJudge` (`AgentRunner.judge`), and the
    Pi Durable runner's sends the prompt through the trial's provider path (`modelJudge`), at
    temperature 0 except on a reasoning model, whose provider fixes its sampling. `officehum eval`
    judges with the live model the trials run on, or the one `--judge provider/model` names; it
    never falls back to another provider. Each judged assertion is graded like any expectation: a
    verdict other than the expected one fails the trial (for a `critical` scenario, the scenario).
    A judge the provider fails, or an answer that is neither word, is no verdict: the attempt is
    `errored` and retried under the rule below, never passed. Each trial's `trace.judged` records,
    per assertion, the claim, the expected verdict, the outcome, the prompt and its version, the
    judge model, the raw answer and the verdict. A run with no judge (a scripted model, or a runner
    without one) records each judged assertion `skipped` with the reason; the scenario and suite
    reports count them (`skippedAssertions`) and the printed report says so in one line (`Judged
    assertions not graded: …`). The scenario is still graded on its other checks, so **scripted CI
    does not exercise judged assertions**: only a live run does. `validateSuite` reports, each with
    its path, an empty or blank claim, a claim over 300 characters, a claim ending with a question
    mark (a claim is a statement about the reply) and a claim the scenario judges twice; the schema
    refuses a verdict other than `absent` or `present`. A judge is measured before it is trusted:
    `officehum judge-check FIXTURE` runs it over a labelled set of replies for one claim
    (`packages/sdk/src/fixtures/judged-promise-replies.json` for the promise claim,
    `judged-offer-replies.json` beside it for the offer claim) and prints its agreement with the
    labels. Each claim says what counts and what does not, since live judges read an honest reply
    ("nothing has been passed on", "the office can put you through") as the thing it denies.
- `memory` runs the role with memory; without it a scenario runs exactly as before, with
  no memory tool or section. The portable extension is installed beside the role, as a bare Pi
  Durable host would install it; a host may run its own memory instead. A save's source comes from the
  verified sender the runner already hands the role, never from the text: an `internal` `from` is a
  `person`, an external one `external`, and nobody named is the bare harness's local user. The memory tools run
  for real (never stubbed), and `expect.calls` and `notCalled` may name them.

  ```json
  "memory": {
    "seed": [
      { "id": "mem_SEEDACMEAPJANE000000000000", "about": "customer:quickbooks:42", "kind": "fact",
        "category": "contact", "text": "Acme's AP contact is Jane Ortiz." }
    ],
    "expect": {
      "count": 2,
      "records": [{ "id": "mem_SEEDACMEAPJANE000000000000", "status": "superseded" }],
      "absent": [{ "status": "active", "text": { "includes": "Jane" } }],
      "reviews": [{ "type": "protected_category", "claim": { "category": "payment_details" } }],
      "prompted": ["Jane Ortiz"],
      "unread": ["level 2"]
    }
  }
  ```

  `seed` writes records straight into storage before the turn, as earlier work (or someone with
  access to the store) would have left them: they never pass `memory_save` or its guards. Each has an
  `id` (`mem_` and 26 capital letters or digits), `about`, `kind`, `category` and `text`, and may set
  `status` (default `active`), `reviewAt` and `source` (default a person, `seed`); the runner sets
  the scope where the agent reads it, the author and the date. `expect` is checked when the trial
  ends: `count` stored records (seeded and superseded included); each `records` matcher matches a
  stored record and no `absent` matcher matches one (partial matches with the `expect.calls[].args`
  rules, so `{ "includes": … }` works on text); each `reviews` matcher matches an item of the office's
  review queue (office mode only: a bare harness has none, so the check fails there); each `prompted`
  phrase is in a prompt the model was given (the `memory` section), and no `unread` phrase is in
  anything the model read, prompt or tool result. `prompted` and `unread` must quote a seeded record's
  text that neither the input nor a stub carries, so a match proves memory carried it.
  `validateSuite` reports every problem with its path. The trace carries `memory` (every stored
  record, and in office mode the review queue) and `prompts` (each system message as rendered with its
  sections; `received` includes them too).
- **Office-only, bare-only and scripted-only suites.** A file may declare `"mode": "office"` at the
  top: only a host's office-mode run runs it, and a bare run skips its scenarios and the report says
  so (`Skipped, runs only in office mode: …`). `validatePackage` keeps such a file in
  `RolePackage.officeSuites`, apart from `suites`, so a bare caller never meets it. A file may instead
  declare `"mode": "bare"`, for a scenario whose right answer depends on there being no host: only a
  bare run runs it, and an office-mode run skips it and says so. The Bookkeeper's refund, repayment,
  bank-detail change and major unmatched item hand-offs are written this way in `evals/bare.json`:
  with no hand-off tool, the reply says nothing was passed on and how to reach the person who
  decides, and never offers to pass it on. A file may also declare `"model": "scripted"`: its model
  is scripted to misbehave (to claim a ticket is done before the work), which a live model cannot be
  told to do, so a live run skips it and says so. `runEvals` takes the run's `mode` (`bare` by
  default) and `model` (`live` by default, so a caller that does not say never runs a scripted-only
  scenario on a live model). The fields that need a host's board (`confirmation`, `expect.ticket`,
  `expect.dispatched`, `expect.notDispatched`, and the host's communication tools in `expect.calls`)
  are allowed only in an office-mode file; `validateSuite` reports each, with its path, in any other.
- `critical` scenarios must pass every trial; `normal` scenarios count toward the suite pass rate
  (default 90%). `trials` defaults to 3. Checks are fixed rules, except a judged reply assertion,
  which is one closed question with two allowed answers and grades like any other check; there are
  no rubric scores.
- A trial ends `passed`, `failed` (the run finished, or the runner stopped it, and an expectation was
  not met) or `errored` (the model provider ended the run: an interrupted stream, a rate limit, a
  timeout, a server error). The Pi Durable runner recognises a provider failure by how Pi Durable
  settled the run (`unanswered` with reason `model_error`), never by the error's wording, and marks
  the trace `errorSource: "provider"`; a run that settled normally with no tool call is still the
  empty-ledger failure. A scripted model's `model_error` is its script running out, so it stays a
  failure. An errored trial is run again on the same runner, so the same provider and model, up to
  `retries` times (default 2), and so is one whose judge failed or gave no verdict; each errored
  attempt is kept in the trial's `erroredAttempts`, and the
  attempt that finishes is graded. A trial still errored is not graded and counts neither way: pass
  rates and the critical rule use graded trials only. A scenario or suite with no graded failure but
  an errored trial is `incomplete`, never passed, and the run should be repeated. Each scenario
  report carries `outcome`, `passedTrials`, `failedTrials`, `erroredTrials` and `retries`; the suite
  report carries `outcome` and `erroredTrials`.
- A trial whose model reply ended at the run's output cap (stop reason `length`) is
  `errored` the same way, with `errorSource: "output-limit"` and an error that names the cap: what the
  agent would have said or called is unknown, and a tool call cut off mid-arguments never ran, so
  the trial is retried and never graded passed or failed. A judge answer cut off at the cap is no
  verdict. The fix is a higher `--max-output-tokens`, not a scenario change.
- Trial counts: `trials` (`--trials N`) sets every scenario's count; `normalTrials`
  (`--normal-trials N`) sets the normal scenarios' instead, so a run can spend fewer trials on them
  than on critical ones. Each scenario line of the report says how many trials it ran
  (`pass  id (normal, 2/2 trials)`), and the pass rate is computed on the trials actually run.

### What a run costs, and how to read the usage line

Every trial's trace carries `usage`: what the trial's own model requests spent, summed from Pi
Durable's per-conversation ledger (`pi.usage`) of the trial's office, so failed attempts and
compaction count too. Each judged record carries the judge call's `usage`. The trial report's
`usage` adds every attempt (errored ones were paid for) and its judge calls; the scenario and suite
reports sum their trials'. Each usage is plain numbers: `input` (uncached input tokens),
`cacheRead` (input read from the provider's prompt cache), `cacheWrite`, `output` (reasoning
included), `reasoning`, and `cost`, the provider's estimate in US dollars from the model's price
table. A live `officehum eval` run ends with one line:

```
Model usage: 1,234,567 input tokens (950,000 cached), 81,000 output tokens (60,000 reasoning); estimated cost $0.1117
```

The input count includes the cached tokens; the bracketed figure is how many of them were billed
at the cached rate. On `paper/ultramarine-1-flash` input costs $0.15 per million tokens, cached
input $0.03 and output, reasoning included, $0.50. About three quarters of a role's input is its
system prompt and tool definitions, identical on every request of a conversation, so a low cached
share means the cache was not reused (the provider's caching is best effort). A scripted run prints
no usage line: its tokens are pi-ai's estimates and it costs nothing; `--report` still carries them.

Two things keep a run cheap. The Paper provider sends Paper's sticky-session header, `x-session-id`,
set to Pi Durable's per-conversation id, on every request, so each trial's repeated prompt is likelier
to be read from the cache. And `officehum eval` caps every request's output, the judge's included,
at `--max-output-tokens N` (default 8,192, the value Paper's examples use at `max` reasoning;
replies stay under 1,000 tokens and reasoning shares the cap). Paper reserves balance for each
request's largest possible cost before it runs, so the cap reserves a quarter of what the model's
32,768-token limit would, and a small prepaid balance is not refused long before it is spent. The cap
is an eval runner option (`maxOutputTokens`); production requests keep the model's own limit.

### How many trials: what a live pass does and does not show

Three trials is a smoke test, not a measurement. A scenario the model misses one time in twenty
passes three of three about 86% of the time, so one three-trial pass cannot show that a role meets
"every critical scenario passes every trial". Measured on `paper/ultramarine-1-flash` on 2026-11-23:
three critical scenarios that had each passed a three-trial run came in at 18 or 19 of
20, and two that had each missed once in a three-trial run then passed every trial of 20.

So a live result is read at two levels:

- **Per change (three trials).** A change a role's model can see gets a live run of that role in
  both modes at three trials. A critical scenario below three of three does not fail the change by
  that fact: it is run again alone at 20 trials with `officehum eval --scenario ID --trials 20`, in
  the mode it missed. Every run made is recorded in the pull request, never only the last one.
  A run may give normal scenarios fewer trials (`--trials 3 --normal-trials 1`) to cut its cost;
  critical scenarios keep `--trials`.
- **To offer a role (20 trials).** A role is offered when each of its critical scenarios has passed
  20 of 20 graded trials in each mode on the model it ships with. A scenario at 19 of 20 or below is
  fixed (a code guard where one fits, a scenario fix where it asserts more than the role's rule, a
  wording change only where neither fits) or its rate and the reason it is accepted are recorded on
  the role's issue. A run with errored trials is incomplete and is repeated; it is never counted.

A miss that a gated action could turn into harm is never accepted at any rate: the guarantee there
is the gate, which is code, and a test that removes the gate's guard proves it.

The SDK owns the format, its validation, the grading and the report. Running a scenario needs a
harness, so it goes through an `AgentRunner`: the SDK's tests use a scripted runner, and
`@officehum/runner` supplies the Pi Durable runner (a bare harness) and a scripted model provider for
deterministic CI.

## Not covered by this design

- Running agents on Pi Durable, solo mode, crash and resume.
- What a host adds: board tools, hand-offs, its own interface and distribution.
- Approval UI and channel caps; the QuickBooks client.
