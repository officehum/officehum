# Agent packages: portable Pi Durable roles

Status: accepted (2026-10-07) · Issue: RASF-3064 · Applies to every package under `agents/`

## Decision

Every Office Hum role (Front Desk, Bookkeeper, Office Manager, and every department role after them)
is a **portable Pi Durable agent**: a free, MIT-licensed package, on npm and GitHub, that anyone can
install into **any** Pi Durable 1.3.x harness, with or without Office Hum. Roles are part of Office
Hum's free offering.

A role is mostly **files Pi users already know**: `AGENTS.md`, `APPEND_SYSTEM.md` and `skills/`, plus
an `officehum.json` manifest and a thin Pi Durable entry point for its tools. Roles generated from an
interview and the department roles Office Hum supplies have exactly this shape.

Office Hum, the platform, is the **coordination, orchestration and configuration layer** on top of
those roles. It runs them together (workboard, relay, workflows, gateways) and lets each business
configure them in plain language, without ever modifying a role package. A role never depends on it.

```
Office Hum — coordination, orchestration, configuration
  workboard · relay · workflow engine · channel and connector gateways · Studio
  "office" extension: board tools, delegate, team section, approval/budget/provenance hooks
  per-customer overlays: AGENTS.md, APPEND_SYSTEM.md, skills, settings (edited in Studio)
        │ installs, composes and configures; never modifies
        ▼
Role packages — portable Pi Durable agents (MIT, on npm and GitHub)
  AGENTS.md · APPEND_SYSTEM.md · skills/ · officehum.json · tools · approval gate · evals
        │ run on
        ▼
Pi Durable 1.3.x — any install
```

## The portability boundary

Enforced by `validatePackage()` and `checkAgent()` in `@officehum/sdk`, and by each role's CI:

1. **Built on Pi Durable.** Tools, hooks and tasks use `defineTool`, `hook` and Pi Durable tasks
   directly. `defineRole` returns plain Pi Durable extensions and agent settings.
2. **Pi Durable and pi-ai are peer dependencies** (range `1.3.x`), never `dependencies`, so a role
   uses the host's single copy.
3. **No platform dependencies.** A role may not depend on `@officehum/office`, `@officehum/cli` or
   anything else that needs the Office. It may depend on `@officehum/sdk` (which depends only on
   Pi Durable, pi-ai, `typebox`, `semver` and `yaml`) and on portable app clients such as
   `@officehum/quickbooks`.
   The SDK's own fixtures in `packages/sdk/fixtures/` are the deliberate exception: they import the
   SDK's **source** by relative path, so the SDK's tests cover source rather than a build. That is
   also why a built CLI cannot load them — see `packages/sdk/fixtures/README.md`, and import the
   package specifier in a role you intend to run.
4. **Safe without Office Hum.** Gated actions are blocked unless the host supplies an approver.
5. **Guardrails live in code, not prompt text.** Approval gates, budgets and provenance are hooks.
   No edit to `AGENTS.md`, `APPEND_SYSTEM.md` or a skill can switch them off.
6. **Proven by a portability test.** A role's evals pass in a bare Pi Durable harness, and again with
   the office extension layered on.

Only *running* agents goes through the adapter in `@officehum/office` (harness, storage, `submit`
with `requestId`, resume, relay). *Building* them does not.

## Four layers

**Context and knowledge inform the agent; wisdom and workflow control it.** Every role, hand-written
or generated by the Role Factory, keeps these four apart:

| Layer | Lives in | Seen | Rule |
| --- | --- | --- | --- |
| Context | `AGENTS.md`, `APPEND_SYSTEM.md` | every turn | Short (under 1,000 words) and structural: who the role is, who it reports to, what it may and may not do. No amounts, percentages or thresholds. |
| Knowledge | `skills/*/SKILL.md`, `skills/*/references/*`, read-only tools | on demand | Descriptions are listed up front; instructions and references load only when read. Facts and tables live in references and the engine's data, not in prose. |
| Wisdom | `replay`, `approvals` with `when`, `noApproval`, overlay limits | enforced by code | Judgment is data and code, never a request in a prompt. Every tool that writes states its approval decision. With no approver, gated actions are refused. |
| Workflow | `accepts` with `done` evidence, operator `commands`, the board | derived from records | Nobody talks a status into existence: a ticket is done only when its declared evidence checks out (an engine check, a record, a file, or a person). |

A `when` condition on an **optional** argument needs `present`: a comparison on a missing argument
fails safe (it holds), so `{ "arg": "discountPercent", "op": "gt", "value": { "limit": "x" } }` alone
gates every call, including the ones that carry no discount. Write the pair instead —

```json
"when": [
  { "arg": "discountPercent", "op": "present" },
  { "arg": "discountPercent", "op": "gt", "value": { "limit": "booking_discount_percent" } }
]
```

— because `when` is a conjunction: absent makes `present` false, so nothing waits. `absent` is the
mirror. Neither takes a value. Absence with no presence operator still holds, so a malformed call
cannot skip a gate by leaving a field out.

A condition can also total an argument instead of comparing it. `field` names a numeric field of each
element of an array argument, and `times` an optional second field to multiply it by:

```json
"when": [
  { "arg": "lines", "op": "gt", "field": "unitPriceCents", "times": "quantity",
    "value": { "limit": "large_invoice" } }
]
```

That is "the lines come to more than the business's limit" with no invoice knowledge in the SDK or in
the office. `op` stays the comparison, so `gt` means the same thing on a total as on one number. The
sum fails safe on every element: a missing, non-numeric or negative field, or a `times` that is not a
positive number, refuses the whole total rather than skipping that element — a skipped element reports
a smaller total than the call's own numbers, which is the one direction that slips a call past a
limit. An empty array is not a total of zero; there is nothing to compare.

An approval can declare its **amount**, the money a call is about, which a remote approver's limit is
checked against (RASF-3108). It names an argument, or a field totalled over one, the same way, and is
in cents:

```json
"amount": { "arg": "lines", "field": "unitPriceCents", "times": "quantity" }
```

The amount is never taken from `when`, whose numbers can be percentages or counts. An approval with
no amount can be approved only by someone with no approval limit.


It guards against three habits:
- pasting policy manuals into `AGENTS.md`
- asking the model in a prompt to "be careful" instead of gating the action
- letting the model declare work finished

Each layer is files or manifest data, never generated code: `@officehum/sdk` enforces wisdom, and
Office Hum enforces workflow (hand-offs are host tools; the board checking completion evidence is
designed, and nothing runs `done` evidence yet (RASF-3230): today the SDK validates that it is
declared, that a tool it names changes nothing, and that it passes only arguments the tool takes).

`checkFourLayers()` checks a package, and `validatePackage()` runs it:
- **Context:** the word budget, no amounts, percentages or thresholds in context files, and a "You may not" section
- **Knowledge:** references only inside `skills/<id>/references/`, and no `data/`, `work/` or `deliverables/` folder
- **Wisdom:** no generic shell or file tool in the role's list (every writing tool's missing approval decision is a manifest error, from `validateManifest`, so it holds for every role)
- **Workflow:** `done` completion evidence for every accepted ticket type

It is strict (every issue an error) for the free department roles and for Role Factory output.
Elsewhere it gives warnings, except wisdom issues, which are always errors.

Learned memory (below) only ever adds to context and knowledge, through an approval; nothing an
agent learns can change the wisdom layer.

## Package layout

```
@officehum/bookkeeper/
  package.json          peerDependencies: Pi Durable and pi-ai 1.3.x
  officehum.json        Office Hum metadata: tools, approvals, accepts, connectors, skills, evals
  AGENTS.md             the role: who it is, what it does, how it works, house style
  APPEND_SYSTEM.md      rules appended to the end of the system prompt (boundaries)
  role.md               optional: the researched description of the job, every claim cited
  role.sources.json     the sources and the supporting passages behind role.md's claims
  skills/
    collections/
      SKILL.md          Agent Skills format: name, description, instructions
      references/       optional files the skill points to
  src/index.ts          the entry point: tools, approval conditions, defineRole
  evals/                scenarios with expected outcomes
```

The files follow Pi's conventions: `AGENTS.md` and `APPEND_SYSTEM.md` as in Pi's agent directory,
and skills in the [Agent Skills format](https://agentskills.io/specification). Pi Durable itself does
not load these files (Pi's coding agent does), so `defineRole` brings them to Pi Durable:

| File | How the agent sees it |
| --- | --- |
| `AGENTS.md` | The `agents_md` prompt section |
| `skills/*/SKILL.md` | The `skills` section lists each enabled skill's name and description; the agent loads the instructions (and reference files) on demand with the safe `read_skill` tool, as Pi does |
| `APPEND_SYSTEM.md` | The `append_system` section, last of the role's sections |
| Tools | `defineTool` with `replay` written out; a skill's tools live in a `<role>.<skill>` extension selected only while the skill is on |
| Approvals | `approvalGate()` in the role extension; applicability, facts and decisions kept in separate tool-task memos |

A role gets no shell or file-editing tools. Pi Durable's own `instructions` stay free for the host's
per-conversation notes.

### `role.md` and `role.sources.json`

A departmental role may ship `role.md`: its function, responsibilities and actions, terminology,
workflows, principles, systems, decisions that go to a manager, measures and sources, as `##`
sections in that order. `role.sources.json` holds `sources` (`S1`, `S2`, … with `url`, `title`,
`kind` and `fetchedOn`) and `claims` (`C1`, `C2`, … each with one or more `{ source, passage }`).
`validatePackage` runs `checkRoleMd` when `role.md` exists, offline, and enforces six rules:

1. Every required section is present, in order.
2. Every list item in the eight content sections ends with claim markers such as `[C12]` or `[C3, C4]`.
3. Every marker names a claim in `role.sources.json`.
4. Every claim has at least one source, each source id exists, and each passage is 1 to 400 characters.
5. `Sources` lists exactly the sources in `role.sources.json`, as `- [S1] Title — URL`. Besides those entries it
   may hold only one closing paragraph that starts `Source licences.`; any other line is reported.
6. Every source is cited by at least one claim.

`officehum verify-role ROLE_DIR [--online]` prints the same issues and exits 1 on any error.
`ROLE_DIR` may be a role package or a folder holding only `role.md` and `role.sources.json`, so a
role can be researched before its package exists; `npm run sync-company` skips such a folder until it
has an `officehum.json`.
`--online` also fetches each source and reports every claim whose passage is not in the page text,
ignoring whitespace and case. That check needs the network, so CI does not run it.

## The entry point

```ts
import { fileURLToPath } from "node:url";
import { defineRole, type Approver } from "@officehum/sdk";
import manifest from "../officehum.json" with { type: "json" };

export default function bookkeeper(options: {
  quickbooks: QuickBooks;
  overlays?: string[];
  approve?: Approver;
}) {
  return defineRole({
    packageDir: fileURLToPath(new URL("..", import.meta.url)),
    manifest,
    overlays: options.overlays,
    approve: options.approve,
    tools: [readInvoices(options.quickbooks), createInvoice(options.quickbooks)],
    skillTools: { collections: [sendReminder(options.quickbooks)] },
    when: { large_invoice: (args) => invoiceTotal(args) > 5000 },
  });
}
```

Code conditions may be synchronous one-argument predicates or async predicates that read committed
durable documents through a read-only environment, and may read the role's limits through it too:

```ts
const firstContact: ApprovalCondition = async (args, { read, limits }, context) => {
  const history = await read.snapshot(MessagesDoc, context);
  if (history?.messages.some((message) => sameTarget(message, args))) return false;
  return invoiceTotal(args) > (limits.large_invoice ?? 0);
};
```

The environment exposes only bound `snapshot` and `snapshotAsOf` methods, plus the resolved
`limits`. A role can also read them directly, through `role.current().limits`, when it writes a
condition that needs the business's values. Before approving or bypassing, the gate stores a
canonical tool/arguments applicability memo with the computed boolean. That value is immutable for
the call across recovery, including `false`; existing legacy decision memos remain authoritative.
Predicate errors, rejected promises, and nonboolean results require approval, while active
cancellation propagates. This keeps a previously declined call declined even when another call later
changes the durable history that the predicate reads, and a condition that names a limit it cannot
resolve waits for a person, like any other error.

An approval can also have a **facts reader** (`approvalFacts` in `defineRole`, keyed by approval
id), so the person approves what the role's records hold rather than what the model typed. After
applicability, and only when an approver is configured, the gate calls the reader with the call's
arguments, the hook context, and the call's identity `{ conversationId, taskId }`
(`ApprovalCallIdentity`). The ids come from the Pi Durable hook API, never from tool arguments, so a
reader can scope what it reads to the call's verified sender by handing them to the role's
`SenderResolver`; the SDK gate, the office gate and the eval runner all pass them. It memoises the
result under `officehum.approval-facts.<callId>.<approvalId>` (first write
wins) and asks with it as `ApprovalRequest.facts` (`{ summary, facts }`). A reader that throws blocks
the call with its message and asks nobody. On a yes the gate returns the arguments with
`officehumApprovedFacts` (`APPROVED_FACTS_ARG`) set to the memoised facts; it overwrites that key
whatever the model sent, and strips it from any call it does not grant. The tool reads it with
`approvedFacts(args)`, refuses without it, and its desk refuses when the record no longer equals it
(`sameFacts`). Pi Durable 1.3 validates the arguments a `beforeTool` hook returns against the tool's
parameters again, so a tool whose parameters refuse additional properties declares the key with
`approvedFactsParameter()`. Accounting's `pay_vendor_bill` is the reference: it takes only `{ billId }`.
Purchasing's `request_po_approval` (`{ draftId }`) and `request_new_supplier` (`{ supplierId, reason }`,
the reason being the requester's words, not a desk fact) and Marketing's `request_claim_approval` and
`publish` (`{ draftId }`) follow it. A record the gate reads must exist on the desk, so an eval scenario
whose stubbed write "creates" the record the next gated call names relies on the demonstration desk
holding it: Purchasing's draft PO-1004 and Marketing's held drafts D-104 and D-105 are seeded for
that reason.

A call the approval does not apply to (its `when` holds false) gets no facts, so a tool that requires
them refuses every call the condition exempts. Give a facts reader only to an approval that applies to
every call of its tool, or let the tool proceed without facts when no approval applied. `defineRole`
also exposes the readers as `DefinedRole.approvalFacts` (always set, `{}` when the role has none), so a
host's own gate can read the same facts.

**The office gate uses the same readers** (RASF-3486). `loadRole` exposes them as
`LoadedRole.approvalFacts`, and `registerOfficeHooks` passes them to the office's gate. When the gate
records a request for a declaration with a reader, it reads the facts once and stores them on the
board row (`approvals.facts_json`, board migration 8). The Inbox item carries them as `facts`
(`{ summary, facts }`, or `null`), so a person sees the bill and not only `{ billId }`. A reader that
throws blocks the call with its message and records nothing. A repeat of a waiting call is the same
ask, and the desk is not read again. The arguments hash ignores `officehumApprovedFacts`. On a granted
decision the gate returns the arguments with that key set to the row's stored facts, so the tool is
bound to what the person saw, and its desk refuses if the record has changed since. The office gate
strips a model-supplied key on every other path: no ticket, no declaration applies, a declaration with
no reader, a granted row that holds no facts (rows asked before migration 8 read `facts: null`), and
every blocked call. A red-team trial runs the office gate with the role's own gate omitted, so this
gate must strip the key by itself. A grant hands on facts only from a row asked under the same
declaration; a row asked under another declaration on the same tool hands on none. A reader or board
read interrupted by an abort is rethrown, not turned into a block, so the call runs again on resume.

The office gate runs before the role's own gate, and it replaces `officehumApprovedFacts` whatever an
earlier hook set. So whenever a role gate with readers also runs, the office gate must be given the
same readers. A host that installs the office gate for a loaded role must pass
`loadedRole.approvalFacts` (`OfficeExtensionOptions.approvalFacts`, `OfficeHookSeam.approvalFacts`).
Without it, no facts are recorded, and a tool that requires them refuses after a grant. In
office-mode evals, the runner's scripted decision reads the facts the same way before it writes its
row, so a scripted yes binds the tool exactly as a person's would.

Installing it on any Pi Durable harness:

```ts
const role = bookkeeper({ quickbooks, overlays: ["./my-bookkeeper"] });
for (const extension of role.extensions) registry.install(extension);
const harness = await Harness.open(storage, { models, registry }, context);
const root = await harness.root(context, { agent: role.agent });
```

**Today comes from the host's clock.** `defineRole({ now })` adds a `today` prompt section, rendered
from that clock at every request: today's date and weekday, the next 14 dates with their weekdays,
and the rule that every date the role states or records comes from that section or a tool result.
The day is the one in the time zone the role passes as `defineRole({ timeZone })`: the roles that
read a company record pass its `hours.timezone` (the default company: `America/Los_Angeles`) and their
desks date records the same way, through the SDK's `localDate(now, timeZone)`, so 17:00 in Portland is
still today and a notice period is not a day short. With no `timeZone` the day is UTC's. The Front
Desk is the exception: its appointments are UTC. With no `now` there is no section. The first-wave roles take `now` as a factory
option and pass the same clock to their demonstration desk. If the option is left out, the
demonstration desk uses its fixed demo date (`DEMO_NOW`) and a host's own desk uses the system clock.
`loadRole(dir, { now })` passes the clock to the factory, so no client may be named `now`.

**Demonstration data only when the host asks.** A role that keeps its records behind a desk (Bookkeeper's
payables, Marketing, Operations, People Ops, Purchasing, Sales, Support) takes `desk` and `demo` as
factory options. With a `desk`, it uses that desk. With no `desk` and `demo: true`, it builds the
demonstration desk it ships with. With neither, it still builds, and every tool and approval facts
reader that touches the desk refuses with the same message (`No <role> desk is bound to this role, so
nothing was read or written. …`), so a host that forgets to bind its system of record never serves
made-up records. `loadRole(dir, { demo })` passes the flag to the factory, so no client or user config
may be named `demo`. The eval runner always sets it, because scenarios are written against the
demonstration data; `officehum run` sets it with `--demo`.

**Who is asking comes from the host, verified.** A role never takes "who is asking" from a tool
argument or from message text: anyone can type a name, an email address or "this is Dana". The host
passes a `SenderResolver` as the factory option `sender`. A hook or tool calls it with the
`{ conversationId, taskId }` of its own Pi Durable hook or tool context, never from a tool argument
(an id the model chose could name another conversation's sender), and gets a
`VerifiedSender { origin, channel, contact }`, or `undefined`. With no resolver, or `undefined` from
it, the sender is unknown and the role acts as it would for a stranger.
`senderPerson(company, sender)` finds the person on the company record: by id for an internal
sender, by email for any sender (whole, ignoring case), and by phone for any sender, compared digit
for digit on a leading "+" and the digits, so the SMS gateway's E.164 number matches the record's
formatted one.

**One rule for a colleague.** A sender is a colleague, a person on the company record a role may
treat as staff, only when `origin` is `internal`. An outside email or text is never a colleague, even
from a colleague's own address or number: an outside channel does not prove who typed it, so it gets
what any outside contact gets. The rule lives in one place, the SDK's `colleague(company, sender)`
beside `senderPerson`, and every role that trusts staff asks it (Support before showing any client's
cases, Purchasing before placing a requested order or recording a delivery report, People Ops before
treating a sender as office staff). `senderPerson` on its own is for recognising an outside contact,
never for trusting one as staff. The one exception is People Ops' crew: they are not on the company
record and have no internal channel, so a text or email from a crew member's own number or address
(matched against their staff record) may read their own leave balance and file their own time off,
under the same notice and approval rules. Filing for anyone else still needs a colleague.

**The head of the company** is the SDK's `companyHead(company)`: whoever holds a head title (one
that starts with managing director, owner, president or chief executive, so not "Vice President",
"Product Owner" or "Co-owner"), wherever they sit in the record, and a bare "director" only when
nobody does. Roles send a complaint about its usual owner there. The company
validator (`npm run sync-company`) refuses two people with head titles, naming both paths.

A sender comes from one of three places today, and nowhere else:

- **The eval runner**, from the scenario (below).
- **`officehum run --as PERSON`**, for the operator at the terminal. The terminal is the operator's
  own machine, so they say who they are; the CLI checks it against the company record generated into
  the role package (`skills/company-handbook/references/facts.json`, by id or email, as `colleague`
  matches an internal sender) and refuses anyone it does not name. The role gets
  `{ origin: "internal", channel: "terminal", contact: <person id> }` for every call. With no `--as`
  the CLI passes no resolver and the sender is unknown.
- **A board-backed host**, which passes `boardSenderResolver(board)`. Today the only host that does
  is the eval runner's office mode. `officehum runtime --board` opens a board for its roles but does
  not pass the resolver: the tickets its agents open do not name the person who asked, so there is
  no sender to resolve yet, and a role there sees the sender as unknown.

`boardSenderResolver(board)` reads the provenance row of the ticket the
conversation is bound to, which the channel gateway resolved before the ticket existed. A child
ticket, `agent_dispatch` children included, copies its root's row, so delegated work keeps the
original asker. `loadRole(dir, { sender })` passes the resolver to the factory, so no client or user
config may be named `sender`. The eval runner hands a role the same thing: in office mode the
board's resolver, with the scenario's `from` and `channel` on the ticket's provenance and its
`origin` as the provenance's origin (internal when the scenario gives none; an inbound-email delivery
is always external and keeps `email` as its channel); in bare mode the scenario's `from` with its
`origin` (external when the scenario gives none), or unknown when the scenario names nobody. A
scenario whose sender is staff says `"origin": "internal"`.

## Overlays: configuring a role without changing it

An overlay is a directory with the package's layout. Overlays sit on the package the way Pi's project
`.pi/` sits on its agent directory, lowest first:

| File | In the package | In an overlay | When both exist |
| --- | --- | --- | --- |
| `AGENTS.md` | Required: the role | The business's additions | Combined, package first |
| `AGENTS.override.md` | Not allowed | Optional | Replaces every `AGENTS.md` below it |
| `APPEND_SYSTEM.md` | Optional | Optional | The top-most one wins (Pi's rule) |
| `skills/<name>/` | Bundled skills | New or edited skills | Merged by name; the higher layer wins |
| `settings.json` | Not allowed (defaults are in `officehum.json`) | Model; skills and tools on or off; named limits | Applied in order; later overlays win |

An overlay's `settings.json` uses Pi's setting names and its `+name` / `-name` edit lists:

```json
{
  "defaultProvider": "paper",
  "defaultModel": "ultramarine-1-flash",
  "defaultThinkingLevel": "high",
  "skills": ["+vip-customers", "-collections"],
  "tools": ["-send_reminder"],
  "limits": { "large_invoice": 2500 }
}
```

Rules:

- Overlays can switch tools **off**, never add them. New tools arrive only in a package release.
- **Limits change; they are never removed.** An overlay sets a value for a limit the package declares.
  It cannot add a limit, remove one, or switch its approval off: a `null` value is refused, because a
  limit that disappeared would leave the approval it configures with nothing to compare.
- Overlay skills hold **instructions and reference files only** (`.md`, `.txt`, `.csv`, `.json`), never
  scripts. Code arrives only in packages, which agencies and developers can publish.
- A replaced skill keeps its on/off state; a new skill starts on.
- Roles default to Paper's Ultramarine 1 Flash. An overlay can choose another provider's model the
  same way; Office Hum surfaces offer the models in its tested catalog (RASF-3298). A model change
  applies to new conversations; a saved conversation keeps the model it started with. The Paper
  provider itself ships as the portable `@officehum/provider-paper` package (RASF-3297), so a role's
  default model resolves in a bare Pi Durable install.
- Prompt text and skills update **live**: `role.reload()` re-reads the files and the agent sees the
  change on its next request. A changed model, or skills and tools switched on or off, apply when the
  host next configures the conversation with `role.agent`. A broken edit is reported and the last
  good files stay in use.

Anyone can use overlays: a Pi Durable user writes the files by hand and passes the directory.

## What Office Hum adds: configuration

Office Hum keeps one overlay per agent per business, on the customer's own server, with version
history. Configuring an agent means editing its overlay; upgrading a role replaces only the package,
so a business's configuration is never overwritten.

- **Studio** edits `AGENTS.md` (or replaces it with `AGENTS.override.md`, with a warning), edits
  `APPEND_SYSTEM.md`, adds and edits skills (the spec's playbooks), switches skills and tools on or off,
  sets the business's named limits, and picks the model. When a role upgrade changes a file the business
  overrides, Studio shows the difference.
- **Plain-language configuration.** The officehum.com portal takes requests like "chase overdue
  invoices weekly, not daily" and hands them to a configurator agent on the customer's server. It
  drafts the overlay change, validates it with `resolveRoleFiles`, shows the person a diff, and
  applies it once approved, so keys and data stay on that server. It enables tools and extensions
  only from a catalog of vetted packages and connectors; it does not write code.
- **The office extension** adds hand-offs, approvals through the Inbox and Teams, budgets and
  provenance when roles work together.

## Engines: a role's deterministic core

Many roles must never produce a number themselves: every figure comes from code. A role does this
with an **engine**, a command-line program (Python, for example) that the role's tools call. The
engine is passed into the role like any app client: the real program in production, `stubEngine` in
tests and evals.

```json
{
  "runtimes": [{ "name": "python3", "version": ">=3.10" }],
  "engine": { "command": ["python3", "engine/engine.py"] },
  "tools": [
    {
      "name": "stock_adjust",
      "replay": "unsafe",
      "description": "Record a stock adjustment.",
      "engine": ["adjust"],
      "parameters": {
        "sku": { "type": "string", "description": "The SKU", "required": true },
        "quantity": { "type": "integer", "description": "Units added or removed", "required": true }
      },
      "guidelines": ["Cite the finding id for every quantity you state."]
    }
  ],
  "approvals": [
    {
      "id": "large_decrease",
      "tool": "stock_adjust",
      "description": "Removing more than 10 units",
      "when": [{ "arg": "quantity", "op": "lt", "value": -10 }]
    }
  ],
  "commands": [{ "name": "stock-board", "description": "Stock on hand", "engine": ["levels"] }]
}
```

- **Runtimes.** The engine's program must be declared in `runtimes`, so every host knows to provide it.
  `checkRuntimes(manifest)` runs each program's `--version` and checks the range before a host loads
  the role.
- **Engine tools are data.** A tool with `engine` has no code: `defineRole({ engine })` builds it from
  its description, guidelines and parameters, with the declared `replay`. A call becomes
  `<command> <subcommand…> --name value…` (underscores become hyphens; a boolean is a bare flag).
- **The contract.** The engine prints one JSON object: `{ "ok": true, "data": …, "findings": [{ "id": … }],
  "caveats": [] }` or `{ "ok": false, "error": "…" }`. Findings carry the ids the role cites. Results
  over 9,000 characters are cut down to their findings.
- **No mutable files in the package.** The engine reads input from `OFFICEHUM_DATA_DIR` and keeps its
  records in `OFFICEHUM_WORK_DIR`, both the host's. Each call carries `OFFICEHUM_IDEMPOTENCY_KEY` (stable
  per tool call), so a repeated write is applied once.
- **No secrets.** The engine sees only `PATH`, `HOME`, `LANG` and what the host passes explicitly; model
  keys and connector tokens never reach it.
- **Guardrails from data.** An approval's `when` conditions (`gt`, `gte`, `lt`, `lte`, `eq`, `ne`, `in`
  over the call's arguments) decide which calls wait for a person. A threshold may be a named limit,
  `{ "limit": "large_invoice" }`, that the business sets in its overlay. `field` (with optional
  `times`) compares against the sum of a field across an array argument instead of one argument, so
  "the lines come to more than the limit" is data rather than code. They fail safe: a condition on
  a missing or unreadable argument, on an element the sum cannot read, or on a limit that does not
  resolve, counts as met. A condition written in code takes precedence — and note that the office's
  gate reads the manifest only, never the role's code, so an approval written as code is
  unconditional there.
- **Operator commands** are engine views with no model involved: `runOperatorCommand(manifest, engine,
  name)`. Studio and Teams show them in Office Hum; other hosts show them their own way.

A role's generator (the Role Factory, RASF-3096) writes these fields from the interview, so generated
roles carry almost no code.

## Memory: what agents learn on the job

> Status: designed, not built. There is no `@officehum/memory` package yet.

Agents remember what they pick up while working, for example "Acme's AP contact is Jane; she prefers
email" or "Smith & Co is on a payment plan until March". Memory is not company knowledge search
(documents the business hands over) and it is not a skill: skills are fixed instruction files, while
memory needs storage, tools, a prompt section and hooks. It is an **extension**, `@officehum/memory`
(RASF-3222), with a companion skill, `memory-hygiene`, that teaches what is worth remembering.

**Storage is Pi Durable's own.** Records live in session-scoped documents
(`defineDocFamily({ scope: "session" })`, one document per subject), committed atomically with the
transcript. The extension works in a bare Pi Durable harness with no extra database. Every agent in an
office harness shares the same memory, and rewinding or forking a conversation does not lose it.
Office Hum adds a search index, review queues and a Studio page on top.

A record has a subject (`business`, `customer:<system>:<id>`, `vendor:…`, `person:<id>`,
`agent:<role>`, `topic:<slug>`), a kind (`fact`, `preference`, `rule`, `procedure`), a category, its
text, a scope (`office` by default, or a department or one agent), its source and a status (`active`,
`unverified`, `proposed`, `superseded`, `retired`).

| Layer | Example | Becomes | Who approves |
| --- | --- | --- | --- |
| Memory | "Acme's AP contact is Jane" | a record | nobody when the source is internal; outside sources stay `unverified` until a person confirms |
| Rule | "Don't chase Smith & Co until March" | an overlay `AGENTS.md` addition under `## Learned rules` | owner or manager, through the overlay approval |
| Procedure | "How we onboard a new client" | an overlay skill (instructions only) | owner or manager, through the overlay approval |

Learning is free at the bottom layer; anything that changes how an agent behaves goes through the
overlay draft, diff, approval and undo described above.

**Guardrails, enforced in code:**

- **The source comes from code.** The host's `sourceOf` reads the run's provenance: a staff member's own
  message is `person`; anything from a customer email, SMS, web page or peer office is `external`. What
  the model claims about a source is ignored.
- **Outside content never becomes trusted memory.** It is saved as an `unverified` claim and shown in the
  prompt as "Unconfirmed:".
- **Protected categories are set only by a person.** Payment and bank details, approval limits,
  permissions and who may authorize things (`payment_details`, `authority`). A save from any other
  source is refused and opens a review item; a pattern scan (IBANs, routing and card numbers, "our bank
  details changed") forces the category. This blocks the classic "please update our bank details" fraud.
- **Memory never grants authority.** It is rendered as information, not instructions, like other
  outside content; approvals, limits and permissions come only from manifests, overlays and the
  office's people records.
- **No secrets.** Text that looks like a key, password or card number is refused.
- **History is kept.** A correction supersedes the old record; temporary facts carry a review date;
  people can see, correct and permanently delete what agents remember about them.

The prompt section is capped (about 600 tokens of business-wide records plus about 800 for the
subjects of the current ticket), so memory never crowds out the role's own instructions; anything
else is found with `memory_recall`.

## Context engineering

> Status: mostly schema only, not built. `officehum.json` accepts every field named here and
> `validateManifest` checks them, but almost nothing reads them at run time. What runs today:
> `agentCard()` and its formatters in `@officehum/sdk` (no host calls them yet); the `team` prompt
> section, which the office extension builds from the installed manifests' `accepts`; and
> `checkAgent`'s prompt budget and sub-agent reference checks. Each part below says what is not built.

Context engineering is deciding what each agent sees, when, and in what shape. The four layers decide
*where* something belongs; context engineering decides how it reaches the model on each request
(RASF-3232). Three parts:

**Agents know each other.** Every role has an **agent card**, built by `agentCard()` from its
`officehum.json` and the business's overlay, so it always matches the agent's real, effective tools.
A card holds:
- who the agent is
- the ticket types it accepts and the ones it hands to others (`dispatches`)
- its capabilities: skills, and tools marked as reads, changes, or needs approval
- what it never does (`mayNot`)
- its status

In an office, the registry holds every agent's card:
- a short `team` section lists colleagues, one line each, in a stable order
- `agent_directory` and `agent_card` give details on demand
- linked offices and the public catalog of free roles come later (RASF-3239)

Not built: the card registry and the `agent_directory` and `agent_card` tools. `agentCard()` builds a
card, but no host holds or serves one; the `team` section that ships lists each colleague with the
ticket types it accepts, read from the manifests rather than from cards.

Hand-offs still go by ticket type: knowing a colleague's tools helps an agent choose whom to ask,
never lets it call those tools. An office warns at install time when a role dispatches a ticket type
that no agent accepts (not built: today `agent_dispatch` refuses such a type when it is called, unless
the company record routes it to a person).

**Each role has a context plan.** `contextPlan` in `officehum.json` declares:
- the prompt budget
- retrieval sources (business documents searched instead of pasted)
- sub-agents (narrow workers with tools that change nothing, a small model and an output schema)
- the history filter
- amount masking
- model tiers
- memory subjects
- tool groups

Schema only, not built, except two checks. `checkAgent` holds the role's stable prompt to
`promptBudgetTokens`, and `validateManifest` and `checkAgent` check each sub-agent's references (safe
tools and skills the role declares). Nothing runs a sub-agent, searches a retrieval source, filters
history, masks amounts, picks a model tier, stores memory or narrows tools by ticket type: `retrieval`,
`subagents`, `historyFilter`, `maskAmounts`, `modelTiers`, `memorySubjects` and `toolGroups` are
validated and then unused.

Also not built: the Role Factory does not write a `contextPlan` or context evals. As designed, the
Role Factory builds the plan from a context profile in the interview. A rule table recommends each
technique with a reason that quotes the interview, and a person accepts or rejects each one in
`ROLE_SPEC.md` — the document the interview writes and the generator reads ([role-spec.md](role-spec.md)).
The generated package carries context evals: the prompt stays under budget, the prompt
prefix is identical across turns, cited ids survive filtering, and sub-agents return valid results.

**Durable context patterns** (designed for `@officehum/sdk`, on Pi Durable's own hooks). The last
column says what exists in the code today:

| Pattern | How | Today |
| --- | --- | --- |
| Storage is not context | The transcript stays complete in storage; each request gets a projection of it | Pi Durable's own behaviour; Office Hum adds no projection of its own |
| Stable sections | No timestamps or counters in stable sections, and per-ticket sections last, so the provider's prompt cache holds; `checkAgent` renders sections twice and flags differences | Not built in `checkAgent`. A prompt-cache check over recorded requests exists in `packages/office/src/evals/prompt-cache.ts`, used only by its own tests |
| Relevance filter | A `beforeRequest` hook stubs older tool results that no longer matter, for that request only; cited ids are always kept, and `context_recall` brings a result back | Not built: no such hook and no `context_recall` tool |
| Compaction that keeps ids | A `beforeCompact` hook checks the summary keeps every cited id and figure, and appends any it dropped | Not built |
| Decisions in memos | Filter and approval decisions live in task memos, so a restart reuses them | Built for approval decisions; there is no filter |
| Amount masking | `read_skill` masks sample amounts in skills and references, so the model takes figures from the engine | Not built: `read_skill` returns the text as written, and `maskAmounts` is never read |
| Sub-agents | Task-owned child conversations with only tools that change nothing, a small model and an output schema; fan-out survives restarts | Not built: declarations are validated, nothing runs them |

## `officehum.json`

Office Hum reads it without running role code: for routing (`accepts`), Studio (tools as permissions,
connectors, skills), the Inbox (`approvals`) and release gates (`evals`). Pi Durable ignores it.

```json
{
  "$schema": "../../packages/sdk/schema/officehum.schema.json",
  "schemaVersion": 1,
  "id": "bookkeeper",
  "name": "Bookkeeper",
  "department": "finance",
  "role": "Invoices completed jobs, chases overdue payments, answers billing questions",
  "defaultModel": { "provider": "paper", "modelId": "ultramarine-1-flash", "thinkingLevel": "max" },
  "tools": [
    { "name": "read_invoices", "replay": "safe" },
    { "name": "create_invoice", "replay": "unsafe" },
    { "name": "send_reminder", "replay": "unsafe", "skill": "collections", "noApproval": "an internal reminder to a known customer; nothing outside the business changes" }
  ],
  "connectors": ["quickbooks"],
  "limits": {
    "large_invoice": { "description": "The amount above which invoices need approval", "default": 5000 }
  },
  "approvals": [
    {
      "id": "large_invoice",
      "tool": "create_invoice",
      "description": "Invoices over the set amount",

    }
  ],
  "channels": ["email"],
  "accepts": [
    {
      "type": "invoice.create",
      "description": "Invoice a completed job",
      "done": [
        { "engine": ["check"], "args": { "job": "{ticket.data.jobId}" } },
        { "tool": "read_invoices", "args": { "job": "{ticket.data.jobId}" }, "expect": "found" }

      "type": "invoice.question",
      "description": "Answer a billing question",

    }
  ],
  "dispatches": [
    { "type": "customer.contact", "when": "a customer needs a reply about an invoice" }
  ],

    { "action": "Issue a refund", "instead": "record a credit note and leave it for a person to approve" }

}
```

| Field | Rule |
| --- | --- |
| `schemaVersion` | `1`. Bumped only with a migration; the Office reads the previous version for one more release. |
| `id` | Kebab-case. The role extension's name and the board's assignee id. |
| `name`, `role` | Display name; one-line job description (≤ 120 characters). |
| `department` | `front-office`, `finance`, `operations`, `sales`, `marketing` or `people`. |
| `defaultModel` | `provider` and `modelId`, optional `thinkingLevel`. Overlays can change it. |
| `runtimes[]` | Programs the host must provide: `name` and a version range, e.g. `python3` `>=3.10`. |
| `engine` | `command` run from the package root, e.g. `["python3", "engine/engine.py"]`. Its program must be a declared runtime. |
| `tools[]` | `name` in `snake_case`, unique; `replay` required, `"safe"` or `"unsafe"`: Pi Durable's replay policy and nothing more. `"safe"` means an interrupted call may be run again (the tool reads, or is idempotent); it does not mean the tool changes nothing. Optional `writes: true` marks a tool that changes something and is still safe to run again, such as Front Desk's bookings; an unsafe tool always counts as writing. Optional `skill` puts the tool in that skill's extension; optional `noApproval` (at most 300 characters) says why a writing tool needs no approval, e.g. `"internal note; no outside effect"`. A tool that writes states exactly one of the two — an approval in `approvals[]` or `noApproval`, never both, never neither — and a tool that changes nothing states neither. A safe tool that an approval names must state `writes: true`. Engine tools add `engine` (the subcommand), `description`, `parameters` and `guidelines`. `read_skill` (the SDK's), `agent_dispatch`, `agent_inbox` and `agent_reply` (the office tools that ship today), and the reserved-but-unshipped `board_*`, `delegate` and `ask` are reserved — the last group so a role published now cannot take a name the office may use later. |
| `commands[]` | Operator views: `name`, `description`, and the `engine` subcommand they run. |
| `connectors` | Kebab-case ids of the apps the business must connect, e.g. `quickbooks`. |
| `approvals[]` | `id` (snake_case), `tool` (a declared tool), `description` (shown in the Inbox), optional `when` conditions over the tool's arguments. A numeric comparison may take a named limit as its value, `{ "limit": "large_invoice" }`, instead of a number. `field` names a numeric field of each element of an array argument, so the comparison is against their sum; `times` multiplies it by a second field per element. Conditions too complex to declare go in the entry point's `when`, keyed by `id` — but the office gate cannot see those, and takes such an approval as unconditional. |
| `limits` | Named amounts the business sets, e.g. `large_invoice`: each has a `description` and a `default`. An approval compares against a limit with `{ "limit": "NAME" }` for `gt`, `gte`, `lt` or `lte`. An overlay changes a value, never removes it. |
| `channels` | `email`, `sms`, `chat`: where the role may face the business's customers. A name alone means both directions. An object `{ "channel", "direction", "replyBy"?, "note"? }` declares one that does not run both ways — `direction` is `inbound`, `outbound` or `both`, and `replyBy` names a channel the role also declares. The Front Desk receives texts and answers them by email: `{ "channel": "sms", "direction": "inbound", "replyBy": "email" }`. |
| `accepts[]` | Dotted ticket types (`invoice.create`) with a description shown to delegating agents, and `done`: the completion evidence for that type (validated today; no host runs it yet). As designed, every entry must pass, and the host runs it, never the model: `{ "engine": ["subcommand", …], "args": {…} }` (the engine answers `ok` with at least one finding), `{ "tool": "NAME", "args": {…}, "expect": "found" }` (a declared tool that is safe to re-run and does not write, whose result reports `found`), `{ "file": "NAME" }` (the result attaches a file), or `{ "person": true }`. Args may interpolate `{ticket.id}` and `{ticket.data.<path>}`, and nothing else; a `tool` entry passes only arguments its tool takes, and should ask about the ticket's own work (a check that is true before the work starts proves nothing, so where no tool can show the work, declare the person alone). |
| `dispatches[]` | Ticket types this role hands to other roles, and when: `type` (a dotted ticket type) and `when` (one line about the trigger). A type the role also `accepts` is an error: a role accepts a type or hands it off, never both. A card carries them, so an agent can choose whom to ask. |
| `mayNot[]` | What the role never does, and what it does instead: `action` and `instead`. Wisdom data: it appears on the role's agent card, never as a tool. |
| `contextPlan` | How the role decides what each request sees. Every part is optional. Only `promptBudgetTokens` and the sub-agent reference rules are enforced today; the rest is schema only (see "Context engineering"). `promptBudgetTokens` (default 4,000) caps the stable prompt. `retrieval.sources[]` (`id`, `description`) are business documents the role searches instead of pasting them in. `subagents[]` are narrow workers: `id`, `purpose`, `model` (`"small"` or `"default"`), `tools` (declared tools of this role that are safe to re-run and do not write), optional `skills` (declared skills), `output` (a JSON Schema) and optional `maxParallel`. `historyFilter` (`keepRecentRounds`, `keepCitedIds`, `maxToolResultTokens`). `maskAmounts` (default true when the role has an engine). `modelTiers.small[]` are purposes that may run on the office's small model. `memorySubjects[]` are subject kinds to remember (`business`, `customer`, `vendor`, `person`, `agent`, `topic`). `toolGroups[]` (`id`, `tools`, `forTicketTypes`) offer only the group for the current ticket type. |
| `skills[]` | `id` (the folder under `skills/`) and `enabledByDefault`. The name and description come from `SKILL.md`, so they cannot drift. Every bundled skill folder must be listed. |
| `evals` | Directory of eval files, relative to the package root. |

`version` is the package's `package.json` version, and the supported Pi Durable range is its peer
dependency, so neither can drift from what npm installs. The Office refuses to load a role whose range
excludes the release's exact Pi Durable version.

### The published schema

`@officehum/sdk` publishes `schema/officehum.schema.json`: an editor-facing JSON Schema (draft
2020-12) generated from the SDK's own `ManifestSchema` when the package builds, so it is the manifest
the code validates, not a second description of it. Point a manifest at it with `$schema`, relative to
the manifest:

- a role package under `agents/`: `"$schema": "../../packages/sdk/schema/officehum.schema.json"`
- an SDK fixture under `packages/sdk/fixtures/<name>/`: `"$schema": "../../schema/officehum.schema.json"`

Every manifest this repository ships declares one, and `packages/sdk/src/schema.test.ts` resolves each
declared path against the file it names — a path that does not work fails the build rather than quietly
giving an editor no completion. The document's `$id` is `urn:officehum:schema:officehum.json:v1`, its
`$schema` is `https://json-schema.org/draft/2020-12/schema`, and it claims `additionalProperties:
false`, so an unknown field is flagged as it is typed.

The schema carries every field in the table above, including the three RASF-3229 added:

- `limits`: a map of snake_case names to `{ "description", "default" }` — the description up to 300
  characters, the default a number.
- `tools[].noApproval`: optional text up to 300 characters, saying why a writing tool needs none.
- `tools[].writes`: optional boolean; `true` for a tool that changes something yet is safe to re-run.
- `accepts[].done`: a list of completion evidence, each entry one of the four shapes — `engine`,
  `tool` with `expect: "found"`, `file`, or `person: true`.

It is structural, and only structural. The rules that span fields — unique names, reserved tool names,
the single approval decision every writing tool states, limits and tools that a condition or a `done`
entry refers to — cannot be written in JSON Schema, and stay in `validateManifest`, which reports them
with a path and a plain message. Role packages the Role Factory generates declare no `$schema`: they are
written to whatever directory the generator is given, so no relative path is right for them.

## Validation

Every validator reports all problems at once, each with a path and a plain message:

```
officehum.json › tools[1].replay: must be one of "safe", "unsafe" (got "maybe")
skills/collections/SKILL.md › name: must match its folder name "collections" (got "Collections")
overlay acme/settings.json › tools[0]: "issue_refund" is not a tool of this role; overlays can switch tools off, not add them
overlay acme/settings.json › limits.vat_rate: "vat_rate" is not a limit of this role; a limit is declared in officehum.json
package.json › dependencies.@officehum/office: is not allowed; a role must run on any Pi Durable install without Office Hum
role › bookkeeper › create_invoice: replay is "safe" in code but "unsafe" in officehum.json
AGENTS.md: warning: is 1200 words; keep AGENTS.md under 1000 words and move the detail into a skill or one of its reference files
```

Each issue carries a **severity**: `error` unless it says `warning:`, and a warning leaves the package valid — it is what the four-layer check reports on a role Office Hum does not own.

- `validateManifest(json)`: the schema plus cross-field rules (duplicates, reserved names, references, the approval decision every writing tool states, and completion evidence).
- `resolveRoleFiles({ packageDir, manifest, overlays })`: the role's files and every overlay. Office
  Hum validates a draft overlay with it before applying an edit.
- `checkFourLayers(packageDir, manifest, { strict })`: the four layers, every issue tagged with its
  layer. Context: the word budget, no numbers in `AGENTS.md` or `APPEND_SYSTEM.md`, a "You may not"
  section. Knowledge: references only inside `skills/<id>/references/`, no host folders. Wisdom: no
  generic shell or file-writing tool in the role's list. Workflow: `done` evidence on every accepted
  ticket type. `strict` makes every issue an error; otherwise context, knowledge and workflow issues
  are warnings and wisdom issues stay errors.
- `validatePackage(dir)`: `package.json` against the portability boundary, `officehum.json`, the
  role's files, `role.md` against `role.sources.json` when present, the four layers (strict for a package under `agents/` or one its `package.json`
  marks `"officehum": { "generated": true }`), and every eval file.
- `checkAgent(bundle, manifest, { strict })`: the entry point's output, with no overlays, against the
  manifest, including that each `done` tool entry passes only arguments its tool takes. It also
  renders the role's stable prompt — its own sections, without any host extension's
  — and estimates its size as characters ÷ 4; over `contextPlan.promptBudgetTokens` (default 4,000) is
  a warning, or an error under `strict` (the `checkFourLayers` rule). A declared sub-agent's `tools`
  must be the role's declared tools that are safe to re-run and do not write, and its `skills` must be declared skills.
- `agentCard(manifest, resolvedRole, { status })`: the role's agent card, for other agents and hosts.
  `formatCardLine(card)` gives a team line of at most 160 characters; `formatCard(card)` gives compact
  Markdown for an `agent_card` tool. A card carries no secrets, overlay settings values, limit amounts
  or the role's prompt text, and a tool an overlay switched off is absent.
- `defineRole` validates the manifest and files itself and throws `RoleFilesError` on problems.

## Evals

Evals check the role's judgment: given a situation, it takes the right actions, avoids the wrong
ones, and asks a person where it must. They run before every role release, on every Pi Durable
upgrade, and as a smoke test after each customer upgrade.

Each file in the `evals` directory holds scenarios:

```json
{
  "scenarios": [
    {
      "id": "invoices-completed-job",
      "description": "A completed job arrives; the bookkeeper creates one invoice",
      "severity": "normal",
      "tags": ["smoke"],
      "input": { "kind": "message", "text": "Job J-12 for Acme is done: 3 hours at $120." },
      "stubs": {
        "read_invoices": { "text": "No open invoices for Acme" },
        "create_invoice": { "text": "Created invoice 1042 for $360" },
        "send_reminder": { "text": "Sent" }
      },
      "approvals": {},
      "expect": {
        "calls": [{ "tool": "create_invoice", "args": { "jobId": "J-12" } }],
        "notCalled": ["send_reminder"],
        "approvalsRequested": [],
        "reply": { "contains": ["1042"] }
      },
      "trials": 3,
      "limits": { "maxTurns": 8 }
    }
  ]
}
```

- `input` is a `message` (text, optional `channel`, `from` and `origin`) or a `ticket` (`type` from
  `accepts`, `payload`, optional `provenance: "external"`). Ticket inputs need the office extension.
  `origin` is `"internal"` or `"external"`: where `from` wrote from. Bare mode defaults it to
  external; office mode makes it the ticket's provenance origin. It needs a `from`.
- Every declared tool is stubbed in every scenario, so evals never touch a real system. Stubs keep the
  tool's real name, description and parameters, using `wrapTool`. `read_skill` runs for real: it only
  reads the role's own files. A stub is `{ "text", "isError"? }`, or `{ "byArgs": [{ "args", "text",
  "isError"? }], "otherwise"? }`, which answers by the call's arguments: the first entry whose `args`
  match answers, else `otherwise`, else the trial stops. In `byArgs` and in `expect.calls[].args`, an
  argument given as `{ "includes": "…" }` matches a string argument that contains that text. An
  argument given as `{ "some": { … } }` matches an array argument when at least one element has
  those fields, matched the same way (only the fields listed, matchers allowed inside), e.g. a quote
  line `{ "lines": { "some": { "priceBookItemId": "clean-office-visit", "visitsPerWeek": 5 } } }`. So a
  parameter cannot be matched against the literal object `{ "includes": … }`: that object is always
  the matcher. A matcher goes on an argument's value only: `validateSuite` refuses `includes` directly
  under `args`, with its path.
- `approvals` scripts the person's decision for each approval id: `approve`, `decline` or `pending`.
  `pending` means the request reaches a person who has not answered by the end of the trial: the
  call is blocked as waiting and the run goes on, so a scenario can grade what the role says while
  it waits. An approver gives the same answer as `{ approved: false, pending: true }`; the gate
  records no decision for it, so the same call is asked again later and runs on a yes.
- `expect.calls` must appear in that order, with other calls allowed in between; `args` matches only
  the fields listed. `notCalled`, `approvalsRequested` (exact set), `delegated` (office extension only)
  and `reply.contains` / `reply.containsAny` / `reply.notContains` complete the checks. Reply matching
  is case-insensitive and compares clock readings without a `:00` seconds suffix, so `10:00` satisfies
  an expectation of `10:00:00`. `containsAny` holds groups of alternatives and needs one phrase from
  each group, so a scenario names the fact it requires instead of one sentence that carries it; a
  prohibition is a wrong action in `notCalled`, never a banned word in `notContains`.
- `critical` scenarios must pass every trial; `normal` scenarios count toward the suite pass rate
  (default 90%). `trials` defaults to 3. Checks are fixed rules; model-graded rubrics may come later as
  a score that never blocks.

The SDK owns the format, its validation, the grading and the report. Running a scenario needs a
harness, so it goes through an `AgentRunner`; RASF-3064 tests it with a scripted runner, and
RASF-3065 adds the Pi Durable runner (bare harness, later with the office extension) and a scripted
model provider for deterministic CI.

## Out of scope for RASF-3064

- Running agents on Pi Durable, solo mode, crash and resume (RASF-3065).
- The office extension, board tools, relay (M2 · Office runtime).
- Studio, the configurator agent and the Docker distribution (their own epics).
- Approval UI and channel caps (RASF-3073, RASF-3089); the QuickBooks client (RASF-3091).
