## 1. How do subagents work (task-owned conversations, foreground vs background, persistent subagents with a reporter task)?

### Takeaway
Pi Durable has **no built-in subagent tool or supervisor**. Subagents are a *pattern* built from two primitives: (a) a conversation can be **owned by a task** (`ownership: { kind: "task", taskId }`), and (b) a tool or task can get a handle with `api.conversation(id)` / `runtime.conversation(id)` and `submit()` input to it with a deterministic `requestId`. The foreground pattern (example 22) has the tool call own the child and block until it answers. The background or persistent pattern (example 23) has a background **anchor** task own the child. A background **reporter** task per message submits the message to the child, waits for the answer, then posts it back into the parent conversation as a `followUp` **input** (so it starts a new parent turn). Request IDs make this restart-safe.

### Cited Findings
- **No built-in subagents (design intent):** "No built-in subagent tool or supervisor task: two concise, product-style examples ... show the patterns." — [pico-v5-handoff.md §18, v1.0.0](https://github.com/earendil-works/pi/blob/v1.0.0/packages/durable/docs/pico-v5-handoff.md). The blog says the same: "Pi Durable has no built-in subagents, but they take a few lines of code to build" — [BLOG](https://earendil.com/posts/pi-durable/).
- **Ownership model:** `type ConversationOwnership = { kind: "ownerless" } | { kind: "task"; taskId: TaskId }`. `ConversationRecord.owner` holds `{ conversationId, taskId }` — [SPEC §2, ~L104-118](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). "Every conversation is ownerless or owned by a task ... A child task always lives in its owner's conversation; only owned conversations cross conversation boundaries. Owner edges are immutable." — [SPEC §5.5](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **README (both versions), "Abort and Subagents":** "A conversation can be **owned** by a task. A subagent tool creates its child inside `api.commit()` with `ownership: { kind: "task", taskId: api.taskId }`, then drives it through `api.conversation(id)`" — [README-1.0.2] and [README-main](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **Owned-work semantics (README):** "Aborting the call aborts the child. So does the call failing"; "The parent is idle only once the child is."; "A task created with `{ background: true }` is a boundary: work it owns survives the parent's abort and does not keep the parent busy. `root.abort(context, { background: true })` aborts it too." — [README-main](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **Agent inheritance:** "A task-owned conversation, such as a subagent's, starts as a copy of its owner's conversation's agent." A new ownerless conversation gets an empty `pi.agent` `{}`. "Copies are one-time: ... later owner changes do not reach it." — [README-main]; [SPEC §2.2 ~L700-708, §12](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Spec's foreground recipe:** the child is created in one transaction; "a replay-safe rerun finds the child with `scanConversations({ ownerTaskId })` before creating one. After settlement the tool reacquires the child, submits with a request ID derived from its task ID, which a rerun keeps, and waits for that submission's result. Provider call IDs are not unique across a Session and must not serve as request IDs." The tool reports the child via `api.details({ conversationId })` "so a UI that sees the call can attach to the child's view or events." — [SPEC §7.3 ~L3270-3285](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Example 22 (foreground), actual code:** `replay: "safe"`. Inside `api.commit`, it reuses `tx.scanConversations({ ownerTaskId: api.taskId }, 1)` or calls `tx.createConversation({ ownership: { kind: "task", taskId: api.taskId } })` and then `configure(tx, created.id, { extensions: { remove: [Subagent] } })` (so the child cannot spawn subagents). Then `api.details({ conversationId: child })`, `api.conversation(child)`, and `submit({ type: "input", content: task, requestId: \`subagent:${api.taskId}\` })` followed by `.wait()`. It throws if the status is not `done`, reads the answer via `tx.entry(AssistantEntry, settled.answer)`, and returns `{ output: [...], details: { conversationId: child } }` — [EX 22-subagent-foreground.ts L39-77](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/22-subagent-foreground.ts).
- **Example 23 (persistent and background), actual code:**
  - A conversation-scoped doc `app.subagents` maps names to `{ conversationId, reported: EntryId[] }` plus `reporters: Record<string, TaskId>`, with `fork: "initial"` ("A fork of the main conversation starts without subagents") — [EX 23 L41-54](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/23-subagent-background.ts).
  - **Anchor:** "A subagent must outlive the main agent's turns, so its conversation is owned by an anchor: a background task that finishes at once. A background task is a boundary: the main agent's Esc and idle waits stop there, but `abort({ background: true })` still reaches past it" — [EX 23 L56-71](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/23-subagent-background.ts).
  - **Reporter:** a two-phase task. In `deliver` it calls `runtime.conversation(conversationId)` and submits with `whenBusy: followUp ? "followUp" : "steer"` and `requestId: \`subagent:${reporter.id}\``, then `wait()`. In one commit it decides the report and records the answer entry as `reported` ("so a restart does not decide again"). In `report` it gets `runtime.conversation(runtime.conversationId)` (the parent) and submits `{ type: "input", content: report, whenBusy: "followUp", requestId: \`subagent-report:${reporter.id}\` }`. The report text is formatted as `[subagent <name> answered, no reply needed] <text>` — [EX 23 L73-126](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/23-subagent-background.ts).
  - **Tool:** one `subagent` tool with actions `spawn | send | stop | status` and `replay: "unsafe"` ("repeating `stop` could stop newer work"). `spawn` and `send` create the anchor (on spawn), the child conversation, and a reporter in **one commit**, with `{ ownership: { kind: "conversation" }, background: true }`. `stop` calls `(await api.conversation(id)).abort()`, which "Aborts the subagent's current answer and tools and drops its queued messages. It stays usable." `status` reads `LiveDoc.run` of each child to report busy or idle — [EX 23 L132-211](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/23-subagent-background.ts).
  - Restart demo: the Harness is closed while a subagent works, then reopened, and "after the restart its answer still arrives" — [EX 23 L350-360](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/23-subagent-background.ts).
  - README summary: "Each message is delivered by a background reporter task that posts the answer back to the parent as a follow-up input once it arrives; request IDs keep a restart from sending a message or a report twice." — [README-1.0.2] / [README-main](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **Esc interaction:** "If the user presses Esc while it waits in the main agent's queue, it is dropped with the other input; a report that arrives after Esc starts a new turn." — [EX 23 L108-110](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/23-subagent-background.ts).
- **Footgun, owned work holds its owner:** "Foreground work an extension starts in a subagent's conversation holds the calling tool, and with it the run; interrogating a subagent while its tool is completing extends the hold. ... work that should not hold its owner is created conversation-owned and `background`." — [SPEC §12](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Footgun, double-counted spend:** "a tool that runs an owned conversation must not report that conversation's usage in its result; the child's `pi.usage` already counts it" — [SPEC §12](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **After the owner finishes:** "work later started in a conversation it owned, for example a user interrogating a finished subagent, runs normally" — [SPEC §5.4](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Example 24 (child tasks, not conversations):** a `Checkout` task creates four `Payment` child tasks with `ownership: { kind: "task", taskId: task.id }` in one commit and returns `{ status: "waiting", on: payments, policy: "failFast" }`. A later phase reads `runtime.outcomes(...)`. Each payment's `abort` handler undoes its own effect ("refunded") — [EX 24 L57-75](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/24-child-tasks.ts); README: "With `allSettled` it resumes once every task in `on` is done; with `failFast` the first failed child also aborts the others." — [README-main](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md). This is task-level fan-out and join, the primitive for a durable "wait for N subagents" step.
- **Example 28 (reviewer) is not agent-to-agent:** it creates an **ownerless** reviewer conversation with its own model, `extensions: [CodingTools, Reviewer]`, `tools: [createReadTool()]`, and `cwd: worktree`. The "review loop" is a `GenerationTask` `onYield` hook that returns `{ continue: "Look again ..." }` until the answer contains "No further findings." The **host** submits "Review user.ts." directly. The main agent never messages the reviewer — [EX 28-reviewer.ts L33-44, L79-100](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/28-reviewer.ts).
- **1.2.0 fix relevant to background subagents:** "A background task may now wait on the owner of its conversation, which is no cycle ([#10411])", and wait cycles are now rejected by `runtime.commit()` instead of hanging — [CHANGELOG-main 1.2.0](https://github.com/earendil-works/pi/blob/main/packages/durable/CHANGELOG.md).
- **1.2.0 rename:** `ToolExecutionResult.content` is now `output` — [CHANGELOG-main 1.2.0](https://github.com/earendil-works/pi/blob/main/packages/durable/CHANGELOG.md). The 1.0.2 README subagent snippet returns `{ content: [...] }`. The main README's returns `{ output: [...] }`.

### Inferences
- On main, example 23's `reply()` helper still returns `content: [...]` (EX 23 L149-150) although 1.2.0 renamed the field to `output`. Issue #10815 reported that this silently gives the model an empty tool result. A maintainer closed it, saying "this example has been removed", which refers to the coding-agent experimental copy, not to example 23. **Do not copy that line verbatim on ≥1.2.0.**
- The reporter pattern is the only documented way to get a **push** back to a parent: the child's answer becomes a new *user-role input* in the parent (a follow-up turn), not a tool result. The parent model therefore sees subagent replies as user messages, prefixed by convention (`[subagent name ...]`).
- `api.details({ conversationId })` plus `viewState()` / `watchEvents()` on the child is how a UI shows nested agents. It is observation, not messaging.

### Gaps
- No example shows a subagent sending a message *up* on its own initiative mid-run (for example asking the parent a question). The reporter only fires on the child's final answer. A child-side "ask parent" tool would have to be custom-built with the same `conversation(parentId).submit()` primitive. That is not documented.

## 2. Can a tool or task in one ownerless conversation submit input to another ownerless (peer) conversation? API and guarantees

### Takeaway
Yes, mechanically. `api.conversation(id)` (tools) and `runtime.conversation(id)` (tasks) accept **any** conversation ID in the Session. The spec states there is **no subtree authorization layer**: "Possession of a Session-global typed ID is sufficient in trusted code." The handle offers `submit(input)`, `abort()` and `waitForIdle()`. Guarantees come from durable admission plus a per-conversation `requestId` dedupe ("exactly-once" admission for retried submits). Restart-safety needs either a replay-safe tool or a durable task that re-submits with the same `requestId`. There is **no** dedicated peer-messaging, addressing, directory, or mailbox primitive beyond each conversation's own `pi.inbox` queue.

### Cited Findings
- **Handle surface:** `interface ConversationHandle { id; submit(submission: InputSubmissionDraft, context): Promise<Submission>; abort(context); waitForIdle(context); }`. Note `InputSubmissionDraft` = only `type: "input"`. A handle cannot submit a `write` — [SPEC §7.3 L2836-2841](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md); same in installed `dist/harness/types.d.ts` L73-80 (1.0.2, where `abort` also takes `ConversationAbortOptions`).
- **Tool API:** `ToolExecutionApi` has `conversation(id: ConversationId, context): Promise<ConversationHandle | undefined>`, plus `commit`, `createTask`, `getTask`, `waitForTask`, `snapshot`/`watchDoc` (via `DocumentObserver`/`DocumentReader`), and on ≥1.2.0 `executeTool` — [SPEC §7.3 ~L2843-2880](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). Task runtime: `conversation(id, context)`, `waitForTask`, `abortOwned` (≥1.2.0), `ownedTasks` (≥1.2.0), and `context(conversationId, ...)` (reads any conversation's model context) — [SPEC §5.1 ~L1762-1778](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **No authorization by subtree:** "Trusted document and conversation access follows sections 3.3 and 9.2; there is no additional subtree authorization layer. Possession of a Session-global typed ID is sufficient in trusted code." — [SPEC §7.3 ~L3256-3260](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). After a create commit settles, "`conversation(id)` acquires an invocation-bound operational handle for submission, explicit abort, and idle waits **without changing ownership**." — same section.
- **Invocation-bound:** "A handle's operations reject after the invocation ends. A `Submission` returned by its `submit()` is invocation-bound in the same way; the admitted submission remains durable after those methods reject." A commit callback must not call `conversation()` — [SPEC §7.3](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Host-level:** `harness.conversation(id)` looks up any conversation (example 08: `(await harness.conversation(retry.id, context))?.id === retry.id`) — [EX 08-harness-conversations.ts L40](https://github.com/earendil-works/pi/blob/main/packages/durable/test/examples/08-harness-conversations.ts). `harness.createConversation({ ownership: { kind: "ownerless" } })` creates peers — [README-main "More Conversations and Forks"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md). "Hosts discover conversations through lookups and scans. There is no creation listener" — [SPEC §2.2 ~L918-920](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **requestId semantics:** "`requestId` deduplicates within one conversation before any write; reusing one for the other submission type rejects." — [SPEC §6](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). "A request ID makes a retried `submit()` to the same conversation exactly-once; a host that must survive a crash between the two calls first finds its conversation again" — [SPEC §2.2 ~L684-687](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). README: "A retried submission with the same `requestId` returns the existing submission instead of submitting twice" and "`harness.submission(id)` reacquires a submission by ID, for example to wait for it after a restart." — [README-1.0.2/main](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md). Storage exposes `submissionByRequest(conversationId, requestId)` — [SPEC §3.3, §10](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **whenBusy modes:** `"steer" | "followUp" | "reject"`, with followUp as the default. "**Steers** are placed after the current tool round and join the running work. **Follow-ups** are placed when the run answers, and start the next run. **Writes** append an entry without asking the model anything." `reject` throws `ConversationBusy` and "writes no record" — [README "Busy Conversations"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md); [SPEC §6](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Inbox:** queued submissions live in conversation-scoped doc `pi.inbox` (`{ items: InboxItem[] }`, `fork: "initial"`, so "a fork starts with an empty inbox"). Boundary selection is deterministic by item ID. `steeringMode`/`followUpMode` `one-at-a-time | all` — [SPEC §6](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Settlement:** `submit()` "returns after durable admission, not settlement". `Submission.wait()` settles an input "only after its answer or terminal failure" (`done` with `answer` entry ID, or `unanswered` with reason such as `aborted`, `stale`, `reset`, `model_error`). "Cancelling `wait()` only cancels that wait." — [SPEC §2.2 ~L922-933](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Failure leaves queue intact:** "If a run fails, queued items stay in the inbox until the next input or queued write places them" — [README-main](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **New in 1.2.0, typed input entries (useful for attributing a sender):** an input may carry `entry: { kind, data }`, "placed as an entry of that kind carrying that data, with its content as the user message". The README example is `kind: "chat.mention", data: { author: "ann", ... }` — [CHANGELOG 1.2.0](https://github.com/earendil-works/pi/blob/main/packages/durable/CHANGELOG.md); [README-main "Busy Conversations"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md). Not in 1.0.2: the installed `SubmissionDraft` has `entry?: never` for inputs (`dist/harness/types.d.ts` L21).
- **New in 1.2.0, display-only writes** (only `kind`+`data`) "are appended at once, even mid-run, and never queued". Writes with `model`, `head` or `edits` wait for the next boundary "like a steer" — [README-main](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **Raw writes to a busy conversation are a footgun:** "only the Harness appends to a conversation with an active run. Raw entries appended by `Harness.commit()` or a custom task while a generation prepares its request can misplace its system prompt entries; use a write submission." — [SPEC §12](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Replay policy for tools:** a tool "reruns on reopen only when it is declared `replay: "safe"`; otherwise the model gets an `interrupted` error result" — [README "Tools"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md). Tasks resume from their last committed checkpoint — [README "Concepts"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **Not exactly-once execution:** for nested calls (≥1.2.0) "This is not exactly-once execution: ... a replay-safe tool with external effects still needs its own idempotency." — [SPEC §7.3 ~L2981-2984](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Blog:** tools can "start tasks and conversations, and talk to other conversations." — [BLOG](https://earendil.com/posts/pi-durable/).

### Inferences
- A **peer-messaging tool** is buildable from documented pieces: tool `send_to(conversationId, text)` creates (in one commit) a background conversation-owned "courier" task (like example 23's Reporter). The task does `runtime.conversation(peerId).submit({ type: "input", content, whenBusy: "followUp", requestId: \`peer:${taskId}\`, entry: { kind: "app.peer-message", data: { from } } })` (the `entry` field needs ≥1.2.0), optionally waits, and posts a reply back to the sender's conversation the same way. Admission is deduplicated per target conversation by `requestId`. A durable task makes it restart-safe. This is my construction; no peer-messaging example exists in the repo.
- Because the handle only takes `input`, a tool cannot *passively* drop a note into a peer's transcript via the handle. It would need `api.commit(tx => tx.appendEntry(peerId, ...))`, which the spec warns against when the peer is busy. So peer notification effectively **always triggers a model turn** in the recipient (steer or follow-up) unless the host does a write submission through `harness.conversation(id).submit({type:"write"})` (host-level `Conversation.submit` takes full `SubmissionDraft`).
- Guarantee summary: **at-most-once admission per (conversation, requestId)**; **durable once admitted**; delivery to the model happens at deterministic boundaries; the answer is observable via `wait()`; restart safety depends on the caller being a durable task (or replay-safe tool) that reuses the same `requestId`. There are no ordering guarantees *across* different target conversations, no acknowledgement or read receipt, no TTL, and no back-pressure beyond `whenBusy: "reject"`.
- Each recipient's answer to a peer-sent input is a normal assistant entry in the recipient's transcript. Getting it back to the sender is application code (the reporter pattern).

### Gaps
- No documented message envelope (sender identity, reply-to, correlation). It has to be conventions in `content` or in a ≥1.2.0 `entry.data`.
- No documented way to discover "peers" other than `scanConversations` / app documents. There is no registry of named agents.

## 3. Shared state between conversations: session-scoped vs conversation-scoped documents, watchDoc, subscribeCommits — a blackboard?

### Takeaway
Yes, a shared board is supported at the primitive level. `defineDoc`/`defineDocFamily` accept `scope: "session"` (one instance per Session, or per key for families), `scope: "conversation"` (per conversation, with `history` and `fork` policy), or `scope: "task"`. Any tool, task or hook with the token can read it (`snapshot`), mutate it atomically in a `commit` (together with entries and task creation), and observe it (`watchDoc` / `documentState`). Observation is convergent, not an audit log. Session-scoped documents cannot be rewindable. Nothing pushes document changes into a model's context automatically: an agent sees board changes only if a tool reads it, a section renders it, or someone submits an input.

### Cited Findings
- **Scopes:** `DocumentSemantics = { scope: "session" } | LatestConversationSemantics | RewindableConversationSemantics | { scope: "task" }`. `defineDoc` and `defineDocFamily` have overloads per scope, with `SessionDocToken` / `SessionDocFamilyToken` — [SPEC §3.1 ~L995-1110](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). `DocumentRecord.scope` is `{ kind: "session" }`, `{ kind: "conversation", conversationId }`, or `{ kind: "task", taskId }` — [SPEC §3.2](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Reads by token:** `snapshot(token: SessionDocToken<T>, context)` (no conversation ID), `snapshot(token: ConversationDocToken<T>, conversationId, context)`, and family variants keyed by `key` — [SPEC §3.3 ~L1203-1218](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Atomic commits:** "`conversation.commit((tx) => ...)` can append entries, edit documents, and create tasks together; either all of it is stored or none of it." — [README "Concepts"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md). Invariant 1: "One Session commit is atomic across all record and document writes." Invariant 2: "A document update is published only after its storage commit succeeds." — [SPEC §1](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Who may watch:** "Tasks, hooks, and tools may observe any existing document for which their code has a token and owner/key. There is no additional subtree permission system inside trusted Session code." — [SPEC §9.2](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **watchDoc semantics:** it delivers "the exact immutable committed value and the exact operation batch that produced it". "A watch retains at most 100 pending committed frames"; overflow replaces them with one root replacement. "This is convergent observation, not an audit stream; consumers requiring every transition must persist those facts separately." `snapshot`/`documentState`/`watchDoc` "never create" a document; only typed `tx.doc()` creates — [SPEC §9.2, §3.3, §12](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). README: "`harness.watchDoc()` and `harness.documentState()` observe one document like the view above." — [README "Your Own State"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **subscribeCommits:** "observes complete immutable publications synchronously on the line after adoption ... their listeners must not block or call Session APIs" — [SPEC §4](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). From 1.2.0, throwing listeners are reported through `onReport` instead of failing the operation — [CHANGELOG 1.2.0](https://github.com/earendil-works/pi/blob/main/packages/durable/CHANGELOG.md).
- **Non-goals relevant to a board:** Durable has no "session-scoped rewindable documents" and no "CRDT/offline multi-writer merge" — [SPEC §13](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). Writes are serialized on one Session mutation line: "All changes go through one line of atomic commits" — [README "Concepts"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **Per-conversation docs in every conversation:** `HarnessOptions.conversationCreated(tx, conversation)` "runs in every commit that creates or forks a conversation, including a tool's raw `tx.createConversation()`" — [README "Your Own State"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **Fork policies (conversation scope only):** `fork: "initial" | "current" | "asOf"`; "`current`, `initial`, and `asOf` are product semantics, not optimizations" — [README], [SPEC §12](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Sections can render documents into the prompt:** "A section sees the resolved agent, the environment built for the request, and committed documents" — [README "System Prompt"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md). The spec warns that unstable section output defeats prompt caching — [SPEC §12](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Memory retention (≥1.2.0):** loaded docs that nothing observes leave memory after `documentRetentionMs` (default 10 minutes) and reload from storage — [SPEC §4](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md); [CHANGELOG 1.2.0](https://github.com/earendil-works/pi/blob/main/packages/durable/CHANGELOG.md).
- **Code mode store (≥1.2.0):** `store(key, value)`/`load(key)` "keep JSON values per conversation", which is per conversation, not shared — [README-main "Code Mode"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).

### Inferences
- A **session-scoped doc (or doc family keyed by board or topic)** is the natural shared board: a `post_to_board` tool commits a mutation, and a `read_board` tool or a prompt section reads it. A board-watcher background task can `watchDoc` it and `submit` follow-up inputs to interested conversations. Watch callbacks run off the mutation line, so submitting from them is allowed, but the overflow behaviour means a watcher can skip intermediate states. For guaranteed per-message handling, store messages as append-only list items or entries and track a cursor.
- Because writes are serialized and atomic, a board doc gives **linearizable** updates within one process. Multi-writer merge across processes is explicitly not provided.

### Gaps
- No documented example of a session-scoped document used for cross-conversation coordination (the examples use conversation-scoped docs: `app.subagents`, plan mode, todos).

## 4. Concurrency: scheduler, limits, single-process or single-owner storage, multi-process or distributed story

### Takeaway
One Harness runs **many conversations concurrently** in one process. The scheduler reserves eligible tasks serially on the Session line and runs handlers off it. I found **no global concurrency cap** in the spec or installed dist. Tool calls in a round run in parallel by default. The hard constraint is **single process, single owner per storage, with no cross-process locking**: watches and events are in-process only. Multi-client or multi-machine use means clients attaching to the owning process (the blog), or sharding into one storage per process or per Durable Object. An experimental client/server stack that did this was removed from main on 2026-10-12.

### Cited Findings
- **Scheduler:** "The scheduler serially reserves eligible tasks, then runs handlers off the Session line." — [SPEC §5.4](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). 1.2.0 scheduler scaling: "a tool making 8000 parallel nested calls finishes in 2.7 s"; "A chain of 500 owned tasks that took 12 s to settle takes 50 ms" — [CHANGELOG 1.2.0](https://github.com/earendil-works/pi/blob/main/packages/durable/CHANGELOG.md).
- **Parallel tools:** `toolExecution: ToolExecutionMode; // "parallel"` default, with per-tool `executionMode` — [SPEC §2.2 ~L411-438](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **No cap found:** grep of main spec and installed `dist/` for `maxConcurren|concurrencyLimit|maxParallel` returned nothing. The only "at most four" limit is for code-mode `models.*` internal calls — [SPEC §7.6 ~L3650](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md). (This is a negative result from search, not a documented statement.)
- **Many conversations:** "In Pi Durable, one harness runs as many conversations as you need, concurrently, all with the same guarantees." — [BLOG](https://earendil.com/posts/pi-durable/).
- **Single owner:** "One process owns a storage at a time; there is no cross-process locking." — [README "Storage"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md). "Old and new Harness instances must never own the same Session concurrently: open the new one after the old one's `close()` resolved" — [SPEC §7.5 ~L3596](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Blog's multi-client model:** "One process owns a storage at a time, and other clients attach to that process." and "That allows the harness to run on one machine while its tools run on another." The blog also says the harness "lets multiple humans steer the same agents" — [BLOG "Multiplayer"](https://earendil.com/posts/pi-durable/). (The transport is not named; my WebFetch summary reported only that state is small enough to "send over a socket".)
- **Watches are in-process only:** issue #10749 (2026-10-09) reported that a second process attached to the same SQLite sees a correct snapshot at attach but "zero post-attach events arrive cross-process", because `subscribeCommits` publishes only to in-process listeners. It was auto-closed. A maintainer (badlogic) replied "i have no idea wtf this issue is trying to tell me." No cross-process notification was added — [issue #10749](https://github.com/earendil-works/pi/issues/10749).
- **Remote client protocol:** `watch()` "delivers the same view with the exact Chord operations of each commit ... for example to a remote client that applies them"; "A client that joins late or reconnects starts from the current view; nothing is replayed." — [README "Watching a Conversation"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **Remote tools and envs:** "`env` builds the execution environment for each tool call ... one function serves a directory per conversation or a container per conversation" — [README "Environment"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md); the main README references pi-env's `RemoteExecutionEnv` — [README-main](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md).
- **Cloudflare (≥1.1.0, extended 1.3.0):** `openDurableObjectSqliteStorage(ctx.storage)` (1.1.0). In 1.3.0, "Multiple Pi storages opened through the Cloudflare adapter with the same storage object automatically share an operation queue", and `{ prefix }` namespaces tables — [CHANGELOG 1.1.0/1.3.0](https://github.com/earendil-works/pi/blob/main/packages/durable/CHANGELOG.md); [README-main "Storage"](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md). Each storage is still its own Session.
- **Non-goal:** no "forced termination of non-cooperative extension code inside one process"; "Safe forced termination ... requires worker/process isolation; that host terminates the process and reopens the Session from durable state." — [SPEC §13, §7.5](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md).
- **Removed experimental multi-process stack:** at v1.0.0, coding-agent had `src/experimental/` with `coordinator.ts`, `server.ts`, `client*.ts`, `session-worker*.ts` and `radius-relay.ts`, plus `packages/server` ("Experimental local server that routes clients to application-hosted durable Sessions ... A Session may have multiple presentation attachments") — [v1.0.0 packages/server/README.md](https://github.com/earendil-works/pi/blob/v1.0.0/packages/server/README.md). Commit 48dd1e2f (2026-10-01): "Session workers now host a durable Harness over a per-session sqlite storage. The server ... never opens the storage itself." Commit **7472cda0 (2026-10-12)**: "remove the experimental server stack and the client, protocol, and server packages", which deletes `packages/client`, `packages/protocol`, `packages/server` and coding-agent's `src/experimental` — [commit 7472cda0](https://github.com/earendil-works/pi/commit/7472cda0).
- **The experimental durable coding agent (v1.0.0) used a lock:** "a lock keeps a second process out (a lock left by a crash goes stale after 10 seconds...)" — [v1.0.0 experimental/durable/README.md](https://github.com/earendil-works/pi/blob/v1.0.0/packages/coding-agent/src/experimental/durable/README.md).

### Inferences
- For agents in **separate processes, harnesses or machines**, Pi Durable itself provides nothing for messaging between Sessions. You must bridge at the application level (for example a tool that calls an HTTP or queue endpoint served by the other process's host, which then calls `conversation.submit({ requestId })` there). The `requestId` dedupe on the receiving side gives idempotent admission for such a bridge.
- Putting all cooperating agents in **one Session/Harness** is the only setup where the documented durable guarantees (atomic cross-conversation commits, shared session docs, in-process watches, ownership-based abort) apply to agent-to-agent traffic.

### Gaps
- No documented concurrency limiter or rate limiting for model requests across conversations. Provider rate limits are left to pi-ai retry settings (`retry: { maxRetries }`).
- No documented sharding or multi-Session coordination guidance.

## 5. What do the design docs and Non-goals say about multi-agent coordination? Any roadmap or issue for peer messaging, A2A, MCP, mailboxes, teams?
